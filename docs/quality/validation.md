# Процедура валидации и результаты

Готовых датасетов и эталонной разметки нет, поэтому качество проверяется на **синтетике с известной истиной**: генератор порождает «настоящие» уровни кандидатов своей латентной моделью, а продукт видит только наблюдаемое (ответы, резюме, результаты). Генераторы устроены иначе, чем формулы продукта, — иначе проверка была бы тавтологией.

Все прогоны детерминированы по сиду и воспроизводятся одной командой:

```bash
make metrics            # всё сразу: тест, экспресс, подбор, банк заданий → reports/metrics/report.md
make eval-assessment    # только тест
make eval               # только подбор и разбор резюме
make families-check     # автопроверка банка заданий
make load               # нагрузка на живом стенде (после make up && make seed)
```

Цифры ниже — прогон `make metrics` (seed 42) от 11.10.2026.

## 1. Тест

**Как проверяем** (`tools/eval_assessment`). Симулятор проходит поток попытки на настоящих функциях ядра (`selection`, `sprt`, `psychometrics`, `integrity`, `lifecycle`) без БД. Истина — θ кандидата из N(0, 1), сложность `b` семейства, медиана времени ответа; продукт видит только баллы, время и уходы со вкладки. Банк — 300 семейств (10 % якорей), начальная `b` с шумом 0.5 относительно истинной.

Фазы:

1. **Основная** — 1000 кандидатов (10 % «списывающих»), каждый проходит тест дважды на разных вариантах; банк калибруется онлайн, тревоги работают.
2. **Полная длина** — фиксированные 20 заданий без остановки: насколько точно восстанавливается θ.
3. **Утечка** — у 20 % активных семейств утекли ответы, их знают 30 % новых кандидатов.
4. **LLM-кандидат** — отвечает верно с вероятностью `ai_solvable` семейства и мгновенно.

**Результаты:**

**LLM как кандидат.** Заявив Junior, модель получает Junior в 87 % случаев (метка «требует подтверждения» — 10 %); заявив Middle — Middle в 37 % (метка — 90 %); заявив Senior — Senior в 20 % (метка — 100 %). Чем выше грейд, тем больше заданий на мышление и тем чаще срабатывает индекс честности.

**Экспресс-режим** (6–8 заданий): 7.0 задания в среднем, точность вне зоны безразличия 69.6 % — это быстрый показ механики, а не замена основного теста; грейд помечен «экспресс».

**Почему точность по всей выборке 74 %, а не 90 %.** У кандидатов, чей уровень в пределах ±0.7 от порога, решение вероятностно при любом разумном тесте: для 90 % на всей выборке нужен SE(θ) ≈ 0.14, то есть около 200 заданий у порога. Проверено на симуляторе: фиксированные 50 заданий дают 78 %, SPRT с 60 заданиями — 80 % при средней длине 29. Поэтому цель — точность вне зоны безразличия (94 %), а у порога решение помечается «низкая уверенность», если тест дошёл до максимума. Подбор параметров — [ADR-0008](../adr/0008-assessment-rasch-sprt.md).

## 3. Подбор

**Как проверяем** (`tools/synth`, `tools/eval`). Синтетический рынок (seed 2002): 1000 кандидатов с латентными ролью, стажем, «талантом» и склонностью приукрашивать резюме (266 приукрашивают) и 115 потребностей. Истинная релевантность пары «потребность — кандидат» считается по скрытым уровням; подбор видит только наблюдаемое (резюме, тест, ФСП, GitHub). Веса подбора настраивались на другом рынке (seed 1001) и проверены на этом.

| Метод | precision@10 | nDCG@10 | Приукрашенных в топ-10 |
|---|---|---|---|
| BM25 по тексту резюме (база) | 0.118 | 0.145 | 20.1 % |
| BM25 + фильтры грейда и зарплаты | 0.246 | 0.344 | 22.3 % |
| **Наш подбор** | **0.275** | **0.372** | 20.1 % |
| — без доказательств из кода | 0.042 | 0.100 | 2.3 % |
| — без тестов | 0.277 | 0.373 | 19.7 % |
| — без ФСП | 0.272 | 0.365 | 19.5 % |

- Прирост nDCG@10 к BM25 — **+156.9 %** (цель ≥ +20 % ✅), к усиленной базе — +8.0 %; precision@10 — +132.3 % и +11.7 %.
- Категории потребности: настоящая роль кандидата среди предложенных категорий — 100 % потребностей.
- Вклад ФСП в nDCG@10: +0.006.

**Справедливость.** Impact ratio «без ФСП / с ФСП» при равном положении в грейде (T): 0.34 при ориентире 0.8–1.25. Это прямое следствие ТЗ («выше те, у кого есть результаты ФСП») и веса F = 0.2 в силе профиля; кандидат без ФСП не штрафуется, но участник ФСП с тем же T стоит выше. Вес вынесен в `scoring.yaml`.

## 5. Нагрузка и ресурсы

`make load` — Locust против живого стенда на ноутбуке разработчика (12 потоков, 4 ГБ под Docker, один процесс `core-api`, база с ≈ 450 кандидатами). Сценарий: работодатели ищут кандидатов и смотрят подборку под вакансию, кандидаты открывают профиль и стартуют тест. Пользователи вводятся не быстрее 9 в минуту: вход ограничен 10 запросами в минуту с одного IP.

| Пользователей | Запросов | Ошибок | Поиск, p50 / p95 | Подбор под вакансию, p50 / p95 | Профиль, p50 / p95 |
|---|---|---|---|---|---|
| 10 | 141 | 0 по сути (7 отказов входа из-за лимита) | 1.2 с / 4.4 с | 1.2 с / 7.8 с | 0.7 с / 2.7 с |
| 25 | 873 | 2 (0.2 %) | 6.3 с / 11 с | 7.1 с / 14 с | 2.4 с / 5.8 с |
| 50 | 1498 | 9 (0.6 %): 6 × 5xx, 3 × 401 (аккаунта нет в тестовой выборке) | 13 с / 25 с | 14 с / 26 с | 6 с / 18 с |

**Вывод: цель p95 ≤ 1 с не достигнута.** Поиск и подбор считаются в Python поверх выборки из БД; при 50 одновременных пользователях все запросы стоят в очереди к одному процессу, пул соединений к БД (5 + 10) исчерпывается и часть запросов получает 5xx. Одиночный запрос после прогрева — 130–280 мс, холодный — до нескольких секунд; страницы выдачи кешируются на 60 с. Для десятков пользователей, о которых говорит ТЗ, работоспособно, но не быстро.

Что снимет ограничение без смены архитектуры: несколько процессов `core-api` за gateway (сервис без состояния), увеличение пула соединений, предрасчёт карточек и счётчиков категорий при пересчёте профиля ([дорожная карта](../product/roadmap.md)).

**Память** после нагрузки: все контейнеры вместе ≈ 1.7 ГБ (core-api 280 МБ, PostgreSQL 134 МБ, core-worker 166 МБ, RabbitMQ 83 МБ, ml-worker-llm 93 МБ, ml-api 57 МБ, остальные меньше) — профиль без LLM укладывается в стенд проверки с большим запасом.

## 6. Что не измерено автоматически

- Точность категоризации «профессия × грейд» на живых людях — требует реальных кандидатов с экспертной оценкой; жюри проверяет её на своих синтетических профилях.
- F1 навыков резюме с LLM — нужен GPU; правиловая ветка измерена выше.
- Время `make up` с нуля.

## Ограничения

Рынок и кандидаты синтетические; модель списывания в симуляторе — половина списанных ответов быстрые, половина после ухода со вкладки; на живых данных пороги детектора нужно перепроверить. Показы и реакции работодателей логируются с первого дня, чтобы проверить подбор на реальных исходах.
