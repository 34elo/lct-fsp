# ADR-0001. Модульный монолит core и сервисы-спутники на RabbitMQ

**Статус:** принято · **Область:** Архитектура

## Контекст

Команда 4–5 человек, сжатые сроки, один сервер. Нужно понятное разделение ответственности и возможность масштабирования, но десяток микросервисов — избыточен.

## Решение

Доменная логика живёт в одном сервисе `core` (api + worker + scheduler) с модулями и жёсткими границами: модули общаются только через `service.py` друг друга. Отдельные сервисы — там, где другой профиль нагрузки или внешняя система: `ml` (модели, GPU), `fsp-connector` (внешний источник, своя БД), `bot` (внешний канал), `fsp-mock` (заменяемая имитация). Межсервисная шина — RabbitMQ: `events` (topic), `commands` (direct), `ui` (topic) для SSE. Redis — только кеш и короткое состояние.

## Почему

Одна БД и обычные транзакции для домена без распределённых саг; при этом контракты событий уже межпроцессные (`packages/contracts`), и любой модуль можно вынести в сервис. Приоритетная очередь `ml.llm` с `prefetch=1` решает дисциплину единственной GPU.

## Последствия

Больше инфраструктурных компонентов (RabbitMQ). Граница модулей поддерживается договорённостью и ревью; для пакетов — import-linter.
