# Сводка сессии вопросов и ответов

Сессия с организаторами (06.10.2026, не больше часа) и ответы в чате задачи (07.10.2026). Отвечали ментор, юрист ФСП, эксперт по веб-платформам и специалист по развитию продукта ФСП. Часть ответов организаторы обещали дать позже — они перечислены в конце.

Как каждое решение отразилось в продукте — в столбце «У нас».

## Главное

| Тема | Ответ организаторов | У нас |
|---|---|---|
| Грейд | Только по первичному тесту категории, не по вакансии и не по ФСП | Грейд пишет только завершённая попытка теста ([assessment.md](../mechanics/assessment.md)) |
| ФСП | Влияет на ранжирование внутри категории, не на грейд | Слагаемое F силы профиля, θ от ФСП не зависит |
| Неподтверждённый грейд | Лучше показывать со статусом и опускать в выдаче, чем прятать | Заявленный в опросе грейд хранится; в выдачу работодателю попадают только подтверждённые тестом, у кандидата — подсказка «пройдите тест» ([ADR-0011](../adr/0011-visible-only-after-test.md)) |
| Выбор грейда | Кандидат выбирает сам, тест подтверждает; подсказка по резюме допустима | Опрос предзаполняется из резюме, грейд выбирает кандидат |
| Повышение | Лучше отдельный тест, не автоповышение | Бонусный этап даёт приглашение на отдельный тест следующего грейда |
| Кулдаун | Нельзя скакать по грейдам; провал и уход ниже — без сжигания попытки | Смена грейда — раз в 90 дней, повтор того же — через 30, грейд ниже после провала — сразу |
| Банк заданий | Одинаковые задачи не должны расходиться | Свой вариант у каждого, общая шкала, экспозиция и тревога утечки |
| Песочница, прокторинг | Плюс, не обязательство | Код кандидата не исполняется; антисписывание — индекс честности без камер |
| LLM | Можно, предпочтительны российские и открытые; облачные допустимы; описать использование | LLM — сменный модуль, в тест и грейд не входит ([ml.md](../mechanics/ml.md)) |
| GPU | На стенде проверки нет | Обязательный путь работает без GPU и без LLM |
| Чужие вакансии | Импорт не нужен и нежелателен | Не делаем |
| Задания работодателя | Пишет работодатель; эталон проверяет система, открытый ответ — работодатель | Конструктор заданий, регулярные задания, задание в приглашении |
| FSP ID / Keycloak | Боевых доступов не будет; имитировать | Мок ФСП с OIDC-совместимым входом + реестр ФСП у администратора |
| Подбор | Минимум: категоризация, объяснимый подбор, адресное приглашение; оригинальность — плюс | Потребность → категории → кандидаты с объяснением → интерес → приглашение |
| Контакты | Открываются пригласившему после принятия; отзыв доступа — плюс | Раскрытие при `accepted`, кандидат может отозвать доступ |
| Чат | Не требовался, но плюс | Переписка по приглашению на сайте и в Telegram |
| Валидация | Своя процедура и результаты; жюри проверяет руками на своих синтетических профилях | Симуляция теста и синтетический рынок ([validation.md](../quality/validation.md)) |
| Стенд жюри | 32–64 ГБ RAM, ~8 CPU, без GPU | Профили `lite` и `standard` |
| После дедлайна | Идею не менять, контейнер переподнять можно | — |
| Несовершеннолетние | С 15 лет лёгкий труд, согласие родителей; плюс | Возрастная группа и согласие родителя в профиле |
| Зарплата | Гросс или нетто — неважно, но подписать | Поле `salary_basis`: «до НДФЛ» / «на руки» |
| Дизайн | Отход от гаммы ФСП не штрафуется | Свои токены в гамме ФСП |

## Ответы в чате задачи

| Вопрос | Ответ | У нас |
|---|---|---|
| ФСП — буст внутри грейда? Какие дисциплины важнее? | Все дисциплины равны; можно учитывать релевантность направления профессии | F = результативность × релевантность дисциплины профессии, уровни соревнований не ранжируются |
| Регулярные задания: адресно или челлендж? Кто оценивает? | По ТЗ адресно; оценка на усмотрение команды | Рассылка категории; автопроверка или рубрика работодателя |
| Как проверяют стабильность грейда? | Процедура команды: test-retest + разделяющая сила; симуляция допустима | Повторяемость κ, точность, r_pb в отчёте метрик |
| Грейд — стаж или навыки? | Уровень навыков по тесту; стаж — атрибут профиля | Грейд из θ, стаж в профиле |
| Несколько категорий? | Не обязательно, но плюс | Грейд на каждую профессию отдельно |
| Облачные LLM? | Допустимы, в том числе зарубежные; риски 152-ФЗ на команде | Локальный llama-server; облако — только настройкой, на стенде не используется |
| Что видит работодатель? | ФИО и места работы можно; закрыты только контакты | Видимость настраивает кандидат; контакты — только после принятия |
| Тест под категорию или под вакансию? | Единый под категорию, но не одинаковый пул; под вакансию — необязательные задания | Тест по профессии; задания работодателя отдельно, в θ не идут |
| Ограничения по образам и RAM | Явных нет, расход обоснован | Профили запуска ([running.md](../operations/running.md)) |
| Скорость или качество? | Качество подбора (35 %) важнее техники (7 %) | Веса подбора подобраны на размеченных парах |
| Категория = специализация + грейд? | Достаточно; детальнее — плюс | Плюс стек, формат, город в фильтрах |
| Антисписывание обязательно? | Нет, но большой плюс | Индекс честности, метка «требует подтверждения» |
| ATS | Синхронизация вакансий, откликов, статусов через API; в MVP — концепция | [Концепция](../architecture/overview.md#концепции-за-рамками-mvp) |
| Минимальный охват | Двух специализаций с двумя грейдами достаточно, если путь работает | Полный банк для Backend, Frontend, AI Engineer; остальные профессии помечены «бета» |
| Дизайнеры | Могут быть в справочнике; приоритет — техническим ролям | Профессия «Дизайнер» в справочнике |

## Термины

- **Грейд** — уровень (Junior, Middle, Senior); у нас присваивается тестом.
- **Категория** — профессия × грейд, внутри которой сравнивают людей.
- **Разделяющая сила** — способность теста отличать грейды друг от друга.
- **Кулдаун** — пауза перед повторной сменой грейда.
- **Keycloak / FSP ID** — сервер идентификации и единый аккаунт участника ФСП; вход по OAuth 2.0 / OpenID Connect.
- **ATS** — система учёта кандидатов у работодателя.
- **Объяснимый подбор** — работодатель видит, почему кандидат попал в выдачу.
- **Адресное приглашение** — работодатель сам зовёт конкретного кандидата.
