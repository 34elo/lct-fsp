# Журнал архитектурных решений (ADR)

Формат: контекст → решение → последствия. Новое решение добавляем в конец со следующим номером. Отменённое не удаляем, а помечаем «Заменено ADR-NNN».

---

### ADR-001. Модульный монолит + спутники вместо мелких микросервисов
**Статус:** изменено ADR-012 (2026-10-02) · принято 2026-10-01
**Контекст:** 4–5 человек, ~10 дней, один сервер. Жюри хочет видеть продуманную архитектуру, но работающий продукт важнее числа сервисов.
**Решение:** доменная логика живёт в одном `core` (API + воркер) с модулями и проверкой границ через import-linter. Отдельные процессы: `ml` (другой профиль нагрузки, GPU), `tg-bot` (внешний канал), `fsp-mock` (заменяемая внешняя система), `llm-chat` (рантайм модели).
**Последствия:** одна БД и транзакции без распределённых саг. Любой модуль core можно позже вынести в сервис: контракты событий и задач уже межпроцессные (`packages/contracts`).

### ADR-002. Python для всех сервисов
**Статус:** принято
**Контекст:** ML на Python. Бэкенд согласен на любой стек.
**Решение:** Python 3.12 + FastAPI в core, ml, mock; aiogram в боте; uv workspace.
**Последствия:** общие pydantic-контракты без кодогенерации, OpenAPI из кода. Производительности хватает с запасом для тысяч профилей.

### ADR-003. Один React + Vite SPA, без Next.js и без второго фронт-проекта
**Статус:** принято
**Контекст:** SEO не нужен, публичные страницы нужны минимально (бейдж, превью профиля). Mini App не делаем.
**Решение:** SPA с ленивыми разделами по ролям. Бейдж — SVG с бэкенда. OG-превью — HTML с бэкенда для краулеров.
**Последствия:** простой деплой статикой, нет синхронизации cookie между Next и API. Настоящий SEO-лендинг при необходимости — отдельно на Astro.

### ADR-004. PostgreSQL + pgvector + pg_trgm вместо Elasticsearch и векторной БД
**Статус:** принято
**Контекст:** тысячи кандидатов, гибрид «жёсткие фильтры + смысл + скоринг».
**Решение:** фильтры, FTS и HNSW-поиск в одном SQL-запросе, скоринг в Python.
**Последствия:** минус два сервиса, транзакционная согласованность. При росте до сотен тысяч профилей — OpenSearch как read-модель из outbox.

### ADR-005. Redis (Streams) + Taskiq вместо Kafka и RabbitMQ
**Статус:** заменено ADR-012 (2026-10-02)
**Контекст:** нужны фоновые задачи с подтверждениями, cron, pub/sub для SSE, кеш, лимиты.
**Решение:** один Redis на всё. Очереди — Taskiq на Redis Streams. Ключи кеша всегда с TTL, `volatile-lru`.
**Последствия:** один инфраструктурный компонент. Запасной вариант — arq, вызовы спрятаны за `enqueue()`.

### ADR-006. llama.cpp (Vulkan) как LLM-рантайм
**Статус:** принято, модель выбираем замером в Д0
**Контекст:** RX 5700 XT 8 ГБ (gfx1010) не поддерживается ROCm официально. Облака нет. Требование — только локальные модели.
**Решение:** `llama-server` с бэкендом Vulkan, модель 7–8B Q4_K_M, JSON-schema-ограниченная генерация, 2 слота. Эмбеддинги на CPU.
**Последствия:** одна GPU — строгая дисциплина очередей и агрессивное кеширование. Есть CPU-профиль для аварий.

### ADR-007. Transactional outbox для доменных событий
**Статус:** принято
**Контекст:** нельзя терять офферы, принятия и новые результаты ФСП между записью в БД и постановкой задачи.
**Решение:** событие пишется в `outbox` в той же транзакции. Relay (LISTEN/NOTIFY + поллинг 500 мс) раздаёт его в обработчики. Обработчики идемпотентны.
**Последствия:** доставка at-least-once с задержкой ≤ 1 с, push об оффере укладывается в цель ≤ 3 с.

### ADR-008. Объяснимый скоринг по правилам вместо обучаемых моделей
**Статус:** принято
**Контекст:** реальных исходов найма нет, кейс требует объяснимости и «подтверждаемости».
**Решение:** доверие (noisy-OR по источникам), категория (взвешенное покрытие профилей ролей), грейд (сумма сигналов), матчинг (взвешенная сумма + жёсткие фильтры) — формулы с весами в конфиге. LLM только извлекает и формулирует.
**Последствия:** каждое решение объяснимо со ссылками на доказательства, честное сравнение с базовым решением на синтетике. Реакции на офферы собираем для будущего обучения ранжирования.

### ADR-009. SSE вместо WebSocket
**Статус:** принято
**Решение:** поток «сервер → клиент» через SSE, действия клиента — обычным REST.
**Последствия:** работает через любые прокси, автоматическое переподключение, нет отдельного протокола.

### ADR-010. Бот на long polling, без Mini App
**Статус:** принято
**Контекст:** домашний сервер за VPS-прокси, мобильного разработчика нет.
**Решение:** aiogram long polling. Сложные экраны — адаптивный сайт по одноразовой ссылке.
**Последствия:** не нужен входящий webhook. Mini App в дорожной карте: адаптивные экраны кандидата потом переиспользуются.

### ADR-011. Порт `FspPort` и собственный мок до появления спецификации
**Статус:** принято
**Контекст:** спецификация ФСП ещё не выдана, а интеграция — сердце кейса.
**Решение:** ядро работает с нормализованными DTO через порт. Наш мок реализует предполагаемый API, OAuth, коды и вебхуки. Под API организаторов пишется отдельный адаптер с маппингом.
**Последствия:** разработка не блокируется. Требование Q6 «тестовые и реальные данные без переделки» закрыто архитектурно.

### ADR-012. Пять логических сервисов и RabbitMQ как шина
**Статус:** принято · 2026-10-02 (изменяет ADR-001, заменяет ADR-005)
**Контекст:** команда хочет понятное разделение на сервисы и классический брокер, но десяток микросервисов — перебор для 4–5 человек.
**Решение:** сервисы web, core (api + worker + scheduler), ml (api + worker-llm + worker-code), fsp-connector, bot (+ fsp-mock). Межсервисное взаимодействие — RabbitMQ: topic-обменник `events`, direct-обменник `commands`, topic-обменник `ui` для SSE. Библиотека FastStream, контракты в `packages/contracts`, AsyncAPI. Redis — только кеш и короткое состояние.
**Последствия:** у каждого сервиса понятный смысл и владелец. Приоритетная очередь `ml.llm` с `prefetch=1` встроенно решает дисциплину единственной GPU. Выросло число компонентов (RabbitMQ), но это классика с веб-интерфейсом, который можно показать жюри.

### ADR-013. Граф доказательств в PostgreSQL: типизированные таблицы + проекции
**Статус:** принято · 2026-10-02
**Решение:** граф хранится в типизированных таблицах вершин и рёбер, плюс представление `graph_edges` для выгрузки и визуализации. Граф навыков держится в памяти core. Подграф кандидата загружается целиком при пересчёте. Обратные запросы идут по индексам проекций (`candidate_skills`, HNSW). Neo4j и Apache AGE не используем.
**Последствия:** транзакции вместе с офферами и вакансиями, pgvector в тех же запросах, одна база. Глубокие обходы делаются при записи, при чтении — максимум один шаг по смежности.

### ADR-014. Рекомендации: контентные + подстройка в сессии, показы логируем с первого дня
**Статус:** принято · 2026-10-02
**Решение:** в MVP — уровень 0 (граф + эмбеддинги + формула) и уровень 1 (Роккио + онлайн-подстройка весов в сессии работодателя, uplift для кандидата). Learning-to-rank, последовательные и генеративные модели («следующий кандидат как токен», семантические ID) — в дорожной карте. Таблицы `impressions` и `rec_feedback` пишутся с первого дня.
**Последствия:** работает без истории, объяснимо. Данные для будущего обучения накапливаются корректно, с позициями показа.

### ADR-015. Outbox + inbox
**Статус:** принято · 2026-10-02
**Решение:** у сервисов с БД события пишутся в outbox в той же транзакции и публикуются с publisher confirms. Потребители core отмечают обработанные сообщения в inbox.
**Последствия:** ничего не теряется и не дублируется при повторной доставке.

### ADR-016. Граф навыков: ядро + рост
**Статус:** принято · 2026-10-02
**Решение:** ядро на 150–250 навыков (теги Stack Overflow с синонимами, карта пакетов, русские названия, правила ФСП). Новые навыки появляются как вершины через конвейер: нормализация → синонимы → нечёткий поиск → модерация (цензурность, «навык ли это») → судья по типу связи (reranker + локальная LLM) → `provisional` → `active` по поддержке или решению админа. Связи нарастают по совместной встречаемости (NPMI), веса ролей — по lift. Новые навыки участвуют в подборе со слабым доверием.
**Последствия:** граф растёт вместе с платформой, нет ручной поддержки длинного хвоста. Нужен человек в контуре для спорных решений, таблица «точно разные» против ловушек вида Java/JavaScript.

### ADR-017. Софт-навыки — командные сигналы с ограниченным коэффициентом
**Статус:** принято · 2026-10-02
**Решение:** софт-навыки не получают точек доверия. Четыре командных сигнала (лидерство, командная работа, результативность, рост) считаются только из фактов (капитанство, командные выступления, траектория результатов, мейнтейнерство). Они дают коэффициент `K_soft = 1 + min(β, Σ α_k·s_k)` с весами по грейду вакансии и потолком β ≤ 0.12, а лидерство даёт `+1.5·L` к баллам грейда. Никакого вывода качеств из голоса, мимики или тональности текста.
**Последствия:** софт-навыки влияют, но не перекрывают навыки. Справедливость контролируется impact ratio для группы «без ФСП».

### ADR-018. Категория и грейд определяются тестом
**Статус:** принято (рабочее) · 2026-10-05 (меняет ADR-008 в части категории и грейда)
**Контекст:** ТЗ прямо требует определять категорию обязательным путём «опрос → выбор грейда → тест», а не по резюме. Сейчас категория и грейд считаются по доказательствам.
**Решение:** категория = профессия × грейд, подтверждённый тестом. Без теста кандидат не виден в поиске. Доказательства (резюме, ФСП, GitHub) больше не задают категорию: они формируют силу профиля внутри категории и объяснения.
**Последствия:** E4-3 и E4-4 перестают определять категорию и грейд, их сигналы уходят в силу профиля. Появляется модуль `assessment`.

### ADR-019. Модель навыков: шесть типов, профессии как профили
**Статус:** принято (рабочее) · 2026-10-05
**Решение:** навык получает тип: фундамент, хард, мышление, бизнес, софт или опыт. У навыка есть карточка: утверждения по уровням, понятия, заблуждения. Профессия — взвешенный набор навыков (бывший `roles.yaml`). Категория — проекция профиля человека на профессии, человек может состоять в нескольких. Новые профессии находятся кластеризацией векторов вакансий и профилей, админ их подтверждает. Грейд — универсальная шкала для всех профессий.
**Последствия:** новая профессия добавляется данными, без кода. Софт по SJT показывается отдельно от точек доверия, ADR-017 сохраняется.

### ADR-020. Тестирование: семейства с формальным ответом, Rasch + SPRT
**Статус:** принято (рабочее) · 2026-10-05 (заменяет 3PL из ml.md)
**Решение:**
- задания строятся по Evidence-Centered Design, технический дизайн — [assessment.md](assessment.md);
- семейство = генератор + решатель + ручки сложности, вариант задаётся `seed`;
- правильный ответ берётся только из вычисления, порчи эталона с формальной проверкой или таблицы стратегий с эмпирическим ключом;
- сложность принадлежит семейству: экспертная оценка → пилотные слоты → онлайн-калибровка Rasch и Elo → якоря, плюс рейтинг ФСП;
- грейд определяет классификационный тест SPRT у порога заявленного грейда, повышение — через бонусный этап;
- кулдауны: смена грейда — 90 дней, повтор — 30 дней, результат действует 12 месяцев.
**Последствия:** сопоставимость обеспечивает общая шкала, а не одинаковые задания. 3PL без данных не откалибровать, поэтому отказываемся от неё.

### ADR-021. «Мир» — контекст варианта задания
**Статус:** принято (рабочее) · 2026-10-05, упрощено в тот же день
**Решение:** `World.from_seed(seed, domain)` даёт вымышленную компанию: домен, словарь сущностей, сервисы как граф, таблицы с данными, метрики, команду. Семейства берут из мира имена, числа и артефакты. Домен задаёт вакансия (e-commerce, финтех, RAG-сервис для AI Engineer). Мир — не отдельный движок, а общий вход для генераторов. Цепочки-инциденты и офлайн-конвейер LLM — фичи поверх него.
**Последствия:** один механизм закрывает уникальность вариантов, «тест под вакансию» и задания по архитектуре и данным. Минимальный мир появляется уже в E22-1, полный — в E26-1.

### ADR-022. Приглашение без вакансии, отклики — офферы с инициатором
**Статус:** принято (рабочее) · 2026-10-05
**Решение:** у `offers` поле `vacancy_id` становится необязательным. Добавляются поля `title`, `description`, `contact_method` и `initiator` (`employer` или `candidate`). Отклик кандидата — это запись с `initiator = candidate`: та же машина статусов и то же правило раскрытия контактов.
**Последствия:** один поток статусов для обеих сторон. Нужен `/contract` и `schema_version` событий офферов.

### ADR-023. Профили запуска; LLM — сменный модуль
**Статус:** принято (рабочее) · 2026-10-05
**Решение:**

| Профиль | RAM | Что работает |
|---|---|---|
| `lite` | ≈ 1–1.5 ГБ | Всё ядро и ML без LLM, малая модель эмбеддингов |
| `standard` | ≈ 4 ГБ | + малая LLM на CPU |
| `full` | GPU | Наш стенд |

Тест, калибровка, категории и подбор от LLM не зависят. Банк семейств генерируется офлайн и лежит в репозитории.
**Последствия:** выполняется требование ТЗ к железу. Без LLM хуже работают разбор резюме и оценка открытых ответов, ядро не страдает.

### ADR-024. Допуск заданий через админа и пилот; у каждой LLM-функции есть альтернатива
**Статус:** принято (рабочее) · 2026-10-05 (уточняет ADR-020, ADR-023)
**Решение:**
- Задания поступают из процедурных генераторов, майнинга мутаций открытого кода, графа навыков, конструктора (работодатели, эксперты, админ) и LLM.
- Любое задание проходит путь `draft → pilot → active` и влияет на балл только после **решения админа и статистики пилота**.
- LLM может дать **примерный правильный ответ**, ключ и рубрику, но всегда как черновик: ключ утверждает админ, затем уточняет эмпирический ключ пилота.
- Флаг `LLM_ENABLED`: у каждой LLM-функции есть правиловая или ручная реализация (таблица — solution.md §3).
**Последствия:** банк растёт без модели. Работодатели становятся соавторами заданий, это закрывает регулярные задания из ТЗ. Нужна админская очередь допуска (E30-4).

### ADR-030. Параметры SPRT, бонуса, честности и тревоги утечки по eval
**Статус:** принято (рабочее) · 2026-10-06 (E27-1, уточняет ADR-020; числа — `data/scoring.yaml`, `assessment.*`)
**Контекст:** `make eval-assessment` (seed 42, 1000 кандидатов) с исходными числами (δ = 0.4, 6–20 заданий, бонус при θ ≥ cut_след − 0.5 до 6 заданий) не выполнял цели metrics.md §9.1. Точность грейда — 0.714 (цель ≥ 0.9), κ — 0.489 (≥ 0.8). До максимума доходили 38 % попыток (≤ 10 %): SPRT у порога при δ = 0.4 — блуждание с шагом ±0.4 до ±2.197, в среднем около 30 шагов. Детектор честности ловил 8.8 % списывающих. В фазе без утечки было 29 карантинов: тревога по доле верных срабатывала на сдвиг состава кандидатов.
**Решение:**
- SPRT: δ = 0.7, α = β = 0.1, минимум 10, максимум 24 задания. Широкую зону безразличия компенсирует минимум 10.
- Бонус: прошёл за ≤ 10 заданий и θ̂ ≥ cut_следующего (`margin` = 0), до 10 заданий. Мягкий бонус давал около половины завышений: при выключенном бонусе завышение падает с 0.16 до 0.07, κ растёт до 0.59.
- Честность: «быстрый верный» считается на нелёгком задании (θ − b < 0.5 вместо < −0.5). Уход со вкладки: −0.15 за каждый, максимум −0.45. Порог `I < 0.6` прежний: пометку дают три ухода перед верными ответами или уход и быстрые ответы.
- Утечка: средний **остаток** `y − P(θ, b)` за последние 50 ответов минус средний остаток за предыдущие, ≥ 0.2 (раньше — разница долей верных). Поле `families.stats.leak` и его тип не меняются, меняется только смысл числа.

Подбор (`seed` 42; где три сида — среднее по 42, 7, 2026). Колонки: точность грейда, κ, среднее число заданий основного этапа, доля попыток до максимума, завышенный грейд у честных, ложные повышения у «знающих», карантины без утечки.

| Параметры | Точн. | κ | Заданий | До max | Завыш. | Утечка | Карантин |
|---|---|---|---|---|---|---|---|

Тревога утечки при δ 0.7, 10–24, бонус 0/10 (сиды 42 и 7). Остатки, окно 50, порог 0.2: 9 карантинов без утечки, 1.5 неутёкших в фазе утечки. Доля верных с теми же числами: 13.5 и 4.5. Порог 0.15 или окно 20–30 дают 40–150 ложных карантинов. Порог 0.25 почти не ловит утечку: в карантин попадает 6 % утёкших. Честность при тех же SPRT: TPR 0.06 → 0.85, FPR 0 → 0.003.

**Что не достигнуто и почему:**
- **Точность ≥ 0.9 и κ ≥ 0.8 недостижимы для модели Rasch с порогами через 1 SD θ (N(0, 1), пороги −1/0/1).** Доля ошибок классификации ≈ 0.7·SE(θ̂). Для 0.9 нужен SE ≈ 0.14, то есть информация ≈ 50, это около 200 заданий у порога. Проверено: фиксированные 50 заданий дают 0.78, 60 заданий с SPRT — 0.80 при 29 заданиях в среднем. Достижимая цель — точность вне зоны безразличия (|θ − cut| ≥ δ): 0.94 при seed 42.
- **Ложные повышения у «знающих» ≤ 5 % тоже недостижимы:** у честных кандидатов тот же отчёт даёт 13 % завышений из-за ошибки измерения. Вклад самой утечки (прирост над фоном) — 0.11–0.12, было 0.18–0.20. Утёкшее семейство в фазе утечки чаще всего не набирает и 50 ответов, поэтому окно тревоги не успевает заполниться.
- RMSE калибровки после 100 ответов (0.29–0.31 при цели ≤ 0.25) не подбирался: калибровка вне этой задачи.
- Детектор честности настроен на модель списывания из симулятора (половина списанных — быстро, половина — с уходом со вкладки). На живых данных пороги надо перепроверить (metrics.md §9.2).

**Последствия:** тест длиннее на минимуме (10 заданий вместо 6), но в среднем короче (13.1 против 14.4) и редко доходит до максимума. Решения у порога, в зоне ±0.7, остаются вероятностными, на максимуме — с пометкой «низкая уверенность». Цели §9.1 по точности и κ нужно пересмотреть: либо мерить точность вне зоны безразличия, либо принять тест около 60 заданий. Решают люди.
### ADR-050. UI — пакет `@fsp/ui`, эталон вида — `docs/design/pack`
**Статус:** принято · 2026-10-06 (E19-0, блок 2)
**Решение:**
- Компоненты, токены и `@theme` живут в `packages/ui` (пакет `@fsp/ui`, без сборки, экспорт из исходников). Экраны `apps/web` собираются из него.
- Эталон вида — `docs/design/pack` (PNG экранов, токены, `fsp-ui.tsx`); сверка скриншотами `pnpm shot`.
- pnpm-workspace в корне (`apps/web`, `packages/ui`), один `pnpm-lock.yaml`; uv-workspace перечисляет Python-пакеты явно, чтобы не принять `packages/ui` за Python-пакет.
**Последствия:** `apps/web/Dockerfile` и CI собираются из корня. Старые пути `shared/brand`, `shared/ui/button`, `shared/lib/cn` — временные реэкспорты до E19-15.
