# Журнал архитектурных решений (ADR)

Формат: контекст → решение → последствия. Новое решение добавляем в конец со следующим номером. Отменённое не удаляем, а помечаем «Заменено ADR-NNN».

---

### ADR-001. Модульный монолит + спутники вместо мелких микросервисов
**Статус:** изменено ADR-012 (2026-10-02) · принято 2026-10-01
**Контекст:** 4–5 человек, ~10 дней, один сервер. Жюри хочет видеть продуманную архитектуру, но работающий продукт важнее числа сервисов.
**Решение:** доменная логика живёт в одном `core` (API + воркер) с модулями и проверкой границ через import-linter. Отдельные процессы: `ml` (другой профиль нагрузки, GPU), `tg-bot` (внешний канал), `fsp-mock` (заменяемая внешняя система), `llm-chat` (рантайм модели).
**Последствия:** одна БД и транзакции без распределённых саг. Любой модуль core можно позже вынести в сервис: контракты событий и задач уже межпроцессные (`packages/contracts`).

### ADR-002. Python для всех сервисов
**Статус:** принято
**Контекст:** ML на Python. Бэкенд согласен на любой стек.
**Решение:** Python 3.12 + FastAPI в core, ml, mock; aiogram в боте; uv workspace.
**Последствия:** общие pydantic-контракты без кодогенерации, OpenAPI из кода. Производительности хватает с запасом для тысяч профилей.

### ADR-003. Один React + Vite SPA, без Next.js и без второго фронт-проекта
**Статус:** принято
**Контекст:** SEO не нужен, публичные страницы нужны минимально (бейдж, превью профиля). Mini App не делаем.
**Решение:** SPA с ленивыми разделами по ролям. Бейдж — SVG с бэкенда. OG-превью — HTML с бэкенда для краулеров.
**Последствия:** простой деплой статикой, нет синхронизации cookie между Next и API. Настоящий SEO-лендинг при необходимости — отдельно на Astro.

### ADR-004. PostgreSQL + pgvector + pg_trgm вместо Elasticsearch и векторной БД
**Статус:** принято
**Контекст:** тысячи кандидатов, гибрид «жёсткие фильтры + смысл + скоринг».
**Решение:** фильтры, FTS и HNSW-поиск в одном SQL-запросе, скоринг в Python.
**Последствия:** минус два сервиса, транзакционная согласованность. При росте до сотен тысяч профилей — OpenSearch как read-модель из outbox.

### ADR-005. Redis (Streams) + Taskiq вместо Kafka и RabbitMQ
**Статус:** заменено ADR-012 (2026-10-02)
**Контекст:** нужны фоновые задачи с подтверждениями, cron, pub/sub для SSE, кеш, лимиты.
**Решение:** один Redis на всё. Очереди — Taskiq на Redis Streams. Ключи кеша всегда с TTL, `volatile-lru`.
**Последствия:** один инфраструктурный компонент. Запасной вариант — arq, вызовы спрятаны за `enqueue()`.

### ADR-006. llama.cpp (Vulkan) как LLM-рантайм
**Статус:** принято, модель выбираем замером в Д0
**Контекст:** RX 5700 XT 8 ГБ (gfx1010) не поддерживается ROCm официально. Облака нет. Требование — только локальные модели.
**Решение:** `llama-server` с бэкендом Vulkan, модель 7–8B Q4_K_M, JSON-schema-ограниченная генерация, 2 слота. Эмбеддинги на CPU.
**Последствия:** одна GPU — строгая дисциплина очередей и агрессивное кеширование. Есть CPU-профиль для аварий.

### ADR-007. Transactional outbox для доменных событий
**Статус:** принято
**Контекст:** нельзя терять офферы, принятия и новые результаты ФСП между записью в БД и постановкой задачи.
**Решение:** событие пишется в `outbox` в той же транзакции. Relay (LISTEN/NOTIFY + поллинг 500 мс) раздаёт его в обработчики. Обработчики идемпотентны.
**Последствия:** доставка at-least-once с задержкой ≤ 1 с, push об оффере укладывается в цель ≤ 3 с.

### ADR-008. Объяснимый скоринг по правилам вместо обучаемых моделей
**Статус:** принято
**Контекст:** реальных исходов найма нет, кейс требует объяснимости и «подтверждаемости».
**Решение:** доверие (noisy-OR по источникам), категория (взвешенное покрытие профилей ролей), грейд (сумма сигналов), матчинг (взвешенная сумма + жёсткие фильтры) — формулы с весами в конфиге. LLM только извлекает и формулирует.
**Последствия:** каждое решение объяснимо со ссылками на доказательства, честное сравнение с базовым решением на синтетике. Реакции на офферы собираем для будущего обучения ранжирования.

### ADR-009. SSE вместо WebSocket
**Статус:** принято
**Решение:** поток «сервер → клиент» через SSE, действия клиента — обычным REST.
**Последствия:** работает через любые прокси, автоматическое переподключение, нет отдельного протокола.

### ADR-010. Бот на long polling, без Mini App
**Статус:** принято
**Контекст:** домашний сервер за VPS-прокси, мобильного разработчика нет.
**Решение:** aiogram long polling. Сложные экраны — адаптивный сайт по одноразовой ссылке.
**Последствия:** не нужен входящий webhook. Mini App в дорожной карте: адаптивные экраны кандидата потом переиспользуются.

### ADR-011. Порт `FspPort` и собственный мок до появления спецификации
**Статус:** принято
**Контекст:** спецификация ФСП ещё не выдана, а интеграция — сердце кейса.
**Решение:** ядро работает с нормализованными DTO через порт. Наш мок реализует предполагаемый API, OAuth, коды и вебхуки. Под API организаторов пишется отдельный адаптер с маппингом.
**Последствия:** разработка не блокируется. Требование Q6 «тестовые и реальные данные без переделки» закрыто архитектурно.

### ADR-012. Пять логических сервисов и RabbitMQ как шина
**Статус:** принято · 2026-10-02 (изменяет ADR-001, заменяет ADR-005)
**Контекст:** команда хочет понятное разделение на сервисы и классический брокер, но десяток микросервисов — перебор для 4–5 человек.
**Решение:** сервисы web, core (api + worker + scheduler), ml (api + worker-llm + worker-code), fsp-connector, bot (+ fsp-mock). Межсервисное взаимодействие — RabbitMQ: topic-обменник `events`, direct-обменник `commands`, topic-обменник `ui` для SSE. Библиотека FastStream, контракты в `packages/contracts`, AsyncAPI. Redis — только кеш и короткое состояние.
**Последствия:** у каждого сервиса понятный смысл и владелец. Приоритетная очередь `ml.llm` с `prefetch=1` встроенно решает дисциплину единственной GPU. Выросло число компонентов (RabbitMQ), но это классика с веб-интерфейсом, который можно показать жюри.

### ADR-013. Граф доказательств в PostgreSQL: типизированные таблицы + проекции
**Статус:** принято · 2026-10-02
**Решение:** граф хранится в типизированных таблицах вершин и рёбер, плюс представление `graph_edges` для выгрузки и визуализации. Граф навыков держится в памяти core. Подграф кандидата загружается целиком при пересчёте. Обратные запросы идут по индексам проекций (`candidate_skills`, HNSW). Neo4j и Apache AGE не используем.
**Последствия:** транзакции вместе с офферами и вакансиями, pgvector в тех же запросах, одна база. Глубокие обходы делаются при записи, при чтении — максимум один шаг по смежности.

### ADR-014. Рекомендации: контентные + подстройка в сессии, показы логируем с первого дня
**Статус:** принято · 2026-10-02
**Решение:** в MVP — уровень 0 (граф + эмбеддинги + формула) и уровень 1 (Роккио + онлайн-подстройка весов в сессии работодателя, uplift для кандидата). Learning-to-rank, последовательные и генеративные модели («следующий кандидат как токен», семантические ID) — в дорожной карте. Таблицы `impressions` и `rec_feedback` пишутся с первого дня.
**Последствия:** работает без истории, объяснимо. Данные для будущего обучения накапливаются корректно, с позициями показа.

### ADR-015. Outbox + inbox
**Статус:** принято · 2026-10-02
**Решение:** у сервисов с БД события пишутся в outbox в той же транзакции и публикуются с publisher confirms. Потребители core отмечают обработанные сообщения в inbox.
**Последствия:** ничего не теряется и не дублируется при повторной доставке.

### ADR-016. Граф навыков: ядро + рост
**Статус:** принято · 2026-10-02
**Решение:** ядро на 150–250 навыков (теги Stack Overflow с синонимами, карта пакетов, русские названия, правила ФСП). Новые навыки появляются как вершины через конвейер: нормализация → синонимы → нечёткий поиск → модерация (цензурность, «навык ли это») → судья по типу связи (reranker + локальная LLM) → `provisional` → `active` по поддержке или решению админа. Связи нарастают по совместной встречаемости (NPMI), веса ролей — по lift. Новые навыки участвуют в подборе со слабым доверием.
**Последствия:** граф растёт вместе с платформой, нет ручной поддержки длинного хвоста. Нужен человек в контуре для спорных решений, таблица «точно разные» против ловушек вида Java/JavaScript.

### ADR-017. Софт-навыки — командные сигналы с ограниченным коэффициентом
**Статус:** принято · 2026-10-02
**Решение:** софт-навыки не получают точек доверия. Четыре командных сигнала (лидерство, командная работа, результативность, рост) считаются только из фактов (капитанство, командные выступления, траектория результатов, мейнтейнерство). Они дают коэффициент `K_soft = 1 + min(β, Σ α_k·s_k)` с весами по грейду вакансии и потолком β ≤ 0.12, а лидерство даёт `+1.5·L` к баллам грейда. Никакого вывода качеств из голоса, мимики или тональности текста.
**Последствия:** софт-навыки влияют, но не перекрывают навыки. Справедливость контролируется impact ratio для группы «без ФСП».
