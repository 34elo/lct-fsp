## 3. Синтетический рынок (`tools/synth`)

**Правило честности:** генератор устроен **иначе**, чем наш подбор. Скрытые «настоящие» уровни навыков порождает собственная латентная модель, а не наши формулы доверия. Иначе мы угадываем сами себя.

### 3.1. Кандидаты (по умолчанию 1000)
1. **Латентные факторы:**
   - роль ~ рыночное распределение (бэкенд 30%, фронтенд 22%, …);
   - стаж ~ Gamma;
   - талант `τ ~ N(0, 1)`;
   - склонность приукрашивать `π ~ Bernoulli(0.25)`.
2. **Настоящий уровень навыка** `t_s ∈ [0, 1]` для навыков профиля роли: `sigmoid(a_s·τ + b_s·log(1 + стаж) + шум)`. Плюс 0–3 случайных навыка из смежных ролей.
3. **Наблюдаемые сигналы с искажениями:**
   - **резюме:** навыки с `t_s > 0.3` попадают с вероятностью 0.85. При `π = 1` добавляются 1–4 навыка с `t_s < 0.15` (приукрашивание), а стаж завышается на 0–12 мес;
   - **ФСП** (у 40%): соревнования, где место определяется скрытой силой `t_discipline + шум` среди сгенерированных соперников. Получаем место из N, уровень, роль капитана (с вероятностью, растущей с τ);
   - **GitHub** (у 50%): технологии с `t_s > 0.4` с вероятностью 0.7, доля авторства. У 10% репозиториев признаки подделки;
   - **тесты** (у 30%): ответы по 3PL от `θ = 4·(t_s − 0.5)` с настоящими параметрами вопросов банка.

### 3.2. Вакансии (по умолчанию 120)
Роль, грейд, 3–6 обязательных и 2–4 желательных навыка по профилю роли. Вилка по грейду с шумом, формат.

### 3.3. Истинная релевантность
`rel(c, v) = 2`, если все обязательные `t_s ≥ порога уровня` и грейд в диапазоне и вилка совместима. `1`, если не хватает ровно одного обязательного или грейд на ступень рядом. Иначе `0`. Считается только по **настоящим** уровням.

### 3.4. Симулированные работодатели (для подстройки в сессии и 🚀 SASRec)
- Скрытый вектор предпочтений по признакам (например, «любит капитанов»: +0.3 к полезности).
- Модель кликов с позиционным смещением (каскадная): `P(клик) = P(просмотр позиции) × σ(полезность)`.
- Сессия — 20–40 показов, 3–8 действий.
- Метрика: nDCG@10 по истинной полезности после k действий с подстройкой и без неё.

### 3.5. Воспроизводимость
`SEED`, параметры в `tools/synth/config.yaml`. Разбиение на `dev` (настройка весов) и `test` (итоговые цифры) по разным seed'ам. Параметры генератора выводятся на страницу качества.

`make synth SPLIT=dev|test` → `reports/synth/<split>/`: `candidates.jsonl` (у кандидата `truth` — скрытое, только для метрик, и `observed` — то, что видит продукт), `vacancies.jsonl`, `employers.jsonl`, `competitions.jsonl`, `relevance.jsonl` (ненулевые `rel`), `item_bank.json`, `meta.json` (seed, хеш и параметры). Из кода — `generate_market()`, `relevance()`, `simulate_session()` в `tools/synth/synth.py`. Черновик банка лежит в `data/questions/<skill>.yaml` (10 навыков × 15, `status: draft`, второй человек ещё не проверил); синтетика его пока не читает: параметры 3PL генерируются заглушкой по навыкам с `testable: true`.

## 5. Стенд оценки (`tools/eval`)

```
tools/eval/
├── bench_llm.py            # Д0: скорость и качество моделей на 5–15 резюме
├── run.py                  # make eval → все раннеры → отчёт
├── runners/
│   ├── resume.py           # F1 навыков, придуманные навыки, ошибка стажа, валидность JSON
│   ├── skills_graph.py     # точность/полнота слияний, F1 «навык ли это», модерация
│   ├── code_dna.py         # точность/полнота технологий, распознавание подделок
│   ├── query.py            # полный разбор запроса, точность по каждому фильтру
│   ├── trust.py            # синтетика: AUC «приукрашенный vs настоящий навык», калибровка точек
│   ├── grade.py            # точность роли и грейда (±1), стабильность при перефразировании
│   ├── matching.py         # P@5, nDCG@10, «идеальный в топ-10», доля приукрашенных в топ-10; BM25 / эмбеддинги / наш / абляции
│   ├── reciprocal.py       # калибровка p_accept на демо-истории офферов
│   ├── session.py          # симулированные работодатели: nDCG@10 после k действий
│   ├── adaptive_test.py    # корреляция θ с настоящим уровнем, длина против фиксированного теста
│   ├── interview.py        # AUC автор/посторонний (по прогонам команды)
│   └── fairness.py         # impact ratio по группам, правило 4/5
└── report.py               # markdown + JSON → reports/ и POST /admin/quality/runs
```

**Состояние (E27-2):** реализованы `run.py`, `report.py`, `bm25.py` и `runners/matching.py`; `make eval [SPLIT=test]` (полный рынок, ~15 с) и `make eval-quick` (200 кандидатов) пишут `reports/eval/eval.{md,json}`. Потребность = вакансия синтетики, истина — `rel` по `truth`. Методы: BM25 по резюме, BM25 с фильтрами грейда и зарплаты, наш подбор (`score_candidate` из core на уверенностях из упрощённой модели доказательств: резюме 0.25, GitHub без подделок, тест, ФСП) и абляции без GitHub/тестов/ФСП. Метрики: precision@10, nDCG@10, доля приукрашенных в топ-10, Δ nDCG от ФСП, попадание роли в категории `needs.recommend`. Остальные раннеры из дерева выше — в своих задачах.

**Разбор резюме hh.ru (E39-19).** `runners/resumes.py` входит в `make eval` / `make eval-quick`: 10 обезличенных резюме в раскладке выгрузки hh.ru (5 PDF, 5 DOCX, вымышленные люди, адреса `example.test`) в `data/eval/resumes/hh/` с эталоном `gold.json`; набор воспроизводит `uv run python tools/eval/gen_hh_resumes.py`. Правиловая ветка ml (без LLM) разбирает файлы; засчитывается совпадение ФИО, телефона, почты, города, начала «Обо мне», у каждой записи опыта — компании, должности, начала и конца, у образования — вуза, года, специальности, а также каждого навыка из эталона. Полнота = засчитано / всего, цель ≥ 0.8 (до правок E39-19 было 0.67, опыт и образование читались на треть), точность навыков — справочно. Отчёт — раздел «Разбор резюме hh.ru» в `reports/eval/eval.{md,json}`; тест `services/ml/tests/test_resume_hh.py`.

**Настройка весов (E36-6):** `uv run python tools/eval/tune.py --out reports/eval-tune` подбирает `matching_weights`, множитель обязательного навыка и `strength.rank_match` по сетке на рынке `dev` (train) и проверяет на `test` (holdout) в режимах match (выдача по вакансии) и rank (выбрана категория); веса принимаются, только если на holdout растут и P@10, и nDCG@10 в обоих режимах. Прогон 2026-10-07: улучшения на holdout нет (разница в пределах шума), веса не менялись — [отчёт](../reports/matching-weights-2026-10-07.md). Ручной разметки потребностей (`relevance`, §2) пока нет — настройка только на синтетике.

### 5.1. Целевые значения

| Механика | Метрика | Цель | Базовое решение |
|---|---|---|---|
| Разбор резюме | F1 навыков · придуманные · ошибка стажа | ≥ 0.85 · ≤ 2% · ≤ 6 мес | regex по словарю |
| Граф навыков | precision / recall слияний · F1 «навык ли это» · полнота модерации | ≥ 0.95 / ≥ 0.8 · ≥ 0.85 · ≥ 0.98 | только rapidfuzz |
| ДНК кода | точность / полнота технологий · подделки | ≥ 0.9 / ≥ 0.8 · ≥ 90% | только языки GitHub API |
| Разбор запроса | все фильтры верны · каждый фильтр | ≥ 70% · ≥ 90% | только правила |
| Доверие | AUC приукрашенный vs настоящий | ≥ 0.8 | ≈ 0.5 (резюме как есть) |
| Категория и грейд | роль (топ-1 / топ-2) · грейд (точно / ±1) · стабильность | ≥ 85% / 95% · ≥ 60% / 90% · ≥ 90% | — |
| Подбор | P@5 · идеальный в топ-10 · **доля приукрашенных в топ-10** | ≥ 0.7 · ≥ 90% · **намного ниже базового** | BM25 по резюме |
| Вклад ФСП | Δ nDCG@10 «полная модель − без ФСП» | главная цифра для заказчика | — |
| Подстройка в сессии | nDCG@10 после 5 действий против без подстройки | рост | без подстройки |
| Адаптивный тест | корреляция θ · длина | высокая · ~в 2 раза короче | фиксированный тест |
| Справедливость | impact ratio всех групп | ≥ 0.8 | — |

### 5.2. Фраза для питча (шаблон)
«На синтетическом рынке из 1000 кандидатов, где каждый четвёртый приукрашивает резюме, поиск по ключевым словам ставит в топ-10 **X%** приукрашенных, наш подбор — **Y%**. Данные ФСП дают **+Z п.п.** nDCG@10. Разбор резюме: F1 **0.8x** на 40 реальных резюме. Живые прогоны: SUS **7x**, оффер за **N** минут.»
