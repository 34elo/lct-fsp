# ML и алгоритмы

> ⚠️ **Концепция v2 (рабочая, 2026-10-05):** грейд и категорию определяет тест (Rasch + SPRT вместо 3PL), а сигналы ниже уходят в силу профиля. См. [solution.md §3](../solution.md#3-тестирование), ADR-018, ADR-020. Ниже описана текущая реализация.

> Принцип: **LLM извлекает и формулирует, формулы решают.** Всё, что влияет на доверие, грейд и ранжирование, считается детерминированно по конфигу `data/scoring.yaml` (в рантайме — `scoring_config`). Поэтому каждое решение объяснимо и воспроизводимо, а метрики честно сравниваются с базовым решением.
> Все числа ниже — **стартовые значения**. Калибруем на эталонных наборах ([§11](#11-оценка-качества)).

## 1. Модели и железо

### 1.1. Железо
Домашний сервер: Ryzen 5 4650G (6C/12T, Zen 2, встроенная Vega 7), 32 ГБ ОЗУ, **Radeon RX 5700 XT 8 ГБ (RDNA1, gfx1010)**. Доступ снаружи через VPS. Облака, скорее всего, не будет.

**Следствия:**
- ROCm официально не поддерживает gfx1010 (`HSA_OVERRIDE_GFX_VERSION` иногда помогает, но это лотерея). **Основной путь — llama.cpp с бэкендом Vulkan** (Mesa RADV). Он стабилен на RDNA1, и ROCm не нужен.
- 8 ГБ VRAM → модели 7–8B в 4-битной квантизации (Q4_K_M ≈ 4.5–5 ГБ) + KV-кеш. Две модели на GPU одновременно не держим, эмбеддинги считаем на CPU.
- Одна GPU — **два слота llama-server**: слот 1 для синхронного ml-api, слот 2 для очереди RabbitMQ `ml.llm` с приоритетами и `prefetch=1`. Плюс кеширование всего, что можно ([messaging.md](messaging.md)).

### 1.2. Выбор моделей

**Сейчас работает (2026-10-02):** на ПК запущен `llama-server` с **Qwen3-VL-4B-Instruct Q4_K_M** + `mmproj` (vision), контекст 16k, 2 слота, flash attention, KV-кеш q8_0, alias `qwen3-vl-4b`.
- Сервер **общий с другим проектом команды**: доступ по ключу через хостовый порт 18090 (снаружи — `llm.patissons.tech`). Нашу GPU-дисциплину (приоритеты `ml.llm`) соблюдаем, но чужие запросы тоже занимают слоты — учитывать при замерах.
- **Плюс vision-модели:** сканы PDF и фото резюме разбираем не через tesseract, а напрямую — страница как картинка в Qwen3-VL. Это и есть OCR.
- **4B меньше планировавшихся 7–8B:** быстрее, но может проигрывать в качестве извлечения. В Д1 замер на эталоне (E0-4). Если F1 навыков < 0.8 — переходим на 7–8B текстовую модель в отдельном слоте или с переключением.

**Решение по ответам организаторов (ADR-025):** ждут российские модели (трансграничная передача ПДн), GPU на стенде жюри нет. Модель по умолчанию — открытая российская (кандидаты — YandexGPT-5-Lite, GigaChat-20B-A3B, T-lite; лицензия и запуск в llama.cpp проверяются), на CPU для стенда жюри и на GPU для нашего. Выбор замером — E32-3, имя — `LLM_MODEL`. В документации сдачи: какая модель, как запущена, для чего (разбор резюме, черновики ключей и объяснений). Qwen3-VL-4B — наш текущий стенд разработки.

**Уточнение по ответам в чате (ADR-027):** облачные LLM допустимы, в том числе зарубежные; предпочтительны открытые модели адекватного размера; риски 152-ФЗ — на команде. Поэтому российская модель — предпочтение, а не требование: в замере E32-3 участвуют и нероссийские открытые модели (Qwen), побеждает лучшая по критериям §1.3а. Облачный провайдер подключается сменой `LLM_BASE_URL`, но на нашем стенде и стенде жюри не используется — разбор резюме передавал бы ПДн наружу (риски — [security.md §4](security.md#4-персональные-данные-и-согласия)).

Исходный план выбора (оставляем как запасной):

| Задача | Кандидаты | Как запускаем |
|---|---|---|
| Чат / извлечение / генерация | **Qwen3-8B** (без режима размышлений), **Qwen2.5-7B-Instruct**, **T-lite** (русскоязычный дообученный Qwen) — все в Q4_K_M GGUF | `llama-server -m model.gguf -ngl 99 -c 16384 --parallel 2 -fa --cache-type-k q8_0 --cache-type-v q8_0` (Vulkan) |
| Быстрый резерв | Qwen2.5-3B-Instruct / Gemma-3-4B Q4 | тот же сервер или на CPU, если GPU недоступна |
| Эмбеддинги | **bge-m3** или **USER-bge-m3** (1024d) | sentence-transformers / ONNX на CPU внутри ml-api |
| Распознавание речи (🚀) | whisper.cpp small/medium | CPU |

**Бюджет VRAM (8 ГБ):** веса 7–8B Q4_K_M ≈ 4.7–5.0 ГБ; KV-кеш 16k токенов (2 слота × 8k, q8_0) ≈ 1.0–1.2 ГБ; рабочие буферы ≈ 0.5 ГБ. Итого ≈ 6.5 ГБ, запас есть.

**Протокол замера в Д0** (`tools/eval/bench_llm.py`):
1. Скорость: токенов/с на prefill и генерации, время разбора 5 эталонных резюме.
2. Качество: F1 навыков и доля «придуманных» навыков на 15 размеченных резюме, валидность JSON (при ограниченной генерации должна быть 100%).
3. Берём лучшую по качеству модель, у которой разбор p95 ≤ 25 с. Ожидаемая скорость на 5700 XT (Vulkan, 7B Q4) — порядка 35–55 токенов/с на генерации и сотни токенов/с на prefill. Цифры **подтвердить замером**.

### 1.3. Клиент LLM
- OpenAI-совместимый клиент (httpx) с профилями `LLM_PROFILE=gpu|cpu`: `base_url`, `model`, `max_tokens`, таймауты.
- **Структурированный вывод:** `response_format: {type: "json_schema", json_schema: <pydantic.model_json_schema()>}`. llama-server превращает схему в грамматику, поэтому JSON всегда валиден. Затем pydantic-валидация и бизнес-проверки. Если проверки упали, один повтор с сообщением об ошибке, после него `failed`.
- Температура 0–0.2 для извлечения, 0.5–0.7 для генерации вопросов.
- **Промпты** лежат в `services/ml/prompts/<task>/v<N>.j2`, версия попадает в `parser_version` / `analyzer_version` и в ключи кешей. Изменение промпта означает новую версию.
- У Qwen3 режим размышлений выключен (`enable_thinking=false` в шаблоне или `/no_think`), иначе латентность вырастет в разы.
- **Реализация:** `services/ml/fsp_ml/llm.py` — `OpenAiLlm` (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_TIMEOUT`, `LLM_MAX_TOKENS`; `chat_template_kwargs.enable_thinking=false`). Ошибки — машинные коды `llm_timeout`, `llm_unavailable`, `llm_invalid`. Профиль `LLM_PROFILE=cpu` пока не реализован. В тестах клиент подменяется фейком с записанными ответами.

### 1.3а. Выбор LLM (E32-3, ADR-031)

**Статус: ждёт замера.** Стенд жюри без GPU (ADR-025 п.8); облако организаторы разрешили, но ПДн из резюме мы наружу не отдаём (ADR-027 п.4), поэтому нужна открытая модель, которая работает локально в llama.cpp на CPU (~8 ядер) и на нашей GPU. Выбор делается замером на задачах проекта, не по отзывам.

**Критерии (по убыванию важности):**
1. **Лицензия** допускает использование и показ жюри; веса можно положить на стенд. Проверяет человек по карточке модели на день замера.
2. **Запуск в llama.cpp:** есть GGUF (или конвертация официальным скриптом), поддержан chat-шаблон и `response_format: json_schema` (грамматика).
3. **Качество:** F1 навыков с проверенной цитатой ≥ 0.85, доля «придуманных» ≤ 2 % ([§2](#2-разбор-резюме-mlparse_resume)), валидность по схеме 100 % с грамматикой, ключи заданий и объяснения проходят проверки набора.
4. **Скорость на CPU:** разбор резюме p95 ≤ 25 с на ~8 ядрах Q4; на GPU быстрее.
5. **Память:** влезает в профили `standard` (≈ 4 ГБ на всё) и `full` ([deployment.md](deployment.md) §профили).
6. **Русский язык** — естественный, без смешения языков в объяснениях.

**Кандидаты.** Названия — направления поиска, а не утверждение, что такие веса есть и подходят. Точные репозитории, версии, размеры, квантизации и лицензии выбирает и проверяет человек.

| Кандидат | Роль в замере | Что проверить человеку |
|---|---|---|
| Открытые веса YandexGPT (линейка «Lite») | российская, основной кандидат | наличие GGUF, лицензия, размер |
| Открытые веса GigaChat (в т. ч. MoE-варианты) | российская, основной кандидат | поддержка архитектуры в llama.cpp, лицензия |
| T-lite (Т-Банк) | российская, дообучен на русском | лицензия, версия, GGUF |
| Saiga | российская, дообучена на русском | на какой базе, лицензия базы |
| Vikhr | российская, дообучена на русском | на какой базе, лицензия базы |
| Qwen (базовая линия, текущий стенд — Qwen3-VL-4B) | не российская, точка отсчёта и запас | сравнение; после ADR-027 может стать моделью по умолчанию, если выиграет замер |

**Как мерить.** Сервер поднимает человек (модели не скачиваются из репозитория и не запускаются скриптами); дальше для каждой модели:

```
# llama-server -m <модель.gguf> --alias <имя> ... (человек); адрес и ключ — в .env
LLM_MODEL=<имя> make eval-llm ARGS="--repeats 5 --server-pid <pid llama-server> --vram-file /sys/class/drm/card0/device/mem_info_vram_used"
LLM_MODEL=<имя> make eval-llm ARGS="--no-grammar"   # валидность JSON без грамматики (запасной путь)
```

Команда `make eval-llm` — `tools/eval_llm`: три набора (разбор 3 вымышленных резюме с разметкой навыков и «ловушками»; черновики ключей для 3 заданий; объяснения ошибок для 2 заданий), отчёт `reports/llm/<модель>.{md,json}`. При `ML_FAKE=true`, без `LLM_BASE_URL` или при недоступном сервере выходит с кодом 2 и пояснением. Наборы маленькие: это отбор кандидатов, а не итоговая метрика; для итога набор расширяют эталоном из [§11.1](#111-наборы-datagold-пдн--вне-git). Запустить на CPU: тот же сервер, `-ngl 0`, `--threads 8`, отдельный прогон. Для замера «тихой» машины остановить чужие запросы к общему серверу.

### 1.4. Заглушки `ML_FAKE=true`

`services/ml` (пакет `fsp_ml`) при `ML_FAKE=true` отвечает фикстурами по контрактам `fsp_contracts.ml`, без GPU и сети: ml-api (`/v1/query/parse`, `/v1/embeddings` на 1024 измерения, `/v1/skills/resolve`, `/healthz`) и оба воркера (`python -m fsp_ml.worker llm|code`) для всех команд `ml.*`. Ответ детерминирован входом, `message_id` результата выводится из `message_id` команды, поэтому повторная доставка безвредна. Сценарии ошибок для фронта: `object_key` с суффиксом `.scanned` → `ml.resume.failed` (`scanned_pdf`), `github_login=not-found` → `ml.code.failed`. `ml.resume.parse` в фейк-режиме отвечает `ml.resume.failed` (`llm_unavailable`) — выдуманный разбор не показываем; фикстуру `parsed_resume.json` отдаёт только `object_key` с суффиксом `.fixture` (тесты). `/v1/embeddings`: если задан `EMBEDDING_MODEL_PATH` (каталог bge-m3) и установлен `sentence-transformers`, считает bge-m3 на CPU, иначе при `ML_FAKE=true` фейк; не более 128 текстов за запрос (422 `too_many_texts`). `/v1/skills/resolve` — быстрый путь по снимку графа из core (`GET /internal/taxonomy/snapshot`, `CORE_URL`, `SERVICE_TOKEN_ML`; перечитывается при новой `taxonomy_version`): нормализация (регистр, ё, версии) → точный поиск по синонимам → нечёткий (rapidfuzz ≥ 92, строки короче 4 символов не ищем, неоднозначное совпадение не склеиваем). Остальное (модерация, судья, новые вершины) — заглушка до E16-4. Лемматизация (pymorphy3) и эмбеддинги в быстром пути пока не используются. `/v1/query/parse` (AU-2, `fsp_ml/query_parse.py`) в любом профиле отвечает 200: база — правиловый разбор (чипы `source=rule`), при `ML_FAKE=false` и доступном LLM он дополняет только пустые поля (`source=llm`), сбой LLM возвращает правила. Остальные пути при `ML_FAKE=false` без моделей отвечают 503 `ml_unavailable`. ml-worker-llm при `ML_FAKE=false` требует `LLM_BASE_URL`: `ml.resume.parse` разбирает через LLM ([§2](#2-разбор-резюме-mlparse_resume)), остальные команды до своих задач отвечают фикстурами с предупреждением `ml_fake_fallback` в логе. Фикстуры — `services/ml/fixtures/`.

## 2. Разбор резюме (`ml.parse_resume`)

```
файл → текст → правила → LLM (JSON-схема) → проверка цитат → нормализация → ParsedResume
```

1. **Текст:** PDF через PyMuPDF (`page.get_text("text")`, с сохранением порядка блоков), DOCX через python-docx (параграфы и таблицы). Если текста меньше 200 символов (скан) и есть tesseract (`rus+eng`), пробуем OCR, иначе `failed: scanned_pdf`.
2. **Правила (без LLM):** email, телефон, Telegram, ссылки (GitHub/GitLab/LinkedIn/Habr), даты периодов работы (regex для «янв 2021 – н.в.», «2019–2022», «03.2020 — 05.2023»).
3. **LLM:** одна генерация с JSON-схемой `ParsedResume` (опыт, образование, навыки). **Для каждого навыка модель обязана вернуть `quote`** — дословный фрагмент из текста.
4. **Проверка цитат (защита от галлюцинаций):** `quote` ищем в тексте (нормализация пробелов и регистра, `rapidfuzz.partial_ratio ≥ 90`). Навык без подтверждённой цитаты отбрасываем и пишем в `warnings`. Доля отброшенных — метрика «придумывает навыки».
5. **Сопоставление с графом навыков** (`POST /v1/skills/resolve`, конвейер [skills.md §3](skills.md#3-конвейер-для-нового-упоминания)): нормализация → точный поиск по синонимам → нечёткий поиск → модерация (цензурность, «навык ли это») → судья (то же / уже / шире / связано / другое). Неизвестный, но корректный навык становится новой вершиной со статусом `provisional` и слабым доверием. Софт-навыки из резюме сохраняются как «указано в резюме» и в расчётах не участвуют ([skills.md §8](skills.md#8-софт-навыки-командные-сигналы-и-коэффициент)).
6. **Стаж:** сумма непересекающихся интервалов коммерческого опыта (стажировки считаем с коэффициентом 0.5).

**Без LLM (`LLM_ENABLED=false`, `resume-rules-v2`, E30-4).** Шаг 3 заменяет `extract_rules`: навыки — по словарю графа (цитата — строка резюме), разделы — по заголовкам («Опыт», «Образование», «О себе»…), записи опыта — абзацы с периодом (компания и должность по словам-должностям и «ООО/АО/«…»»), образование — вуз, степень, специальность, год, город — по метке или «г. …». Локальный NER Natasha (`resume_ner.py`, модели в пакете, ≈ 200 МБ RAM, без сети) — запасной путь для имени, города и компании; без пакета правила работают сами. Нераспознанное остаётся пустым. Шаги 4–6 те же. Цель: F1 навыков ≥ 0.6 (тест `tests/test_resume_nlp.py`).

**Выгрузка hh.ru (E39-19).** Правила узнают раскладку hh.ru: заголовок «Опыт работы — 5 лет 3 месяца» (длительность в заголовке), «Желаемая должность и зарплата», «Знание языков», «Повышение квалификации», «Резюме обновлено» относятся к своим разделам, а «Проживает: город» задаёт город. Опыт: период в начале строки («Август 2021 — настоящее время») и следом строка длительности («5 лет 2 месяца») открывают запись; дальше компания, «город, сайт» (пропускается), должность и «Обязанности: …»; левая и правая колонки PDF, склеенные в одну строку, и таблица DOCX читаются одинаково (DOCX обходится в порядке документа, ячейка из нескольких абзацев даёт отдельные строки). Образование: уровень («Высшее образование», «Бакалавр», «Магистр», «Среднее специальное»), год отдельной строкой, «Вуз, город», факультет, специальность. Лигатуры PDF («Airﬂow») приводятся к буквам. Результат попадает в черновик вкладки «Данные» профиля (E39-15). Метрика — полнота полей на `data/eval/resumes/hh/` (см. [evaluation.md §5](evaluation.md#5-стенд-оценки-toolseval)), цель ≥ 0.8.
7. **Сила доказательств из резюме:** базовая 0.30. Если навык упомянут в описании опыта длительностью ≥ 12 мес — 0.40. Навыки из блока «Навыки» без привязки к опыту — 0.25. Правки кандидата → `source=self`, 0.15.

**Метрики:** F1 навыков ≥ 0.85, доля придуманных ≤ 2%, ошибка стажа ≤ 6 мес, правок вручную ≤ 2 поля.

**Реализация (E3-3, `services/ml/fsp_ml/resume_*.py`, промпт `prompts/parse_resume/v2.j2`):**
- Формат файла определяется по сигнатуре (`%PDF-`, zip с `word/document.xml`), заявленный `mime` не используется. Битый или чужой файл → `bad_file`. OCR пока не подключён: скан (< 200 символов текста) сразу `scanned_pdf`. Текст длиннее 12 000 символов обрезается (`warnings: text_truncated`).
- Контакты и ссылки берутся только из правил, ответ LLM для них не используется. Имя из ответа LLM сохраняется, только если найдено в тексте. Даты периодов из ответа LLM приводятся правилами к `YYYY-MM`; «н.в.» → `end=null`, год без месяца в конце периода → декабрь.
- Ответ LLM проверяется внутренней pydantic-схемой `LlmResume` (навык = `name` + `quote`). Невалидный ответ — один повтор с текстом ошибок, затем `llm_invalid`.
- Проверка цитат (шаг 4) дополнена: навык должен быть упомянут в своей цитате (по названию или синониму из графа, целыми словами; нечётко — `fuzz.ratio ≥ 80` по окнам слов, для названий ≤ 3 символов только точное слово). Так «Java» с цитатой про JavaScript отбрасывается. E44-2: если цитата найдена, но названия в ней нет, название (и синонимы) ищется целыми словами в окне ±2 строки/предложения вокруг цитаты, затем во всём тексте, и найденная строка становится цитатой; нет названия в тексте — навык отбрасывается как раньше. Отброшенные навыки — в `warnings` как `quote_not_found:<навык>` / `skill_not_in_quote:<навык>`.
- Сопоставление (шаг 5) — пока только быстрый путь `TaxonomyIndex` (нормализация → синонимы → rapidfuzz ≥ 92, снимок графа из core). Не найденные навыки с подтверждённой цитатой — в `unknown_skills`; модерация, судья и новые вершины — E16-4. Без снимка графа все навыки уходят в `unknown_skills` (`warnings: taxonomy_unavailable`). В `experience[].skills` попадают только навыки с подтверждённой цитатой.
- **Заявленное (E20-5):** схема `LlmResume` дополнена `soft_skills` (имя + цитата), `declared_grade` (грейд + цитата) и `roles` (роль из `RoleSlug` + цитата); в `ParsedResume` это `soft_skills`, `declared_grade`, `declared_roles` (необязательные, совместимо). Значение остаётся, только если цитата найдена в тексте и заявленное читается в самой цитате (софт-навык — по названию; грейд и роль — по маркерам вроде «Middle», «бэкенд»); иначе отбрасывается с `warnings: soft_dropped:` / `grade_dropped:` / `role_dropped:`. Это «указано в резюме»: доверия нет, категорию, грейд и подбор не меняет, считает их тест. В правиловой ветке (`LLM_ENABLED=false`) поля пустые.
- **Запасной путь (E43-8):** если после проверки цитат от LLM осталось 0 навыков или меньше 3 при тексте длиннее 1000 знаков, к результату добавляются навыки правилового `extract_rules` (те же проверки цитат, навык упомянут в цитате). Такие навыки помечены `ResumeSkill.source = "rules"` (по умолчанию `"llm"`), в `warnings` — `llm_fallback_rules:<n>`; опыт, образование и контакты остаются от LLM. Лог `resume_parsed` (без ПДн): `prompt_version`, `chars`, `llm_skills`, `skills`, `dropped`, `dropped_share`, `experience`, `education`, `fallback_rules`, `seconds`; нулевой ответ LLM — отдельная запись `resume_llm_empty_skills`. Сравнение вариантов вызова — `tools/eval/resume_llm_variants.py`, отчёт — [reports/resume-llm-2026-10.md](../reports/resume-llm-2026-10.md).
- Стаж (шаг 6) считается так же, как в core (`resumes.service.experience_months`): конец периода не включается; стажировка определяется по должности («стажёр», «intern», «практикант»). Силу доказательств (шаг 7) считает core при подтверждении.
- `parser_version` = `resume-v2:<LLM_MODEL>`. Прогресс — `job.progress` в `ui.user.<candidate_id>` (`job_id = resume_id`, этапы `text` 10 → `llm` 30 → `verify` 85 → `done` 100). Ошибки → `ml.resume.failed` с кодом: `bad_file`, `scanned_pdf`, `file_unavailable`, `llm_timeout`, `llm_unavailable`, `llm_invalid`.
- Ручной прогон на модели: `uv run --package fsp-ml python -m fsp_ml.resume_parser <файл> [data/taxonomy/skills.yaml]`. Кеш `c:resume:{sha256}:{parser_v}` ([messaging.md](messaging.md)) пока не реализован. Качество и время на эталоне ещё не замерены.

## 3. Доверие к навыкам

### 3.1. Сила доказательства по источнику

| Источник | Формула силы `s` (0…1) | Затухание (полураспад) |
|---|---|---|
| `self` | 0.15 | нет |
| `resume` | 0.25 / 0.30 / 0.40 (см. §2.7) | нет |
| `github` | `0.6 × authorship × maturity × volume × (0.5 если есть флаг подозрительности)`. `authorship` — доля собственных изменений в технологии; `maturity` ∈ [0.6, 1]; `volume` = `min(1, loc_authored / 2000)^0.5` | 2 года от последнего коммита |
| `test` | `clip(0.45 + 0.12·θ, 0.30, 0.75)` — потолок 0.75 ниже порога уровня 4 (0.8): **один тест — не выше ●●●○**, ●●●● только со вторым независимым источником (ФСП, задание работодателя, повторный тест не раньше чем через 30 дней; E41-5) | 1.5 года. Минимальная версия идеи «срок действия»: результат **действует 12 месяцев** («действует до …» в профиле), потом доказательство деактивируется. Пересдача — через 30 дней (в `DEMO_MODE` без ограничения) |
| `ai_interview` | `0.45 + 0.10 · avg_score(0…3)` → 0.45…0.75 | 1.5 года |
| `fsp` | `min(0.95, w_rule × k_level × k_result × k_stage)` (см. §3.2) | 3 года от даты соревнования |
| `codeforces` | по рейтингу: <1200 → 0.35, 1200–1599 → 0.5, 1600–1899 → 0.65, ≥ 1900 → 0.8 (только для `algorithms`, `data_structures`, `cpp`/`python`) | 2 года |

Затухание: `s_eff = s · 0.5^(age_years / half_life)`.
Неверифицированная привязка ФСП: × 0.5.
Навык со статусом `provisional` (новая вершина графа): сила любого доказательства ограничена 0.25, пока навык не станет `active` ([skills.md §3.4](skills.md#34-жизненный-цикл-вершины)).
Софт-навыки точек доверия не получают: вместо них командные сигналы ([skills.md §8](skills.md#8-софт-навыки-командные-сигналы-и-коэффициент)).

### 3.2. Достижение ФСП → навыки

`strength = min(0.95, w_rule × k_level × k_result × k_stage)`

| Коэффициент | Значения |
|---|---|
| `w_rule` | вес навыка в правиле «дисциплина (+трек) → навык», 0…1 ([fsp.md §5](fsp.md#5-правила-дисциплина--навыки)) |
| `k_level` | региональное 0.60 · межрегиональное 0.75 · всероссийское 0.90 · международное 1.00 |
| `k_result` | 1–3 место 1.00 · топ-10% 0.90 · топ-25% 0.80 · топ-50% 0.70 · участие 0.55. Процентиль = `place / participants_total` |
| `k_stage` | финал 1.00 · отборочный этап 0.85 |

Дополнительно:
- `team_role = captain` → событие лидерства для командного сигнала `L` ([skills.md §8.2](skills.md#82-формулы-сигналов)), а не точки доверия у софт-навыка;
- разряд — не доказательство навыка, а сигнал грейда (§5).

Примеры: призёр всероссийского финала по алгоритмическому (`algorithms`, w=1.0): 1.0 × 0.9 × 1.0 × 1.0 = **0.90 → ●●●●**. Участник регионального этапа: 1.0 × 0.6 × 0.55 = **0.33 → ●○○○**.

### 3.3. Объединение доказательств

1. Внутри одного типа источника берём **максимум** `s_eff` (десять резюме не дают высокого доверия).
2. Между типами — **noisy-OR** (независимые подтверждения усиливают друг друга):
   `confidence = 1 − Π_t (1 − s_t)`
3. Уровень:

| confidence | Уровень | Значок |
|---|---|---|
| < 0.20 | 0 | ○○○○ (показываем как «заявлено») |
| 0.20–0.39 | 1 | ●○○○ |
| 0.40–0.59 | 2 | ●●○○ |
| 0.60–0.79 | 3 | ●●●○ |
| ≥ 0.80 | 4 | ●●●● |

Проверка на соответствие продуктовой таблице: только резюме (0.30) → ●○○○ ✓; только GitHub (0.5) → ●●○○ ✓; GitHub + резюме → 1 − 0.5·0.7 = 0.65 → ●●●○ ✓ (подтверждения усиливают); тест 0.65 → ●●●○ ✓; ФСП 0.90 → ●●●● ✓.

`claimed_only = sources ⊆ {self, resume}` — на фронте такие навыки выглядят иначе.

## 4. Категория (роль × грейд × стек × формат)

- В справочнике у каждой роли есть веса навыков `role_skills` (например, backend: `sql` 0.8, `postgresql` 0.7, `python|go|java|kotlin|csharp` по 0.7, `fastapi|django|spring|nestjs` по 0.6, `docker` 0.5, `rest` 0.6, `redis` 0.4, `kafka|rabbitmq` 0.4, `system_design` 0.5…).
- `role_score(r) = Σ_s w_rs · conf_s / Σ_{top-k} w_rs`, где k = 8: нормируем на 8 самых весомых навыков роли, чтобы длинный список навыков не давал преимущества.
- Роли с `score ≥ 0.6 · max` становятся метками; вес метки — её доля среди выбранных (сумма 1). Роль `fullstack` по своим весам не считается: она появляется только по правилу «backend и frontend оба ≥ 0.5 и разница < 0.15», её score = среднее двух, и тогда она основная (`primary_role`), а backend и frontend остаются метками. Пороги — секция `category` в `data/scoring.yaml`. Ниже `min_score = 0.05` категория не определена (`primary_role = null`).
- `primary_stack` — топ-3 по `confidence` среди навыков основной роли, которые являются языком (`group = language`) или фреймворком (прямой потомок языка в иерархии: `fastapi → python`).
- **Объяснение категории:** топ-5 навыков основной роли по вкладу `w · conf`, с уровнями и источниками. Не хранится: считается по `candidate_skills` (`graph/category.py: load_category`).
- **Где считается:** `recompute_profile` (E4-2) после сборки навыков пишет `candidates.primary_role/roles/primary_stack`; смена основной роли попадает в `diff.category` события `skills.profile.updated`.
- **Стабильность** (метрика ≥ 90%): то же резюме, переписанное другими словами, должно давать ту же основную роль. Проверяем на парах из эталонного набора.

## 5. Грейд

Сумма сигналов → пороги. Каждый сигнал попадает в `grade_breakdown` с доказательствами.

| Сигнал | Баллы |
|---|---|
| Коммерческий стаж | 0 мес → 0 · < 12 → 1 · 12–35 → 3 · 36–59 → 5 · 60–95 → 7 · ≥ 96 → 8 |
| Лучшее достижение ФСП | всероссийский/международный призёр +3 · всероссийский финал +2 · межрегиональный призёр +1.5 · региональный призёр +1 · участие +0.5 |
| Разряд ФСП | юношеские +0.5 · III–I +1 · КМС +2.5 · МС и выше +3.5 |
| Тесты | максимальный θ по навыкам основной роли: < 0 → 0 · 0–1 → +1 · 1–2 → +2 · > 2 → +3 |
| Зрелость кода (ДНК) | 0…2 (тесты, CI, документация, история) |
| ИИ-интервью | средняя оценка ≥ 2 → +1 |
| Командный сигнал «лидерство» `L` (0…1, [skills.md §8](skills.md#8-софт-навыки-командные-сигналы-и-коэффициент)) | +1.5 · L |
| Сложность опыта (LLM-оценка описаний, опционально) | 0…1.5 |

| Баллы | Грейд |
|---|---|
| < 2 | Intern |
| 2–3.9 | Junior |
| 4–5.9 | Junior+ |
| 6–8.4 | Middle |
| 8.5–10.4 | Middle+ |
| 10.5–12.9 | Senior |
| ≥ 13 и `L ≥ 0.5` (или подтверждённый опыт руководства) | Lead |

Ограничения:
- без коммерческого опыта — максимум Middle (олимпиадник-КМС, призёр всероссийского финала: 3 + 2.5 + тесты 2 = 7.5 → Middle);
- `grade_confidence` = доля непустых групп сигналов (стаж, ФСП, тесты, код). Если < 0.5 → «предварительно» + подсказка, что подключить;
- `next_grade.points_needed` и `hints` («пройди тест по Python: до +2», «подключи GitHub: до +2») питают навигатор.

Реализация (`graph/grade.py`, `recompute_profile` после категории; параметры — `grade_signals`, `grade_thresholds`, `lead_requirements` в `data/scoring.yaml`):
- **Откуда сигналы.** Стаж — `candidates.experience_months` (заполняет модуль опыта). Остальное — из активных `evidence` по `details`: ФСП (`source=fsp`, `fact_type=fsp_result`): `{level: regional|interregional|national|international, place, final|stage}`, берётся лучшее достижение; разряд — `fact_type=fsp_rank`: `{rank: youth_1…msic}`; тест (`source=test`): `{theta}`, максимум по навыкам основной роли; ДНК (`source=github`): `{code_maturity: 0…1}` → баллы `2 · maturity`; ИИ-интервью: `{avg_score}`. Лидерство `L` и `management_confirmed` — `candidates.team_signals`: `L` и остальные сигналы пересчитывает `recompute` из фактов (`app/graph/team_signals.py`, формулы — [skills.md §8.2](skills.md#82-формулы-сигналов)); `management_confirmed` пересчёт сохраняет. Факты для сигналов: `fsp_result.details` — `team_role`, `team_size`, `participants`, `teammates` (непрозрачные id напарников, в профиль не пишутся); `code_repo.details` (`source=github`) — `maintainer`, `external_authors_merged`, `active_authors`. Неверифицированные результаты ФСП в сигналах не участвуют. «Сложность опыта» пока не считается (0).
- **Разбивка.** `grade_breakdown` — список `{signal, value, points, evidence_ids}` по присутствующим сигналам (стаж пишется всегда), плюс строки без баллов `constraint_no_commercial_cap` (грейд обрезан до Middle) и `constraint_lead_requires_leadership` (баллов на Lead хватало, но нет `L ≥ 0.5`).
- **Уверенность.** Группы: стаж, ФСП, тесты (тест или интервью), код. `grade_confidence` = доля непустых групп; `< 0.5` — «предварительно».
- **`next_grade`.** Хранится в `candidates.grade_next` как `{grade, points_needed, hints[{signal, max_gain, text}]}`, подсказки по убыванию возможного прироста; у Lead `null`.
- Смена грейда попадает в `diff.grade` события `skills.profile.updated`.

## 6. Матчинг вакансия ↔ кандидат

### 6.1. Жёсткие фильтры (SQL)
- `search_status ≠ dnd`, не удалён, компания не в стоп-листе кандидата;
- `formats ∩ vacancy.formats ≠ ∅`;
- `salary_min ≤ salary_to × 1.10` (до +10% пропускаем с пометкой ⚠);
- грейд в `[grade_min − 1, grade_max + 1]`;
- обязательные навыки: для каждого `level(s) ≥ min_level` **или** смежный навык даёт `conf(a) × adj(s,a) ≥ порог уровня` (такие кандидаты пропускаются с ⚠ «есть смежное»). Если не выполнены два и больше обязательных навыка, кандидат отсекается.

### 6.2. Скоринг

```
base  = 0.45·skills + 0.20·semantic + 0.15·grade + 0.10·salary + 0.10·fsp
score = min(1, base · K_soft · 1.03 [если «активно ищу»])
K_soft = 1 + min(β(v), Σ_k α_k(v) · s_k)        командные сигналы L, T, R, G (skills.md §8.3), β ≤ 0.12
```

| Компонента | Формула |
|---|---|
| `skills` | `Σ_s W_s · min(1, eff_conf_s / target(min_level_s)) / Σ W_s`, где `W = 2·weight` для обязательных и `1·weight` для желательных; `eff_conf_s = max(conf_s, max_a conf_a · adj(s,a))`; `target` = нижняя граница уровня (2 → 0.4, 3 → 0.6) |
| `semantic` | `clip((cos(emb_vac, emb_cand) − 0.30) / 0.55, 0, 1)` |
| `grade` | 1 — внутри диапазона, 0.5 — на ступень рядом, 0 — иначе |
| `salary` | 1, если `salary_min ≤ mid(вилки)`; линейно до 0 при `salary_min = salary_to`; 0, если выше |
| `fsp` | максимум силы ФСП-доказательств по навыкам вакансии |
| `K_soft` | коэффициент командных сигналов (лидерство, командная работа, результативность, рост) с весами по грейду вакансии и потолком β; только повышает ([skills.md §8.3](skills.md#83-коэффициент-в-подборе)) |

Реализация (E7-1): `services/core/app/matching/scoring.py` (формулы, веса из `matching_weights`, `hard_filters`, `grade_fit_scoring`, `skills_coverage` в `scoring.yaml`), `services/core/app/matching/service.py` (отбор и сборка данных через `service.py` модулей vacancies, taxonomy, graph, candidates). Уточнения: `K_soft` берётся по `grade_max` вакансии; кандидат без грейда фильтр по грейду проходит, `grade = 0`; `semantic = 0`, пока у вакансии нет вектора (колонка `vacancies.embedding` ещё не добавлена).

### 6.3. Объяснение
- Каждая компонента порождает кандидатов в `ExplanationItem` с вкладом (`weight`) и `evidence_ids`.
- Показываем топ-3 плюса и топ-3 минуса/предупреждения по модулю вклада.
- Пункты об опыте кандидата (`skill_confirmed`, `skill_adjacent`, `skill_claimed_only`, `fsp_achievement`, `grade_fit`, `grade_mismatch`, `team_signal`) ссылаются на его доказательства: навык — `candidate_skills.top_evidence` (для смежного — доказательства смежного навыка), ФСП — лучшее доказательство с затуханием, грейд — `evidence_ids` из `grade_breakdown`, командный сигнал — доказательства его фактов. Пункт без доказательства не показывается (в скоре вклад остаётся). Пункты об анкете (`salary_fit`, `salary_below_min`, `active_search`) и `semantic_only`, а также `skill_missing` без частичного или смежного подтверждения идут без `evidence_ids`.
- Текст строится по **шаблонам** (детерминированно, мгновенно): «FastAPI, PostgreSQL — подтверждено кодом (●●●○) и тестом», «Нет подтверждения Kafka (есть смежное: RabbitMQ ●●○○)».
- 🚀 Для топ-5 по вакансии `ml.explain_matches` пишет связный абзац. В промпт передаём **только** структурированные факты и пункты объяснения, без ПДн. Каждое утверждение абзаца должно ссылаться на пункт из списка, проверяем постобработкой.

### 6.4. Поиск без вакансии
Те же формулы. Фильтры из чипсов играют роль «виртуальной вакансии»: роли, грейд, навыки, формат, бюджет. `semantic` считается по `semantic_text`.

### 6.5. Подсказка по зарплате
- `below_candidate_min = salary_to < candidate.salary_min`;
- `vs_category_median = salary_to / median(salary_min в ячейке role×grade) − 1`;
- `p_accept` — вероятность принятия из взаимного подбора ([matching.md §4.1](matching.md#41-взаимный-подбор-интерес-кандидата)): `< 0.35` — низкая, `0.35–0.65` — средняя, `> 0.65` — высокая;
- `range_too_wide = salary_to / salary_from > 1.6` → предупреждение «Слишком широкая вилка: кандидаты не поймут реальную сумму» (норма директивы ЕС о прозрачности оплаты). То же правило — при публикации вакансии.

## 7. Поиск обычным текстом

1. **Правиловый парсер (мгновенный):** словарь синонимов навыков и ролей (Aho-Corasick по алиасам), грейды («мидл», «сеньор», «джун+»), форматы («удалёнка», «гибрид», «офис»), деньги («до 220 тыс», «200-250к», «от 150 000»), города. Выход — `SearchFilters` с `source=rule`.
2. **LLM (`/v1/query/parse`):** JSON-схема `SearchFilters` + `semantic_text`. В промпт передаём список ролей и грейдов, а навыки — только в нормализованной форме справочника (top-200 алиасов не нужны, нормализуем после).
3. **Слияние:** числа (зарплата) и форматы берём из правил, если они есть. Роли, навыки и смысловую часть берём из LLM после нормализации через справочник. Конфликты показываем чипсом со знаком `?`.
4. **Метрика:** все фильтры верны ≥ 70% запросов, каждый фильтр по отдельности ≥ 90% (эталон — 30–50 запросов).

## 8. Адаптивный тест

- **Модель:** 3PL IRT с фиксированными `a = 1.0` (или экспертным) и `c = 0.25` (угадывание при 4 вариантах). `b` задаётся экспертно по шкале 1–5: `b = (d − 3) × 1.0`.
  `P(верно | θ) = c + (1 − c) / (1 + e^{−a(θ − b)})`
- **Оценка θ:** EAP на сетке θ ∈ [−3, 3] с шагом 0.1, априорное N(0, 1). SE — апостериорное стандартное отклонение.
- **Выбор вопроса:** максимум информации Фишера в θ̂ среди неиспользованных. Плюс ограничение экспозиции: из топ-3 по информации выбираем случайно.
- **Остановка:** ≥ 5 вопросов и SE < 0.45, или 8 вопросов.
- **Банк:** ~10 навыков × 15–20 вопросов (python, javascript, sql, algorithms, data_structures, git, docker, linux, networks, react). Черновик: `data/questions/<skill>.yaml` (`id`, `d` 1–5, `text`, `code?`, `options` ×4, `correct` A–D, `explanation`; `status: draft`, `source: llm_draft`). Вопросы пишет команда. LLM (`ml.generate_questions`) только предлагает черновики, каждый проверяет человек (`status=draft → approved`).
- **Метрики на синтетике:** корреляция θ̂ с настоящим уровнем; адаптивный тест примерно в 2 раза короче фиксированного при той же точности (симуляция в `tools/eval`).

## 9. ДНК кода (`ml.analyze_code`)

1. **Метаданные (все репозитории):** GitHub REST `GET /users/{login}/repos?per_page=100&type=owner` + `GET /repos/{r}/languages`. Условные запросы по ETag, токен из `GITHUB_TOKEN`.
2. **Выбор для глубокого анализа (до 8):** не форк (или форк с собственными коммитами), размер < 200 МБ, приоритет: свежесть × звёзды × размер × доля основных языков.
3. **Клон:** `git clone --filter=blob:none --no-tags --single-branch` в tmpfs, `GIT_LFS_SKIP_SMUDGE=1`, без сабмодулей, таймаут 60 с, лимит 300 МБ. Затем checkout HEAD.
4. **Авторство:** `git log --author=<login|emails из API> --numstat --no-merges` → строки, добавленные кандидатом, по файлам. `own_commit_share` — доля его коммитов.
5. **Языки:** по расширениям и эвристикам с vendor-исключениями (`node_modules`, `vendor`, `dist`, `build`, `*.min.js`, сгенерированные файлы, lock-файлы). Доли считаем **по авторским строкам**.
6. **Технологии:** парсеры манифестов (`package.json`, `requirements*.txt`, `pyproject.toml`, `Pipfile`, `go.mod`, `pom.xml`, `build.gradle(.kts)`, `Cargo.toml`, `composer.json`, `Gemfile`, `*.csproj`) → пакеты → навыки по `data/taxonomy/package_map.yaml` (`fastapi → fastapi`, `@nestjs/core → nestjs`, `spring-boot-starter-web → spring`…). Инфраструктурные файлы: `Dockerfile`, `docker-compose*.yml`, `.github/workflows/*`, `.gitlab-ci.yml`, `k8s/*.yaml`/Helm, `*.tf`, `ansible/`.
7. **Зрелость (0…1):** наличие тестов (доля тестовых файлов), CI, README > 500 символов, линтер или форматтер в конфиге, осмысленные сообщения коммитов (средняя длина > 15 символов, не «fix», «upd»), равномерность истории.
8. **Признаки подозрительности (`flags`):**
   - `fork_no_changes` — форк без собственных коммитов;
   - `giant_commit` — один коммит содержит > 70% авторских строк репозитория при общем объёме > 3000 строк;
   - `overnight` — вся история уложилась в < 24 ч при объёме > 2000 строк;
   - `author_mismatch` — большинство коммитов от email, не связанного с аккаунтом;
   - `template_like` — > 80% файлов совпадают по хешам с известными шаблонами (create-react-app, cookiecutter и т. п., список хешей в `data/code/templates.json`).
   Флаги снижают силу GitHub-доказательств (× 0.5), но не блокируют кандидата.
9. **Радар (6 осей, 0…1):** backend, frontend, devops, data, quality (= зрелость), open_source (принятые PR в чужие репозитории через Search API `type:pr author:{login} is:merged -user:{login}`, 🚀).
10. 🚀 **Характеристика:** LLM получает агрегаты и 3–5 фрагментов кода и пишет 2–3 предложения о стиле и сильных сторонах.

**Метрики:** точность и полнота технологий ≥ 0.9 / ≥ 0.8; подставные распознаны ≥ 90%; честные ошибочно помечены ≤ 10% (эталон — 20–30 репозиториев, из них 5–10 подставных).

## 10. ИИ-интервью по коду

1. Выбор фрагментов: из глубоко разобранного репозитория с `own_commit_share ≥ 0.5` берём 3 функции или блока по 15–80 строк, написанных кандидатом (по `git blame` на выбранных файлах). Предпочитаем нетривиальные: ветвления, работу с БД или сетью, асинхронность.
2. Генерация (JSON-схема): `{question, rubric: [3–5 тезисов, которые должен упомянуть автор], difficulty}` на каждый фрагмент. Вопросы про «почему так», а не «что делает строка».
3. Ответ: текст (🚀 голос → whisper.cpp), 3 минуты, время фиксируется.
4. Оценка (JSON-схема): `{score: 0..3, matched_rubric: [i], rationale}`. Температура 0, промпт с примерами оценок.
5. Результат → `evidence(source=ai_interview)` по технологиям репозитория + `authorship_confirmed` повышает `authorship` для GitHub-доказательств этого репозитория до 1.0.
6. **Метрика:** AUC отличия автора от постороннего ≥ 0.8. Протокол: члены команды отвечают по своему и чужому репозиторию, в отчёте честно указываем число попыток. Плюс согласованность оценок ИИ с оценками людей.

### 10.1. Вопросы для структурированного интервью

Для работодателя: по кнопке «Вопросы для интервью» в карточке кандидата под выбранную вакансию. Структурированное интервью — самый валидный метод отбора (r = 0.42, Sackett и др., 2022).

1. **Вход** (без ПДн): требования вакансии, навыки кандидата с уровнями и источниками, пробелы (обязательные навыки с уровнем ниже требуемого, навыки «только заявлено», смежные вместо требуемых), командные сигналы.
2. **Генерация** (команда `ml.interview_kit.generate`, приоритет 5, JSON-схема): 5–7 вопросов. Каждый привязан к навыку или пробелу, у каждого рубрика «слабый / хороший / сильный ответ» и 1–2 уточняющих вопроса. Минимум 2 вопроса — на подтверждение сильных сторон, остальные — на пробелы.
3. **Ограничения:** только профессиональные вопросы. Никаких вопросов о возрасте, семье, здоровье. Постпроверка по стоп-словам.
4. **Выход:** экран и печатная версия (PDF через бэкенд), кеш по `(vacancy_version, profile_version)`.

## 11. Оценка качества

### 11.1. Наборы (`data/gold/`, ПДн — вне git)
Эталонные резюме (30–50, разметка двумя людьми), репозитории (20–30, из них 5–10 подставных), запросы работодателя (30–50), релевантность (15–20 вакансий × топ-20 разных методов ≈ 300–500 пар).

### 11.2. Синтетический рынок (`tools/synth`)
- **Генератор устроен иначе, чем скоринг** (правило честности): скрытые «настоящие» уровни навыков генерируются из латентных факторов (роль, талант, опыт) через собственную модель, а не через наши формулы.
- Наблюдаемые сигналы с искажениями: резюме (20–30% кандидатов приписывают несуществующие навыки), ФСП (сильно коррелирует с настоящим уровнем), GitHub (у части, среди них подставные), тесты (шумные ответы по настоящему уровню через IRT).
- Истинная релевантность пары считается по настоящему профилю.
- Разделение на dev/test: веса подбираем на dev, итоговые цифры считаем на test.

### 11.3. Сравниваемые методы
1. **Базовое решение:** BM25 по тексту резюме (rank-bm25).
2. BM25 + эмбеддинги.
3. Наш подбор целиком.
4. Абляции: без ФСП, без GitHub, без тестов.

Метрики: Precision@5, Recall@10 «есть идеальный в топ-10», nDCG@10, **доля приукрашенных резюме в топ-10** (главная наглядная цифра), AUC «приукрашенный навык vs настоящий» для доверия, калибровка значков (доля действительно имеющихся навыков по корзинам уровня).

### 11.4. Воспроизводимость
`make eval` → `tools/eval/run.py` (фиксированные seed'ы) → `reports/eval-<date>.md` + JSON → `POST /admin/quality/runs` (таблица `eval_runs`) → страница качества в админке.
