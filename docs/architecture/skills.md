# Навыки: ядро, растущий граф, софт-сигналы

> ⚠️ **Концепция v2 (рабочая, 2026-10-05):** у навыка появляются тип (фундамент, хард, мышление, бизнес, софт, опыт) и карточка; роли становятся профилями профессий. См. ADR-019 и [solution.md §2](../solution.md#2-решение-в-пяти-идеях).

> Как появляются и связываются вершины-навыки, как отсекается мусор и склеиваются синонимы, и как учитываются софт-навыки. Опирается на [graph.md](graph.md). Практика больших платформ и нормы — [../notes/research.md](../notes/research.md).
> Решения (ADR-016, ADR-017): **ядро + рост**; новые навыки сразу участвуют в подборе со **слабым доверием**; софт-навыки **без точек доверия**, только как **командные сигналы из фактов** с ограниченным коэффициентом.

## 1. Зачем навыки как вершины

Навык — **адрес, к которому крепятся доказательства**. Без отдельных вершин не получится:
- повесить силу и дату («ФСП подтверждает алгоритмы, 0.9»);
- задать требование «FastAPI не ниже ●●●»;
- объяснить совпадение путём в графе;
- посчитать uplift «+64% вакансий»;
- построить карту рынка.

Эмбеддинг профиля один на человека и не знает, что из сказанного доказано. Он дополняет граф, но не заменяет его.

## 2. Ядро и рост

| | Ядро (на старте) | Рост (во время работы) |
|---|---|---|
| Объём | 150–250 навыков, синонимы, роли, правила ФСП | неограниченно |
| Откуда | Теги Stack Overflow с их синонимами (`js` = `javascript`), карта пакетов из манифестов (`package_map`), русские названия и сленг, правила дисциплин от экспертов ФСП | Упоминания в резюме, вакансиях, манифестах репозиториев, запросах HR |
| Статус | `active` | `provisional` → `active` / `merged` / `rejected` |
| Кто проверяет | Команда (ревью YAML) | Конвейер + очередь админа ФСП для спорных решений |

Зачем вообще ядро:
- правила «дисциплина → навыки» и банк вопросов ссылаются на конкретные вершины;
- редактору вакансий нужны подсказки с первого дня;
- без якорей первые пользователи назовут навыки кто во что горазд.

LinkedIn делает так же: таксономисты + ML поверх ядра, 39 тыс. навыков и 374 тыс. синонимов выросли из базы.

## 3. Конвейер для нового упоминания

```
сырое упоминание («Postgres 15», «коммуникабельный», «FastAPI-Users», «ху…»)
   │
1. нормализация ─────────► 2. точный поиск по синонимам (Aho-Corasick) ── нашли ──► навык
   │                                  │ нет
   │                       3. нечёткий поиск (rapidfuzz ≥ 92) ── нашли ──► навык + новый синоним
   │                                  │ нет
   │                       4. модерация: цензурно? навык ли это? ── нет ──► отклонено / стоп-лист
   │                                  │ да
   │                       5. сопоставление: 10 ближайших по эмбеддингу → судья
   │                                  │
   │            то же ─► синоним    уже/шире ─► новая вершина + «часть»
   │            связано ─► новая вершина + «смежен»    другое ─► новая вершина
   │                                  │
   └──────────────────────► 6. вершина provisional → active (поддержка или админ)
```

### 3.1. Нормализация
Нижний регистр, ё → е, срезать версии и мусорные символы («Python 3.11» → «python», «C++17» → «c++»). Лемматизация русских слов (pymorphy3): «коммуникабельность» → «коммуникабельный». Варианты транслитерации («джава», «постгрес»).

### 3.2. Модерация
1. **Цензурность:** словарь мата и оскорблений + маленький русский классификатор токсичности (класса `rubert-tiny-toxicity`, CPU). Отклонённое попадает в `skill_blocklist` и больше не проверяется.
2. **ПДн и инъекции:** телефоны, email, ссылки, фразы-инструкции («игнорируй…») → отклонение без записи текста в справочник.
3. **«Навык ли это»:** логистическая регрессия поверх эмбеддингов bge-m3, 4 класса:
   - `hard` — технология, метод, инструмент;
   - `soft` — личное или командное качество;
   - `domain` — предметная область: финтех, медтех;
   - `not_skill` — должность, компания, город, оценочное слово («красивый»), мусор.
   
   Обучается на ядре (позитивы) и сгенерированных негативах: должности, компании, города, частотные прилагательные. В серой зоне (уверенность 0.4–0.7) решает локальная LLM с ответом по JSON-схеме.

### 3.3. Сопоставление с существующими (если поиск не нашёл)
1. **Кандидаты:** 10 ближайших вершин по эмбеддингу «название + синонимы + описание».
2. **Судья:** reranker `bge-reranker-v2-m3` даёт оценку пары. Если оценка выше 0.3, локальная Qwen по JSON-схеме классифицирует отношение:

```json
{"relation": "same | narrower | broader | related | different", "confidence": 0.0, "reason": "…"}
```

3. **Решение:**

| Отношение | Уверенность | Действие |
|---|---|---|
| `same` | ≥ 0.9 и косинус ≥ 0.88 | Новый синоним существующего навыка (автоматически) |
| `same` | 0.6–0.9 | Временная вершина + предложение слияния в очереди админа |
| `narrower` / `broader` | ≥ 0.7 | Новая вершина + ребро «часть» (вес 0.6 по умолчанию) |
| `related` | ≥ 0.7 | Новая вершина + ребро «смежен» (вес = оценка reranker × 0.8) |
| `different` / низкая уверенность | — | Новая вершина без связей (связи нарастут по совместной встречаемости, §5) |

4. **Ловушки:** Java ≠ JavaScript, C ≠ C++ ≠ C#, React ≠ React Native, Go ≠ «go», Spring ⊂ Spring Boot, 1С ≠ «1 с». Таблица `skill_distinct` (пары, которые точно разные) проверяется **до** судьи, её пополняет админ. Автослияние запрещено, если хотя бы одна сторона в паре `distinct`.
5. **Кеш решений** навсегда: `(norm_a, skill_id_b) → решение` в таблице `skill_mentions`. Повторное упоминание стоит один поиск.

### 3.4. Жизненный цикл вершины

| Статус | Как попасть | Участие в подборе | В интерфейсе |
|---|---|---|---|
| `provisional` | Создана конвейером | Да, но доверие как у заявленного: максимум сила 0.25, даже если доказательство сильнее, пока навык не станет `active`. Поиск только по точному совпадению | Пометка «новый навык» |
| `active` | Встретилась у ≥ 5 разных кандидатов, либо подтвердил админ | Полное | Обычный навык |
| `merged` | Слита в другую (`merged_into`) | Доказательства перенесены | Скрыта, остаётся синонимом |
| `rejected` | Админ отклонил | Нет | Скрыта |

## 4. Где это работает

| Компонент | Роль |
|---|---|
| **ml-api** `POST /v1/skills/resolve` | Синхронно для пачки до 50 упоминаний: нормализация → поиск → модерация → судья. Вызывается из разбора резюме, редактора вакансий и разбора запроса HR |
| **ml-worker-llm**, команда `ml.skills.resolve` (приоритет 3) | Массовый разбор: seed, переразбор после смены модели |
| **core, модуль `taxonomy`** | Владеет вершинами: применяет решения (создать, синоним, связь, слияние), держит граф навыков в памяти, публикует `taxonomy.updated` |
| **core-scheduler → `core.jobs`** | Ночные задачи роста связей (§5) и продвижение `provisional → active` |
| **Админка** | Очередь спорных решений, слияние и разделение, «точно разные», стоп-лист, статистика роста графа |

## 5. Как нарастают связи

Ночная задача `skills.relations.refresh`:

1. **Совместная встречаемость → «смежен».** Для пар навыков в профилях (уровень ≥ 2) и в требованиях вакансий считаем NPMI:
   `npmi(a,b) = log(p(a,b) / (p(a)·p(b))) / −log p(a,b)`.
   При `npmi ≥ 0.3` и поддержке ≥ 5 создаём или обновляем ребро `adjacent` с `source=cooccurrence`, `weight = 0.4 + 0.5·npmi` (максимум 0.9). Рёбра от судьи и админа не перезаписываются, а усредняются с весом источника.
2. **Веса ролей из данных.** `lift(s, r) = p(s | r) / p(s)` по ролям кандидатов и вакансий. Для нового навыка с поддержкой ≥ 5 создаём `role_skills` с весом `min(0.8, 0.2·log2(lift))`, `source=data`. Веса ядра правит только админ.
3. **Подсказки экспертам ФСП.** Для дисциплины `d` и навыка `s`: если у участников `d` навык встречается с `lift ≥ 2` и поддержкой ≥ 10, предлагаем добавить в правило («у участников ИБ часто встречается Wireshark»). Решает эксперт, автоматически не применяется.
4. **Продвижение** `provisional → active`: поддержка ≥ 5 разных кандидатов или решение админа.

После задачи — `taxonomy.updated {changed_skill_ids}` → пересчёт затронутых профилей.

## 6. Слияние задним числом

1. Админ или судья решил, что B — то же, что A → `B.status = merged`, `B.merged_into = A`, синонимы B переходят к A.
2. Доказательства B перепривязываются к A (`UPDATE evidence SET skill_id = A WHERE skill_id = B`). Дубли по уникальному ключу схлопываются: остаётся сильнейшее.
3. `vacancy_skills` перепривязываются так же.
4. `taxonomy.updated` → пересчёт затронутых кандидатов и подборок.

Разделение (ошибочное слияние) — обратная операция по журналу `skill_merges`.

|---|---|---|
| Сопоставление | Точность и полнота слияния на ~200 размеченных парах (рус/англ синонимы, сокращения, ловушки Java/JavaScript, C/C#) | precision ≥ 0.95, recall ≥ 0.8 |

## 8. Софт-навыки: командные сигналы и коэффициент

### 8.1. Принцип
- Софт-навыки **не получают точек доверия**. «Общительный» и «стрессоустойчивый» в резюме ничего не доказывают: это заявления, их видно как текст, но в расчётах они не участвуют.
- Вместо этого — **4 командных сигнала**, которые считаются **только из проверяемых фактов**. Они сопоставлены с моделью компетенций Great Eight:

| Сигнал | Кластер Great Eight | Из каких фактов |
|---|---|---|
| **Лидерство** `L` | Руководство и решения | Капитан команды на соревновании ФСП; мейнтейнер репозитория, принимающий чужие PR |
| **Командная работа** `T` | Поддержка и сотрудничество | Участие в командных соревнованиях; разные напарники; совместные репозитории |
| **Результативность** `R` | Достижение целей | Доля выступлений, доведённых до финала или топ-25% |
| **Рост** `G` | Обучение и исследование | Устойчивое улучшение результатов от сезона к сезону |

- **Нельзя:** выводить качества из голоса, мимики или «тональности» текста. Это совпадает с запретом распознавания эмоций на рабочем месте в EU AI Act — ориентир хорошей практики.
- Сигналы **только повышают** скор кандидата, отсутствие сигнала ничего не снижает. Вклад ограничен сверху (§8.3).

### 8.2. Формулы сигналов

Затухание как у ФСП-доказательств: `d(age) = 0.5^(age_years / 3)`. `k_level`, `k_result` — коэффициенты уровня соревнования и места из [ml.md §3.2](ml.md#32-достижение-фсп--навыки).

**Лидерство** — noisy-OR по событиям лидерства:

```
L = 1 − Π_i (1 − ℓ_i)

капитан на соревновании i:   ℓ_i = 0.5 · k_level · max(0.6, k_result) · k_size · d(age)
                              k_size = min(1, (n − 1) / 4)        n — размер команды: 2 → 0.25, 3 → 0.5, 5+ → 1
мейнтейнер репозитория:      ℓ = 0.3 · min(1, внешних_авторов_с_принятыми_PR / 10)
```

Пример: капитан команды из 5 человек, 2 место на всероссийском финале в прошлом году: `0.5 · 0.9 · 1.0 · 1.0 · 0.79 ≈ 0.36`. Ещё раз капитан на региональном этапе (команда из 4, топ-25%, этот год): `0.5 · 0.6 · 0.8 · 0.75 · 1.0 = 0.18`. Итого `L = 1 − 0.64·0.82 ≈ 0.47`.

**Командная работа** — noisy-OR по командным выступлениям + бонус за разнообразие напарников:

```
T = 1 − Π_j (1 − τ_j) · (1 − b)
τ_j = 0.25 · k_level · d(age)                      каждое командное соревнование
b   = 0.05 · min(4, уникальных_напарников − 1)     до 0.15; совместный репозиторий с ≥ 2 активными авторами даёт +0.05 к b
```

**Результативность** — байесовское среднее, чтобы «1 из 1» не давало 100%:

```
R = (успехи + 1) / (попытки + 3)                    успех = финал, или призовое место, или топ-25%
считается при попытках ≥ 2, иначе сигнала нет
```

**Рост** — наклон процентиля результата по сезонам:

```
p_t = 1 − место / участников                        процентиль в выступлении t
slope = МНК-наклон p_t по годам (минимум 3 выступления в ≥ 2 сезонах)
G = clip(0.5 + 2·slope, 0, 1), учитывается только при G ≥ 0.6
```

### 8.3. Коэффициент в подборе

```
K_soft(c, v) = 1 + min( β(v), Σ_k α_k(v) · s_k(c) )        k ∈ {L, T, R, G}
score_итог   = min(1, score · K_soft)
```

**Веса `α_k` по грейду вакансии** (в `scoring_config`):

| Грейд вакансии | α_L | α_T | α_R | α_G | Потолок β |
|---|---|---|---|---|---|
| Intern / Junior | 0.01 | 0.03 | 0.02 | 0.03 | 0.06 |
| Middle | 0.02 | 0.03 | 0.02 | 0.02 | 0.06 |
| Senior | 0.04 | 0.03 | 0.02 | 0.01 | 0.08 |
| Lead | 0.08 | 0.03 | 0.02 | 0.01 | 0.12 |

**Работодатель может отметить важные качества** в вакансии («нужен лидер», «командная работа»). Соответствующий `α_k` удваивается, потолок β растёт на 0.02.

Пример: вакансия Middle, кандидат с `L = 0.47`, `T = 0.6`, `R = 0.6`, `G` нет → `0.02·0.47 + 0.03·0.6 + 0.02·0.6 ≈ 0.039` → `K_soft = 1.039`. Скор 0.85 становится 0.88. Командные сигналы различают близких кандидатов, но не перекрывают навыки.

Реализация: `app/graph/team_signals.py` (`compute_team_signals`, `k_soft`); параметры — `team_signal_formulas`, `team_signal_weights`, `employer_emphasis` в `scoring.yaml`. Уточнения: бонус `b` в `T` ограничен 0.15 вместе с бонусом за совместный репозиторий; наклон `G` считается по календарным годам; потолок β с акцентом работодателя не выше 0.12 (§8.6).

### 8.4. Грейд
- В сумме сигналов грейда пункт «капитан +0.5» заменяется на **`+1.5 · L`**.
- Грейд **Lead** требует `L ≥ 0.5` или подтверждённого опыта руководства командой. Сейчас это только заявление из резюме, поэтому показывается как «заявлено».

### 8.5. Как это видно
- **Кандидат и работодатель** видят блок «Командные сигналы» без точек, словами и с фактами:
  - «**Лидерство** — сильное подтверждение: капитан на 2 соревнованиях (Кубок России 2025, финал, 2 место)»;
  - пороги: `≥ 0.6` — «сильное подтверждение», `0.3–0.6` — «есть подтверждение», `< 0.3` — не показываем.
- **В объяснении совпадения** отдельная строка: «✓ Лидерство: капитан команды-призёра всероссийского финала (+2%)».
- **Заявленные софт-навыки** из резюме видны серым списком «Указано в резюме» и в расчётах не участвуют.

### 8.6. Справедливость
Сигналы есть в основном у участников ФСП, поэтому:
- потолок β не больше 0.12;
- на странице качества считаем impact ratio для группы «без ФСП» в топ-10 (правило четырёх пятых);
- если отношение падает ниже 0.8 на синтетическом рынке, уменьшаем α.
