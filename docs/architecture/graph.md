# Граф доказательств

> Центральная модель продукта. Профиль кандидата — это не список навыков, а граф: кто человек, какие с ним были **проверяемые факты** и **какие навыки эти факты подтверждают и с какой силой**. Категория, грейд, процент совпадения, объяснения, рекомендации и навигатор вычисляются из графа.
> Формулы весов — в [ml.md](ml.md), рекомендации и uplift — в [matching.md](matching.md), как появляются и связываются вершины-навыки и как считаются софт-сигналы — в [skills.md](skills.md).

## 1. Зачем граф и зачем рядом эмбеддинги

| | Граф | Эмбеддинг |
|---|---|---|
| Вопрос | «Что **доказано** и чем?» | «О чём этот человек **по смыслу**?» |
| Хранит | Точные факты с весами и датами | Вектор 1024 чисел (bge-m3) по тексту профиля |
| Силён в | Доверии, жёстких требованиях, смежности, объяснениях | Синонимах, контексте, словах вне справочника («highload», «финтех») |
| Слаб в | Свободном тексте | Не знает про доверие: «Python» из выдуманного резюме и Python с призовым местом ФСП для него одинаковы. Не умеет объяснять |

**Граф — источник правды, эмбеддинг считается из графа и используется как один из признаков ранжирования.** Текст для эмбеддинга собирается из подтверждённых навыков (уровень ≥ 2) и описаний опыта, поэтому выдуманные навыки на смысловой поиск почти не влияют.

Что даёт мышление графом:
1. **Происхождение:** у любого утверждения есть путь до проверяемого факта («не резюме, а доказательства»).
2. **Расширяемость:** новый источник (Codeforces, хакатон партнёра) — это новый тип факта и его рёбра к навыкам. Подбор, объяснения и UI не меняются.
3. **Рассуждение через связи:** смежность и иерархия навыков, команды, путь к соревнованию в навигаторе.

## 3. Рёбра

| Ребро | Откуда → куда | Атрибуты | Кто создаёт | Хранение |
|---|---|---|---|---|
| имеет факт | Кандидат → Факт | — | импорт | `candidate_id` в таблице факта |
| **подтверждает** | Факт → Навык | **сила 0–1, дата**, верифицировано | правила при импорте | `evidence` |
| **владеет** | Кандидат → Навык | **доверие, уровень 0–4**, источники, `derived` | пересчёт (агрегат «подтверждает» + наследование) | `candidate_skills` |
| смежен | Навык ↔ Навык | вес (FastAPI ~ Django 0.6), источник (ядро / судья / совместная встречаемость / админ) | справочник + рост графа | `skill_relations` (`kind=adjacent`, хранится в обе стороны) |
| часть | Навык → родитель | коэффициент наследования (FastAPI → Python 0.6) | справочник | `skill_relations` (`kind=parent`) |
| важен для | Навык → Роль | вес | справочник | `role_skills` |
| относится к роли | Кандидат → Роль | вес (категория) | пересчёт | `candidates.roles` |
| командный сигнал | Кандидат → лидерство / командная работа / результативность / рост | значение 0–1, факты-основания | пересчёт ([skills.md §8](skills.md#8-софт-навыки-командные-сигналы-и-коэффициент)) | `candidates.team_signals` |
| на соревновании | Результат ФСП → Соревнование | этап, место | импорт ФСП | `fsp_results.competition_id` |
| дисциплина | Соревнование → Дисциплина | — | импорт ФСП | `fsp_competitions.discipline` |
| правило | Дисциплина → Навык | вес, трек | эксперты ФСП | `discipline_skill_rules` |
| в команде | Кандидат → Команда | роль (капитан) | импорт ФСП | `fsp_team_members` |
| соавтор | Кандидат → Репозиторий (чужой) | доля коммитов | анализ GitHub | `repo_contributors` |
| связан с | Кандидат ↔ Кандидат | тип (`fsp_team`, `repo`), контекст, сила | вычисляется | `candidate_links` (материализованное представление) |
| открыла | Компания → Вакансия | — | работодатель | `vacancies.company_id` |
| **требует** | Вакансия → Навык | **обязательный, мин. уровень, вес** | работодатель | `vacancy_skills` |
| оффер | Вакансия → Оффер → Кандидат | статус, вилка | работодатель | `offers` |
| показан / открыт / отклонён | Компания → Кандидат | время, позиция, вакансия, сессия | система | `impressions`, `rec_feedback`, `profile_views` |

```
Компания ──открыла──► Вакансия ──требует (обяз., мин. ●●●)──┐
                                                             ▼
Кандидат ──имеет факт──► Факт ──подтверждает (0.9)──► Навык ◄──смежен (0.6)──► Навык
   │  │                    │                            ▲  │
   │  │                    └──на──► Соревнование ──►    │  └──часть (0.6)──► Навык-родитель
   │  │                             Дисциплина ──правило─┘
   │  └────────── владеет (0.65, ●●●○) ─────────────────┘
   └──в команде (капитан)──► Команда ◄──в команде── другой Кандидат
```

Центр — треугольник **Кандидат → Факт → Навык**. «Владеет» — сжатая сумма всех путей «Кандидат → Факт → Навык», посчитанная заранее.

## 4. Как хранится

### 4.1. Типизированные таблицы + единое представление
- У каждого вида вершин и рёбер своя таблица (DDL — [data-model.md](data-model.md)): внешние ключи, ограничения, индексы, простой ORM.
- Универсальную пару `nodes(id, type, props jsonb)` + `edges(src, dst, type, props)` **не используем**: она гибкая, но без целостности и с медленными запросами.
- Для визуализации и выгрузки есть представление **`graph_edges`** — `UNION ALL` всех рёбер в формате `(src_type, src_id, dst_type, dst_id, kind, weight, observed_at)`.

```sql
CREATE VIEW graph_edges AS
SELECT 'candidate' src_type, e.candidate_id src_id, e.fact_type dst_type, e.fact_id dst_id, 'has_fact' kind, NULL::real weight, e.observed_at
  FROM evidence e WHERE e.is_active
UNION ALL
SELECT e.fact_type, e.fact_id, 'skill', e.skill_id, 'confirms', e.strength, e.observed_at FROM evidence e WHERE e.is_active
UNION ALL
SELECT 'candidate', cs.candidate_id, 'skill', cs.skill_id, 'owns', cs.confidence, cs.updated_at::date FROM candidate_skills cs
UNION ALL
SELECT 'skill', r.skill_a, 'skill', r.skill_b, r.kind, r.weight, NULL FROM skill_relations r
UNION ALL
SELECT 'vacancy', vs.vacancy_id, 'skill', vs.skill_id, 'requires', vs.weight, NULL FROM vacancy_skills vs;
-- … команды, соревнования, правила дисциплин
```

### 4.2. Где происходит обход

| Часть графа | Размер | Где обрабатываем |
|---|---|---|
| **Граф навыков**: навыки, смежность, иерархия, веса ролей, правила дисциплин | ~250 узлов, ~1–2 тыс. рёбер, меняется редко | **Целиком в памяти** core (dict/adjacency lists), перечитывается по событию `taxonomy.updated` |
| **Подграф кандидата**: его факты, доказательства, навыки | десятки фактов, ~100 рёбер | Загружается **одним запросом** при пересчёте, агрегация в памяти, результат пишется в проекции |
| **Обратные запросы**: «у кого навык X ≥ уровня», «кто подходит под вакансию» | все кандидаты | **Индексы** по проекциям: `candidate_skills (skill_id, level)`, HNSW по `candidates.embedding` |
| **Связи людей** | пары кандидатов | Материализованное представление `candidate_links`, обновляется после импорта ФСП и анализа кода |
| **Аналитика** (кластеры навыков рынка, «скрытые ниши») | весь граф | Выгрузка `graph_edges` в networkx внутри аналитической задачи |

Поэтому **при чтении граф почти не обходится**. Глубокая работа идёт при записи, а чтение использует готовые проекции плюс максимум один шаг по смежности навыков.

### 4.3. Проекции (что посчитано заранее)

| Проекция | Что внутри | Обновляется |
|---|---|---|
| `candidate_skills` | ребро «владеет»: доверие, уровень, источники, топ-3 доказательства, `derived` | пересчёт профиля |
| `candidates.(grade, roles, primary_stack, has_fsp, verified_skills_cnt)` | категория и грейд с разбивкой | пересчёт профиля |
| `candidates.embedding` + `profile_text` | смысловой слой | пересчёт, только если `sha(profile_text)` изменился |
| `matches` | подборки по открытым вакансиям с объяснениями | пересчёт профиля / публикация вакансии |
| `candidate_links` | связи людей | после импорта ФСП и анализа кода |
| `mv_market_cells` | карта рынка | раз в 2 мин при изменениях |
| снимок карточки (кеш) | готовый JSON анонимной карточки | по `profile_version` |

### 4.4. Целостность и версии
- **Доказательства не удаляются**, а деактивируются (`is_active=false`) — это аудит происхождения.
- Пересчёт пишет `candidate_skills` кандидата **в одной транзакции** (upsert + удаление исчезнувших) и увеличивает `profile_version`.
- Слияние пересчётов без задержек: писатели ставят `candidates.recompute_requested_at = now()` и шлют команду. Обработчик пропускает команду, если `recomputed_at ≥ requested_at`. Пачка из 20 доказательств даёт 1–2 пересчёта, а не 20.
- Правка справочника (смежность, правило дисциплины) → событие `taxonomy.updated` → находим затронутых кандидатов через `evidence.skill_id` / `fact_type` → пересчитываем только их.

### 4.5. Почему не Neo4j и не Apache AGE

| Вариант | Почему нет (сейчас) |
|---|---|
| Neo4j | Вторая база и синхронизация данных. Наши обходы — 1–3 шага, граф навыков помещается в память. Офферы, вакансии и pgvector нужны в тех же транзакциях и запросах |
| Apache AGE (Cypher внутри PostgreSQL) | Риск зрелости, неудобство с ORM и pgvector. Можно упомянуть в питче как путь развития, если понадобятся глубокие обходы |

## 5. Вычисления на графе

### 5.1. Доверие (ребро «владеет»)
1. Для каждого навыка — все рёбра «подтверждает» от фактов кандидата.
2. Сила с затуханием по дате, максимум внутри типа источника, noisy-OR между типами ([ml.md §3](ml.md#3-доверие-к-навыкам)).
3. **Наследование по иерархии:** родитель получает `max(child_conf × coef(child→parent))`, если это выше его собственного доверия. Ребро помечается `derived=true` и показывается как «выведено из FastAPI». Наследуем только вверх, не больше двух уровней. Пример: FastAPI 0.90 → Python ≥ 0.54 (●●○○).

   Реализация: `services/core/app/graph/trust.py::inherit` (чистая функция), коэффициенты — вес связи `parent` (`skill_relations`); граф иерархии держит `SkillGraphCache` (`app/taxonomy/service.py`): сбрасывается обработчиком `taxonomy.updated` и перечитывается, если версия справочника (`scoring_config.taxonomy`) изменилась. `candidate_skills.derived_from` — непосредственный дочерний навык; `sources`, `top_evidence` и `claimed_only` берутся у него.

### 5.2. Категория и грейд
Роли — взвешенное покрытие рёбер «важен для» ребрами «владеет». Грейд — сумма сигналов из фактов: стаж из опыта, лучший результат ФСП, разряд, θ тестов, зрелость кода ([ml.md §4–5](ml.md#4-категория-роль--грейд--стек--формат)).

### 5.3. Обходы для работодателя
Запись в стиле Cypher для наглядности. Реализация — SQL по проекциям ([matching.md](matching.md)).

| Что получает работодатель | Путь |
|---|---|
| **Подборка под вакансию** | `(v)-[:requires]->(s)<-[:owns]-(c)` + `(v)-[:requires]->(s)-[:adjacent]-(s2)<-[:owns]-(c)` + фильтры по атрибутам `c` + косинус векторов |
| **Карточка** | `(c)-[:owns]->(s)` топ-8 → для каждого `(c)-[:has_fact]->(f)-[:confirms]->(s)` топ-3 → `(f:fsp_result)-[:at]->(comp)` → фильтр видимости |
| **Объяснение «почему подходит»** | для каждого требования лучший путь `v → s ← c ← f` или через смежный навык |
| **Похожие кандидаты** | `(c)-[:owns]->(s)<-[:owns]-(c2)` с весом по доверию + косинус |
| **Сыгранная команда** | `(c1)-[:member_of]->(t)<-[:member_of]-(c2)` |
| **Сигнал «выступал с сильными»** | `(c)-[:linked]-(c2)` где `c2` — призёр. Показываем агрегатом без имён |
| **Карта рынка** | `(c)-[:has_role]->(r)` × грейд |
| **Подсказка по вилке** | медиана `salary_min` в ячейке роль × грейд |

### 5.4. Обходы для кандидата
| Что получает кандидат | Путь |
|---|---|
| «Откуда этот навык» | `(s)<-[:confirms]-(f)<-[:has_fact]-(c)` |
| **Uplift: какой навык добавить, чтобы подходить под N% больше вакансий** | спрос `(v)-[:requires]->(s)` по подходящим вакансиям минус `(c)-[:owns]->(s)` → симуляция ребра «владеет s ●●●» → пересчёт числа подходящих вакансий ([matching.md §6](matching.md#6-uplift-для-кандидата-какой-навык-добавить)) |
| Как подтвердить | `(s)<-[:rule]-(d)<-[:discipline]-(comp {status: announced})` + доступный тест по навыку + GitHub |

### 5.5. Антинакрутка через граф
- Один факт (репозиторий, участник ФСП) привязан к двум кандидатам → флаг и модерация.
- Всё доверие навыка из одного факта с флагом подозрительности → понижение.
- Кандидат связан только с кандидатами-«пустышками» (без фактов) → сигнал для модерации (на будущее).

## 6. API подграфа

`GET /candidates/me/graph` (владелец) и `GET /candidates/{pseudo_id}/graph` (работодатель, анонимно). Собирается из проекций, кешируется по `profile_version`.

Параметры: `skills=top|all`, `depth=facts|competitions`, `vacancy_id=` (подсветить пути под требования вакансии).

```json
{
  "profile_version": 12,
  "nodes": [
    {"id": "cand", "type": "candidate", "label": "Backend #4821"},
    {"id": "f:fsp:91", "type": "fsp_result", "label": "Кубок России, финал · 2 из 40 · капитан", "date": "2025-04", "verified": true},
    {"id": "f:repo:7", "type": "repo", "label": "репозиторий · её кода 82%", "date": "2026-08"},
    {"id": "s:fastapi", "type": "skill", "label": "FastAPI", "level": 3, "confidence": 0.65},
    {"id": "s:python", "type": "skill", "label": "Python", "level": 2, "confidence": 0.54, "derived_from": "s:fastapi"},
    {"id": "s:django", "type": "skill", "label": "Django", "level": 0, "ghost": true}
  ],
  "edges": [
    {"from": "cand", "to": "f:fsp:91", "type": "has_fact"},
    {"from": "f:repo:7", "to": "s:fastapi", "type": "confirms", "strength": 0.5, "evidence_id": "…"},
    {"from": "s:fastapi", "to": "s:python", "type": "parent", "weight": 0.6},
    {"from": "s:fastapi", "to": "s:django", "type": "adjacent", "weight": 0.6}
  ],
  "highlight": [{"requirement": "fastapi", "path": ["vac", "s:fastapi", "cand", "f:repo:7"]}]
}
```

Анонимная версия для работодателя: без URL репозиториев (если `visibility.repos=false`), без названий компаний в опыте, без имён в командах (только «команда, 4 участника, 2 на платформе»).

## 7. Связи между людьми и приватность

- Источники связей: **команды ФСП** (`fsp_team_members`) и **общие репозитории** (`repo_contributors`, если соавтор тоже на платформе и привязал GitHub).
- Работодатель видит **агрегат**: «выступала в команде с 2 призёрами ФСП», без псевдонимов.
- Карточка команды (найм сыгранной команды) показывает псевдонимы участников, только если у каждого включено `visibility.teams` (по умолчанию включено, можно выключить).
- Связи не участвуют в жёстких фильтрах и дают максимум +0.03 к скору (сигнал, а не решающий фактор).
