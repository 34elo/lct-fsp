# Фронтенд (web)

> React 19 + Vite + TypeScript, один SPA с ленивыми разделами по ролям. Почему не Next.js — [stack.md §2](stack.md#2-фронт-react-spa-nextjs-или-два-проекта). Визуальная часть — [design/brief.md](../design/brief.md).

## 1. Карта маршрутов

Маршруты приняты из макетов (таблица экран → файл → маршрут — [design/brief.md §0](../design/brief.md#0-дизайн-получен-2026-10-02--с-чего-начинать-фронтенду)).

| `/employer/subscriptions` | E | Подписки на категорию (E33-4): профессия, грейды, формат, бюджет, навыки с уровнем, «только подтверждённые»; список и удаление. Ссылка из «Кандидаты категории» и из «Ваших категорий» в Подборе (в меню пункта нет, E39-25) |

| `/run/:token` | испытатель | Живой прогон + SUS (Q3) |

**Меню (E35-1, E39-25; `NAV` в `app/routes.ts`), второй строки вкладок нет ни у одной роли.** Кандидат: Главная (`/me`) · Тест (`/me/assessment`) · Приглашения (`/me/offers`; фильтр на странице `?show=offers|interests|responses` — приглашения, интересы компаний, свои отклики; `/me/interests` и `/me/responses` переадресуют) · Вакансии (`/jobs`) · Статистика (`/me/stats`) · Профиль (`/me/profile`; «Данные», «Резюме и ФСП», «Регулярные задания» — ссылки внутри профиля; внутри «Обзора» свои вкладки Навыки · ФСП · Резюме · Граф). Работодатель: Подбор (`/employer`; подписки — ссылка в «Ваших категориях», `/employer/subscriptions`) · Шорт-лист · Приглашения (`/employer/offers`; фильтр `?show=responses` — отклики на вакансии, `/employer/responses` переадресует) · Вакансии · Задания · Компания. Бейдж на «Приглашениях» кандидата — приглашения плюс интересы. Нижняя панель на ≤768 px — пять пунктов (у кандидата без «Статистики», у работодателя без «Заданий»: они открываются с Главной и со страницы «Компания»). После входа работодатель попадает на `/employer`. Админ (≤ 6): Дашборд · Допуск заданий · Профессии · Граф навыков · Модерация · Качество. Меню аватара: тема, «Выйти» (красный, `danger`); переключатель темы в шапке; favicon, `manifest.webmanifest` и `<title>` по экрану (`app/DocumentTitle.tsx`, из `routes.ts`); настройки и согласия — с экраном E36-4. Пункт подсвечивается по самому длинному префиксу пути (`activeNav`, доп. префиксы — `match`). **Сетка (E39-4):** каркас `PageContainer` — максимум 1440 без полей; страница берёт ширину из `PAGE` (`shared/lib/page.ts`) или компонента `Page`: `narrow` 768 (формы), `normal` 1328 (списки, кабинеты), `wide` во всю ширину (таблицы, админка); поля 16/24 px, вертикальный ритм 8/16/24/32 (`gap-2/4/6/8`); карточка входа и регистрации — по центру экрана. Заглушек нет: маршрут без экрана удаляется или получает `redirect`; это проверяет `routes.test.ts`. Публичная карточка `/athlete/:id`, проверка бейджа `/verify/:id`, рынок E1, граф и интервью в карточке работодателя, матрица, демо-пульт и «Здоровье» убраны до появления экранов.

Бейдж `/badge/:id.svg` отдаёт бэкенд (P2). Кабинет кандидата — **mobile-first** (основной макет 390), работодатель и админка — desktop-first (1440/1024).

## 3. Данные и состояние

- **Серверное состояние** — только TanStack Query. Ключи из orval, `staleTime` 30 с для справочников и 0 для офферов.
- **Клиентское состояние** — минимально: auth (access-токен в памяти), тема, черновики форм. Zustand при необходимости.
- **Фильтры поиска** — в URL (`?q=&roles=backend&skills=python:3`), чтобы ссылкой можно было поделиться и вернуться назад.
- **Генерация клиента:** `pnpm api:gen` (`make api-gen`, нужен Node 22) берёт схему из `OPENAPI_URL` (например, `http://localhost:28080/api/v1/openapi.json`), без неё — снимок схемы core `apps/web/openapi.json` (без `/internal/*`; обновляется выгрузкой `app.openapi()`) → `src/api` (orval, fetch-мутатор `src/api/mutator.ts`: Bearer, один refresh на 401). В CI проверяем, что сгенерированный клиент совпадает со схемой.
- **Авторизация:** access в памяти, при 401 один раз `POST /auth/refresh` (cookie), затем повтор запроса. При старте приложения тихий refresh.
- **Вход (E1-4):** `/login`, `/register`, `/auth/magic?token=&redirect=` (одноразовый токен, `redirect` — только путь SPA) и `/consents` (отдельный чекбокс на каждое согласие, список и `current_version` из `GET /me/consents`). После любого входа, если в `GET /me` нет `pd_processing`, ведём на `/consents`; `RequireRole` делает то же для кабинетов. Telegram Login Widget пока не подключён.
- **Главный путь кандидата (E35-2a):** регистрация → `/consents` → `/me/assessment` (опрос; новый кандидат идёт туда сразу, `from` по умолчанию — `PATH_START`) → «Начать тест» сейчас или «Сохранить опрос» и пройти тест позже (ссылка «На главную») → `/me/assessment/attempts/:id` → результат → «На главную» (`/me`). Пока нет опроса или завершённого теста, на любом экране кандидата, кроме самих `/me/assessment*` и Главной `/me` (там это и есть весь экран, E38-1), над страницей стоит баннер с одной кнопкой (`PathBanner` в слоте `banner` каркаса): «Пройти опрос» / «Пройти тест» / «Продолжить тест» — по `GET /assessment/history` (`pathStep` в `features/assessment/model.ts`). Вход существующего кандидата по-прежнему ведёт на `/me`.
- **Результат теста (E38-5, макеты `v2_me-assessment-result__*`):** итог «Профессия · Грейд — подтверждён» / «Грейд не подтверждён», `GradeScale` и `TypeBar` (`theta_by_type`) на шкале 0–100: балл = 55 + 25·θ, так пороги Junior −1 / Middle 0 / Senior 1 ложатся на 30 / 55 / 80, погрешность — 25·`se` (`toScale`, `seScale` в `features/assessment/model.ts`). Порог на шкале: подтверждён — следующий грейд, не подтверждён — заявленный. Подтверждён: главная кнопка «На главную», вторая — тест по приглашению бонусного этапа или «Смотреть приглашения»; не подтверждён — главная «Пройти <грейд ниже> сейчас» (`/me/assessment?profession=&grade=`), «На главную» вторая. «Ответы по темам» (`by_skill`) раскрываются по клику, «Ошибки» — неверные ответы (`ErrorBlock`) с «Объясни ответ»; «?» раскрывает правила теста и кулдаунов; «Рост» ведёт на `/me/navigator`.
- **Главная кандидата (E38-1, макеты `v2_me__*`, бриф §6.1):** до теста (`pathStep` из истории не пуст) — одна карточка «Пройди тест — без него тебя не видят работодатели», кнопка по шагу пути (опрос / тест / продолжить) и `SkillConstellation` заявленных навыков (навыки профиля и стек опроса пунктиром). После теста — слева профиль (грейд и «подтверждён 07.10 · экспресс» или «не подтверждён»), навыки с источником и ФСП; в центре «Следующий шаг» (`CircuitLine`: тест → ФСП → ответ на интерес, если есть интересы без ответа → тест на следующий грейд из `GET /candidates/me/navigator`, при кулдауне — дата), созвездие (смежные — `skill_gaps` навигатора), «Вами интересуются» (3 `OfferCardV2`); справа `MetricTile` «Сила» (`strength.value`·100) и «Место» (`топ-N %`, полоса 100 − N) из `GET /candidates/me/standing`, «Интересы». На ≤ 1024 px порядок макета 375: шаг, плитки в ряд, созвездие, интересы, навыки; профиль и ФСП — на `/me/profile`. Под плитками — ссылка «Статистика» на `/me/stats` со счётчиком «смотрели: N» (`companies_30d` из `GET /candidates/me/views`). Модель — `features/profile/home-model.ts`.
- **Статистика кандидата `/me/stats` (E38-2, макеты `v2_me-stats__*`, бриф §6.1; не в меню, ссылка с Главной):** заголовок и одна кнопка — тот же «следующий шаг», что на Главной. Плитки `MetricTile` «Сила», «Место», «Интересы», «Смотрели» (компании за 30 дней). Линии «порог Middle» нет: порога следующего грейда на шкале силы API не отдаёт (`navigator.next_grade.points_needed` — шкала баллов v1). Модель — `features/profile/stats-model.ts`.
- **Профиль кандидата (E38-6, макеты `v2_me-profile__*`, бриф §6.7):** заголовок «Профиль», кнопка «Добавить доказательство» (`/onboarding`), вкладки в адресе `?tab=skills|fsp|resume|graph`. «Навыки»: карточки «Подтверждено» (точки доверия + метки источников, «тест 07.10» — дата из `top_evidence`) и «Заявлено» (пунктир), справа статус — грейд (`GradeTag`: сплошной по `GET /candidates/me/standing`, пунктир по профилю), «подтверждён 07.10 · экспресс», «профиль опубликован», PDF, «Заполнить профиль вручную» (`/me/profile/edit`) и чек-лист «что усилит»; ниже «Почему такой грейд», «Заявлено и подтверждено», командные сигналы. «ФСП»: достижения, разряды и `FspLinkPanel` (возврат на `?tab=fsp`). «Резюме»: город, ожидания, формат, опыт. «Граф»: бывший `/me/graph` (фильтры в адресе). Без доказательств — «Доказательств пока нет» и одна кнопка; загрузка — скелетон, ошибка — «Не загрузилось · ошибка N · Повторить».
- **Онбординг (E3-5):** `/onboarding` (кандидат) — шаги на схемной линии: согласия (уже выданы, иначе `RequireRole` ведёт на `/consents`) → резюме → ФСП → GitHub → готово, каждый шаг пропускается. Шаг «Резюме»: `POST /candidates/me/resumes`, `BuildLog` строится из SSE `job.progress` (`job_id` = `resume_id`; опрос `GET …/resumes/{id}` раз в 3 с как страховка), по `parsed` показывается «Вот что я понял» с правкой опыта, образования и навыков на месте, «Всё верно» → `POST …/confirm` (правки уходят только если что-то менялось). Шаг GitHub пока заглушка «подключим позже». Шаг ФСП (E5-7): `FspLinkPanel` — «Войти через ФСП» (`GET /auth/fsp/start` → `location.assign` на мок/ФСП, возврат с `?fsp=linked|error&reason=` на `/onboarding` или `/me`), запасной путь — ID/email → код (`/fsp/link`, `/fsp/verify`) или «привязать без кода»; после привязки «Обновить из ФСП» (`/fsp/sync`). Тот же блок — в карточке «Достижения ФСП» на `/me/profile`; SSE `fsp.imported` инвалидирует профиль и обзор ФСП, «Сила профиля» и радар ДНК кода не показываются. Автоматического перехода на `/onboarding` после регистрации пока нет.

## 4. Realtime (SSE)

- Хук `useEventStream()` в корневом провайдере: один `EventSource` на вкладку, переподключение с экспоненциальной паузой.
- Обработчики событий инвалидируют запросы (`profile.updated` → `['profile']`, `offer.updated` → `['offers', id]`) и показывают тосты.
- `job.progress` → компонент `BuildLog` (терминальный лог этапов, см. дизайн-бриф).
- `profile.updated.diff` → анимация «значки загораются» на экране профиля.

## 5. Тема и токены

**Из дизайна** (v1 — [design/pack/components](../design/pack/components/) и [pack/tokens](../design/pack/tokens/); v2 — [design/v2](../design/v2/README.md)):
- `globals.css` → `packages/ui/src/styles/tokens.css` (`@fsp/ui`): CSS-переменные, светлая в `:root`, тёмная в `.dark` (переключение классом на `<html>`, тем две — светлая и тёмная (E39-2): при первом входе тема системная и следует за ней, выбор пользователя (шапка, «Настройки», `localStorage fsp-theme`) сильнее; карточка кандидата следует общей теме; `<ThemeScope dark>` включает тёмную тему для области; шкала текста `text-11…text-48`, метка `lbl`, тени `shadow-xs`/`shadow-card`). **v2:** имена из `docs/design/v2/fsp2.css` (`--deep`, `--mid`, `--t50…t200`, `--hair`, `--ok`, `--warn*`, `--err*`) — алиасы тех же токенов, плюс `--chip-fg`, `--code-*`, `--err-border`, `--shadow-menu`; `<ThemeScope light>` (класс `.light`) — светлая область внутри тёмной (`.dark .lt` макетов). Утилиты `num`, `skl`. Шапка `.hd`, нижняя панель `.tb` и меню аватара — `AppBar`/`TabBar`/`AccountMenu` из `@fsp/ui`, приложение передаёт `renderLink`.
- **Tailwind 4** (CSS-first): цвета из `tailwind.config.ts` переносятся в `@theme inline` и **ссылаются на переменные**, например `--color-brand: var(--brand)`, `--color-tint-50: var(--tint-50)`. Тогда классы `bg-brand`, `border-tint-200`, `text-brand-deep` из `fsp-ui.tsx` работают в обеих темах.
- `fsp-ui.tsx` → `packages/ui/src/brand/`. Захардкоженные цвета заменить токенами (см. [design/brief.md §0](../design/brief.md#0-дизайн-получен-2026-10-02--с-чего-начинать-фронтенду)).
- shadcn/ui: Dialog, Sheet, Drawer, Tabs, Tooltip, Popover, Select, Toast — макеты на них и рассчитаны.

Прежние правила ниже остаются в силе.


- CSS-переменные в `tokens.css` (светлая и тёмная темы), Tailwind берёт значения из них. Палитра и шрифты — [brand.md](../design/brand.md).
- Фирменные компоненты (`TrustDots`, `ConstellationAvatar`, `CircuitLine`) — SVG, без растровых картинок.
- Графики ECharts получают цвета из тех же токенов (тема ECharts собирается из CSS-переменных при монтировании).

## 7. Качество
