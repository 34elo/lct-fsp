# Фронтенд (web)

> React 19 + Vite + TypeScript, один SPA с ленивыми разделами по ролям. Почему не Next.js — [stack.md §2](stack.md#2-фронт-react-spa-nextjs-или-два-проекта). Визуальная часть — [design/brief.md](../design/brief.md).

## 1. Карта маршрутов

Маршруты приняты из макетов (таблица экран → файл → маршрут — [design/brief.md §0](../design/brief.md#0-дизайн-получен-2026-10-02--с-чего-начинать-фронтенду)).

Без навыка и профессии потребность не строится (подсказка). Карточки категорий и кандидатов крупные — только главное (профессия, грейд, вилка, совпадение, 3 навыка), подробности по клику; на карточке кандидата видимая кнопка «В шорт-лист» (закладка + текст, состояние «В шорт-листе»; `POST/DELETE /needs/{id}/shortlist/{pseudo}`, оптимистично с откатом). Работодатель: Подбор (`/employer`; подписки — ссылка в «Ваших категориях», `/employer/subscriptions`) · Шорт-лист · Приглашения (`/employer/offers`; фильтр `?show=responses` — отклики на вакансии, `/employer/responses` переадресует) · Вакансии · Задания · Компания. Бейдж на «Приглашениях» кандидата — приглашения плюс интересы. Нижняя панель на ≤768 px — пять пунктов (у кандидата без «Статистики», у работодателя без «Заданий»: они открываются с Главной и со страницы «Компания»). После входа работодатель попадает на `/employer`. Админ (E39-29, [admin.md §5](admin.md#5-меню-и-страницы)): Главная, затем группы **Очереди** (Заявки ФСП · Допуск заданий · Модерация) · **Справочники** (Реестр ФСП · Профессии · Граф навыков) · **Аналитика** (Воронка · Качество); на телефоне — строка разделов под шапкой; у каждой страницы шапка `AdminPageHeader` — подзаголовок «зачем» и ⓘ. Меню аватара: тема, «Выйти» (красный, `danger`); переключатель темы в шапке; favicon, `manifest.webmanifest` и `<title>` по экрану (`app/DocumentTitle.tsx`, из `routes.ts`); настройки и согласия — с экраном E36-4. Пункт подсвечивается по самому длинному префиксу пути (`activeNav`, доп. префиксы — `match`). **Сетка (E39-4):** каркас `PageContainer` — максимум 1440 без полей; страница берёт ширину из `PAGE` (`shared/lib/page.ts`) или компонента `Page`: `narrow` 768 (формы), `normal` 1328 (списки, кабинеты), `wide` во всю ширину (таблицы, админка); поля 16/24 px, вертикальный ритм 8/16/24/32 (`gap-2/4/6/8`); карточка входа и регистрации — по центру экрана. Заглушек нет: маршрут без экрана удаляется или получает `redirect`; это проверяет `routes.test.ts`. Публичная карточка `/athlete/:id`, проверка бейджа `/verify/:id`, рынок E1, граф и интервью в карточке работодателя, матрица, демо-пульт и «Здоровье» убраны до появления экранов.

Бейдж `/badge/:id.svg` отдаёт бэкенд (P2). Кабинет кандидата — **mobile-first** (основной макет 390), работодатель и админка — desktop-first (1440/1024).

## 3. Данные и состояние

- **Серверное состояние** — только TanStack Query. Ключи из orval, `staleTime` 30 с для справочников и 0 для офферов.
- **Клиентское состояние** — минимально: auth (access-токен в памяти), тема, черновики форм. Zustand при необходимости.
- **Фильтры поиска** — в URL (`?q=&roles=backend&skills=python:3`), чтобы ссылкой можно было поделиться и вернуться назад.
- **Генерация клиента:** `pnpm api:gen` (`make api-gen`, нужен Node 22) берёт схему из `OPENAPI_URL` (например, `http://localhost:28080/api/v1/openapi.json`), без неё — снимок схемы core `apps/web/openapi.json` (без `/internal/*`; обновляется выгрузкой `app.openapi()`) → `src/api` (orval, fetch-мутатор `src/api/mutator.ts`: Bearer, один refresh на 401). В CI проверяем, что сгенерированный клиент совпадает со схемой.
- **Авторизация:** access в памяти, при 401 один раз `POST /auth/refresh` (cookie), затем повтор запроса. При старте приложения тихий refresh.
- **Вход (E1-4):** `/login`, `/register`, `/auth/magic?token=&redirect=` (одноразовый токен, `redirect` — только путь SPA) и `/consents` (только обязательные согласия — отдельный чекбокс на каждое, список и `current_version` из `GET /me/consents`; необязательные выдаются в настройках и до этого выключены, E39-6). В форме регистрации — чекбокс обязательного согласия `pd_processing`: без него аккаунт не создаётся, после `POST /auth/register` согласие сразу уходит в `PUT /me/consents`, экран `/consents` новому пользователю не показывается. После любого входа, если в `GET /me` нет `pd_processing`, ведём на `/consents`; `RequireRole` делает то же для кабинетов. Telegram Login Widget пока не подключён.
- **Главный путь кандидата (E35-2a, E39-6 — один поток):** регистрация (с обязательным согласием) → `/me/assessment`: «Шаг 1. Направление и навыки» (все профессии справочника крупными карточками `ChoiceCards` — подложка выделения плавно «перетекает» к выбранной, тонкий банк помечен «бета» с ⓘ; навыки — `SkillInput` с подсказками по профессии) → «Шаг 2. Грейд и ожидания» (карточки грейда, формат, `SalaryRangeInput`, экспресс) → «Начать тест» сохраняет ответы и открывает «Шаг 3. Тест» `/me/assessment/attempts/:id` → результат → «На главную» (`/me`); «Разбор теста» `/me/assessment/attempts/:id/review` (E39-10, из результата и истории: задания по типам навыков, ваш и верный ответ, причина; переключатель «Скрыть объяснения» хранится в `localStorage`, у каждого задания своё сворачивание; блок «Что подтянуть» → `/me/navigator`); «Сохранить, тест позже» — ссылка «На главную». Шаг 2 открывается сразу, если направление уже сохранено или пришло в ссылке (`?profession=&grade=` из навигатора и результата); `?step=1` — правка направления и навыков из профиля (ссылка «Направление и навыки» на `/me/profile`, кнопка «Сохранить» без теста). Слова «опрос» в UI нет. Пока нет опроса или завершённого теста, на любом экране кандидата, кроме самих `/me/assessment*` и Главной `/me` (там это и есть весь экран, E38-1), над страницей стоит баннер с одной кнопкой (`PathBanner` в слоте `banner` каркаса): «Выбрать направление» / «Пройти тест» / «Продолжить тест» — по `GET /assessment/history` (`pathStep` в `features/assessment/model.ts`). Вход существующего кандидата по-прежнему ведёт на `/me`.

На ≤ 1024 px порядок макета 375: шаг, плитки в ряд, созвездие, интересы, навыки; профиль и ФСП — на `/me/profile`. Под плитками — ссылка «Статистика» на `/me/stats` со счётчиком «смотрели: N» (`companies_30d` из `GET /candidates/me/views`). Модель — `features/profile/home-model.ts`.

Без доказательств — «Доказательств пока нет» и «Пройти тест», вкладки остаются; загрузка — `SkeletonProfile`, ошибка — «Не загрузилось · ошибка N · Повторить». Шаг GitHub пока заглушка «подключим позже». Шаг ФСП (E39-28, ADR-052): `FspLinkPanel` — одна кнопка «Привязать ФСП» (`POST /candidates/me/fsp/registry-link`): нашли — «Ваш email найден в базе ФСП», обзор опрашивается раз в 2 с до появления достижений (до 30 с), затем обновляются все экраны; не нашли — форма заявки (ФИО, email/телефон в ФСП, мероприятие → `POST /candidates/me/fsp/requests`), дальше статус заявки (`GET /candidates/me/fsp/request`: ждёт / отклонена с причиной и «Подать заявку заново»). «Войти через ФСП» и ввод кода из UI убраны (бэкенд сохранён); после привязки «Обновить из ФСП» (`/fsp/sync`). Тот же блок — в карточке «Достижения ФСП» на `/me/profile`; SSE `fsp.imported` инвалидирует профиль и обзор ФСП, «Сила профиля» и радар ДНК кода не показываются. Автоматического перехода на `/onboarding` после регистрации пока нет.

## 4. Realtime (SSE)

- Хук `useEventStream()` в корневом провайдере: один `EventSource` на вкладку, переподключение с экспоненциальной паузой.
- Обработчики событий инвалидируют запросы (`profile.updated` → `['profile']`, `offer.updated` → `['offers', id]`) и показывают тосты.
- `job.progress` → компонент `BuildLog` (терминальный лог этапов, см. дизайн-бриф).
- `profile.updated.diff` → анимация «значки загораются» на экране профиля.

## 5. Тема и токены

**Из дизайна** (v1 — [design-pack/components](../archive/design-pack/components/) и [design-pack/tokens](../archive/design-pack/tokens/); v2 — [design/v2](../design/v2/README.md)):
- `globals.css` → `packages/ui/src/styles/tokens.css` (`@fsp/ui`): CSS-переменные, светлая в `:root`, тёмная в `.dark` (переключение классом на `<html>`, тем две — светлая и тёмная (E39-2): при первом входе тема системная и следует за ней, выбор пользователя (шапка, «Настройки», `localStorage fsp-theme`) сильнее; карточка кандидата следует общей теме; `<ThemeScope dark>` включает тёмную тему для области; шкала текста `text-11…text-48`, метка `lbl`, тени `shadow-xs`/`shadow-card`). **v2:** имена из `docs/design/v2/fsp2.css` (`--deep`, `--mid`, `--t50…t200`, `--hair`, `--ok`, `--warn*`, `--err*`) — алиасы тех же токенов, плюс `--chip-fg`, `--code-*`, `--err-border`, `--shadow-menu`; `<ThemeScope light>` (класс `.light`) — светлая область внутри тёмной (`.dark .lt` макетов). Утилиты `num`, `skl`. Шапка `.hd`, нижняя панель `.tb` и меню аватара — `AppBar`/`TabBar`/`AccountMenu` из `@fsp/ui`, приложение передаёт `renderLink`.
- **Tailwind 4** (CSS-first): цвета из `tailwind.config.ts` переносятся в `@theme inline` и **ссылаются на переменные**, например `--color-brand: var(--brand)`, `--color-tint-50: var(--tint-50)`. Тогда классы `bg-brand`, `border-tint-200`, `text-brand-deep` из `fsp-ui.tsx` работают в обеих темах.
- `fsp-ui.tsx` → `packages/ui/src/brand/`. Захардкоженные цвета заменить токенами (см. [design/brief.md §0](../design/brief.md#0-дизайн-получен-2026-10-02--с-чего-начинать-фронтенду)).
- shadcn/ui: Dialog, Sheet, Drawer, Tabs, Tooltip, Popover, Select, Toast — макеты на них и рассчитаны.

Прежние правила ниже остаются в силе.


- CSS-переменные в `tokens.css` (светлая и тёмная темы), Tailwind берёт значения из них. Палитра и шрифты — [brand.md](../design/brand.md).
- Фирменные компоненты (`TrustDots`, `ConstellationAvatar`, `CircuitLine`) — SVG, без растровых картинок.
- Графики ECharts получают цвета из тех же токенов (тема ECharts собирается из CSS-переменных при монтировании).
