# Рекомендации, подбор и uplift

> ⚠️ **Концепция v2 (рабочая, 2026-10-05):** выдача по категориям из теста, сила профиля (тест, ФСП, доверие, свежесть), экран «потребность → категории». См. [solution.md §4](../solution.md#4-категории-и-подбор). Ниже описана текущая реализация.

> **Приоритет — качество подбора (ADR-027 п. 6):** подбор весит 35 % оценки, техника — 7 %. Где качество спорит со скоростью или памятью (`lite`), выбираем качество; веса `match` и `rank` подбираются на размеченных парах против BM25 (E36-6). Слагаемое ФСП в силе профиля получит множитель релевантности дисциплины профессии (E36-3).

> Как мы рекомендуем кандидатов работодателю и навыки кандидату. Опирается на [graph.md](graph.md) (что за граф и как он хранится) и формулы [ml.md](ml.md).
> Решение: в MVP — **уровень 0** (контентные рекомендации по графу и эмбеддингам) и **уровень 1** (подстройка под работодателя в сессии). Обучение на реакциях и генеративная модель «следующий кандидат как токен» — в дорожной карте. Показы логируем с первого дня (ADR-014).

## 2. Конвейер

```
отбор (до ~300)          ранжирование               переранжирование            объяснение
──────────────────       ──────────────────         ──────────────────          ──────────────────
SQL по проекциям         признаки из графа          разнообразие (MMR)          лучший путь в графе
+ 1 шаг смежности        + косинус векторов         не перегружать кандидата    для каждого
+ pgvector top-K         + веса сессии (ур. 1)      «активно ищу», свежесть     требования
```

Весь конвейер выполняется в **core** (модуль `matching`). Вектор запроса и разбор текста даёт `ml-api` синхронно.

## 3. Отбор кандидатов

Два источника объединяются:

**A. По графу** — кто закрывает обязательные навыки сам или через смежный:

```sql
WITH req AS (                                   -- требования + смежные навыки (1 шаг по графу навыков)
  SELECT skill_id, skill_id AS via, 1.0 AS adj, min_level
  FROM vacancy_skills WHERE vacancy_id = :vid AND required
  UNION ALL
  SELECT vs.skill_id, r.skill_b, r.weight, vs.min_level
  FROM vacancy_skills vs JOIN skill_relations r ON r.skill_a = vs.skill_id AND r.kind = 'adjacent'
  WHERE vs.vacancy_id = :vid AND vs.required
),
cover AS (                                      -- насколько каждый кандидат закрывает каждое требование
  SELECT cs.candidate_id, req.skill_id, max(cs.confidence * req.adj) AS eff, max(req.min_level) AS min_level
  FROM req JOIN candidate_skills cs ON cs.skill_id = req.via
  GROUP BY cs.candidate_id, req.skill_id
)
SELECT c.user_id
FROM candidates c JOIN cover ON cover.candidate_id = c.user_id
WHERE c.deleted_at IS NULL AND c.search_status <> 'dnd'
  AND c.formats && :formats
  AND (c.salary_min IS NULL OR c.salary_min <= :salary_to * 1.1)
  AND NOT (:company_id = ANY (c.stoplist_company_ids))
GROUP BY c.user_id
HAVING count(*) FILTER (WHERE cover.eff >= level_floor(cover.min_level)) >= :required_count - 1;
```

Реализация (E7-1): запрос разбит по владельцам таблиц — покрытие требований по `candidate_skills` (`graph.service.covering_candidates`, тот же `HAVING`, лимит `matching_candidate_limit_sql`), затем фильтры по анкете (`candidates.service.eligible`; `formats &&` и стоп-лист — в SQL только на PostgreSQL). Все жёсткие фильтры повторно проверяются при скоринге (`matching.scoring.hard_filter`).

**B. По смыслу** — `ORDER BY embedding <=> :vacancy_vec LIMIT 100` с теми же жёсткими фильтрами по атрибутам. Добирает тех, у кого нужные навыки не легли в справочник. Такие кандидаты идут с пометкой «совпадение только по смыслу».

**Несколько направлений (E43-6).** Кандидат с завершёнными тестами по двум профессиям — одна запись и один псевдоним, карточка считается при каждом запросе (отдельного индекса нет, дублей не бывает). Фильтр `roles` пропускает его по `primary_role` анкеты **или** по действующему грейду теста в этой профессии; анкета без `primary_role`, но с тестом, видна. Если запрошено направление (`category`, `professions`, `roles`), в карточке `primary_role` и `grade` — этого направления, `categories` — все.

Для **поиска без вакансии** чипсы-фильтры собираются в «виртуальную вакансию» (роли, грейд, навыки, формат, бюджет), смысловой остаток запроса даёт вектор.

## 4. Ранжирование

Признаки и формула — [ml.md §6](ml.md#6-матчинг-вакансия--кандидат):

```
score = w1·покрытие навыков (доверие + смежность)   ← граф
      + w2·смысловая близость (косинус)             ← эмбеддинг
      + w3·попадание в грейд                        ← граф
      + w4·попадание в вилку
      + w5·сила подтверждения ФСП                   ← граф
      + w6·сигнал связей («выступал с призёрами»), максимум 0.03
стартовые веса: 0.45 / 0.20 / 0.15 / 0.10 / 0.10 / ≤0.03
```

Веса лежат в `scoring_config`. На уровне 1 они подстраиваются в пределах сессии (§7).

### 4.1. Взаимный подбор: интерес кандидата

В найме выбирают обе стороны. Скор `score` отвечает на вопрос «подходит ли кандидат работодателю», `p_accept` — «примет ли кандидат этот оффер».

```
p_accept(c, v, вилка) = σ( b0 + b1·salary_gap + b2·format_match + b3·stack_interest + b4·company_rating + b5·active )

salary_gap     = (salary_to − salary_min_кандидата) / salary_min_кандидата       (обрезка −0.5…0.5)
format_match   = 1, если формат вакансии среди желаемых, иначе 0
stack_interest = доля primary_stack кандидата среди навыков вакансии (0…1)
company_rating = (рейтинг ответственности − 3) / 2                                  (−1…1)
active         = 1, если статус «активно ищу»
стартовые коэффициенты: b0 = −0.5, b1 = 4, b2 = 1, b3 = 1.5, b4 = 0.5, b5 = 0.5
```

- **Где используется:**
  - подборка под вакансию по умолчанию сортируется по гармоническому среднему `H = 2·score·p_accept / (score + p_accept)`, переключатель «только по соответствию» тоже есть;
  - в модалке оффера `p_accept` пересчитывается при вводе вилки: «Вероятность принятия: низкая → средняя»;
  - в модалках интереса и приглашения (E33-5) к `p_accept` добавлены подсказка «поднимите верх вилки до X → Y %», медиана ожиданий категории и средний срок ответа кандидатов категории (`scoring.yaml` `p_accept.forecast`);
  - в карточке, если выбрана вакансия, показывается «Интерес кандидата: высокий».
- **Калибровка:** коэффициенты донастраиваются логистической регрессией на истории офферов (демо-история в seed, позже — реальная). Калибровочная кривая — на странице качества.
- **Честность:** `p_accept` не скрывает кандидатов и не участвует в жёстких фильтрах, только сортирует и подсказывает.

## 5. Переранжирование

| Правило | Зачем |
|---|---|
| **MMR** по эмбеддингам (λ = 0.8) в топ-20 | Не показывать 10 почти одинаковых профилей подряд |
| У кандидата ≥ 3 неотвеченных офферов → × 0.9 | Не заваливать одного человека, давать шанс другим |
| Показан этой компании ≥ 5 раз без действий → × 0.95 | Выдача не застывает |
| «Активно ищу» → × 1.03; профиль обновлён за 7 дней → × 1.01 | Приоритет тем, кто готов к разговору |
| Пол, возраст, фото, место жительства в признаках отсутствуют | Защита от предвзятости |
| Мониторинг: доля кандидатов без ФСП в топ-10 | Платформа не должна стать «только для олимпиадников» |

## 6. Uplift для кандидата: какой навык добавить

**Что видит кандидат:**

> **Подтверди Docker — подойдёшь под 64% больше вакансий** (сейчас 14, станет 23), медиана вилок +20 000 ₽.
> Как подтвердить: тест на платформе (10 мин) · проект с Docker на GitHub · Кубок по продуктовому программированию, 15 ноября.
> Docker + Kafka вместе: +93% (14 → 27).

**Алгоритм:**
1. **Релевантные вакансии `V`:** опубликованные; формат пересекается с форматами кандидата; `salary_to ≥ 0.9 × salary_min`; роль в топ-2 ролях кандидата; грейд в пределах ±1 от его грейда.
2. **Базовое число:** `base = |{v ∈ V : проходит жёсткие фильтры и score ≥ 0.6}|`.
3. **Кандидатные навыки `S`:** навыки из `vacancy_skills` по `V`, где уровень кандидата ниже требуемого хотя бы в одной вакансии. Берём топ-30 по спросу.
4. **Симуляция:** для каждого `s ∈ S` берём копию профиля с `conf(s) = max(conf(s), 0.65)` (уровень ●●●○) и пересчитываем наследование по иерархии. Считаем `new(s)`, получаем `Δ = new − base`, `pct = Δ / max(base, 1)`. Если `base = 0`, показываем абсолютное «+N вакансий» и долю от `|V|`.
5. **Комбинация:** жадно добавляем до 3 навыков, каждый раз беря лучший по приросту.
6. **Деньги:** `Δ медианы = median(salary_to | подходит после) − median(salary_to | подходит сейчас)`.
7. **Как подтвердить** (`how_to_confirm`):
   - тест, если навык `testable`;
   - GitHub (подсказка «добавь проект»), если код уже анализировался;
   - соревнования ФСП в ближайшие 120 дней, где правило дисциплины даёт навыку вес ≥ 0.5. Обход: `skill ← rule ← discipline ← competition {status: announced}`.

**Реализация** (`app/matching/uplift.py`, `uplift_service.py`, `GET /candidates/me/uplift`, параметры — `scoring.yaml` `limits.uplift_*`): в ответ идут только навыки с `extra > 0`, не больше `uplift_items_max` (10); `combo` отдаётся при ≥ 2 навыках; нет меток ролей — берётся основная роль, нет её — фильтр по роли не применяется; при `base = 0` `median_salary_delta = 0`; соревнования — со статусом `announced` или `registration`, `start_date` в ближайшие 120 дней; симуляция пересчитывает только вакансии, чьи требования затрагивает поднятый навык (сам, родитель по иерархии или смежный).

**Стоимость:** ~100 вакансий × 30 навыков × скоринг ≈ 3 000 оценок по несколько микросекунд — меньше 50 мс. Кеш по `(profile_version, vacancies_version)` на 10 минут.

**Где показываем:**
- навигатор (полный список);
- виджет «Быстрый рост» в профиле (топ-1);
- бот: после обновления профиля или раз в неделю, если лучший прирост ≥ 15%.

**Честность:** подпись «по вакансиям, открытым сейчас в твоих ролях». Прирост детерминированный, его можно проверить: подтвердил навык → число подходящих вакансий стало ровно таким.

**Отдельно — путь к следующему грейду** (из разбивки грейда): «До Middle не хватает 1.5 балла: тест по Python (+1–2) или GitHub (+до 2)».

## 7. Уровень 1: подстройка под работодателя в сессии

**Сессия** — пара «пользователь работодателя + контекст» (вакансия или хеш поискового запроса). Живёт 24 ч, состояние в Redis `s:rec:{user}:{ctx}`.

**Сигналы:**

| Событие | Вес | Откуда |
|---|---|---|
| Открыл карточку | +1 | фронт → `POST /recs/feedback` |
| Смотрел карточку > 20 с | +1 | фронт |
| В шорт-лист | +3 | кнопка «В шорт-лист» |
| Оффер | +5 | создание оффера |
| «Не подходит» (опц. причина) | −3 | кнопка на карточке |

**Что меняется** (после ≥ 3 сигналов):
1. **Вектор запроса (Роккио):** `q' = norm(q + 0.3·mean(emb⁺) − 0.15·mean(emb⁻))`.
2. **Веса признаков:** онлайн-логистическая регрессия на признаках позитивных и негативных кандидатов. Сильная L2-регуляризация к стартовым весам, каждый вес ограничен диапазоном `[0.5·w₀, 1.5·w₀]`, сумма нормируется. Дополнительные бинарные признаки: капитан, есть GitHub, «активно ищу».
3. **Причины «не подходит»** превращаются в подсказки фильтров: «не тот стек» → предложить сделать навык обязательным, «дорого» → предложить поднять вилку.

**Что видит HR:** чипсы «Учли: чаще выбираете кандидатов с подтверждением ФСП ×» — если вес вырос больше чем на 25%. Крестик сбрасывает подстройку.

**Ограничения:** жёсткие фильтры не меняются никогда. Подстройка — только перестановка внутри уже подходящих.

**Реализация (E17-4)** — `app/recommendations/tuning.py` (формулы), `service.py`, `router.py`; параметры — `scoring.yaml` `session_tuning` (стартовые веса — `matching_weights` + `extra_weights`):
- сессия = `session_id` выдачи (показы пользователя работодателя); сигналы — `rec_feedback` этой сессии за `session_ttl_hours`; одна и та же реакция на кандидата учитывается один раз (повтор не меняет подстройку); `offer` (+5) учитывается, если записан в `rec_feedback`;
- признаки `x = {skills, semantic, grade, salary, fsp, captain, github, active}` снимаются при показе в `impressions.features.x` (без вакансии: `skills` — покрытие запрошенных навыков, `fsp` — есть навык из ФСП, `grade = salary = 0`);
- веса: метка кандидата — сумма весов реакций, `> 0` — позитив, `< 0` — негатив, вес примера `|y|`; учим множители `m_k = w_k/w₀_k`: `m += η·(|y|·(t − σ(w·x̃))·x̃ − λ·(m − 1))`, `x̃` — центрирование по показам сессии, `m ∈ [0.5, 1.5]`, затем нормировка `Σw = Σw₀` с сохранением границ;
- Роккио — по векторам кандидатов выдачи, `q` — вектор вакансии (нет — нулевой); `semantic` пересчитывается по `q'`;
- скор: с вакансией `score' = min(1, Σw'·x · score/base)` (`K_soft` и «ищу» сохраняются), без вакансии `Σw'·x`; затем те же множители и MMR (§5); подстроенная выдача не кешируется;
- причины «не подходит» (`stack`, `salary`, `grade`, `format` или текст с ключевыми словами) → `hints`: «сделать навык обязательным», «поднять вилку» и т. п.;
- сброс (`DELETE /recs/sessions/{id}`) пишет в Redis `s:rec:{user}:{session_id}` id последней реакции (TTL 24 ч): учитываются только реакции после него, журнал `rec_feedback` не удаляется;
- чужая или несуществующая сессия → 404 `rec_session_not_found`; чужой `session_id` в поиске выдачу не подстраивает.

Проверка на симуляции (`tests/test_recs_tuning.py`): работодатель со скрытым предпочтением «капитаны с подтверждением ФСП», 5 действий на верхних кандидатах — nDCG@10 растёт и с Роккио, и только на весах.

## 8. Логирование показов и реакций

Без показов нельзя честно учиться: клик без знания «что было показано и на какой позиции» смещён. Поэтому пишем с первого дня:

```sql
CREATE TABLE impressions (
  id bigserial PRIMARY KEY,
  company_id uuid, user_id uuid, session_id text,
  context_type text,            -- vacancy | search | similar
  context_id text,              -- vacancy_id или хеш фильтров
  candidate_id uuid, position smallint, score real,
  features jsonb,               -- снимок признаков на момент показа
  model_version text,           -- версия весов / конфига
  shown_at timestamptz DEFAULT now()
);
CREATE TABLE rec_feedback (
  id bigserial PRIMARY KEY,
  impression_id bigint, company_id uuid, user_id uuid, session_id text,
  candidate_id uuid, event text,  -- open | dwell | shortlist | dismiss | offer
  reason text, created_at timestamptz DEFAULT now()
);
```

Исходы офферов (принят, отклонён с причиной, нанят) уже лежат в `offers` и `offer_events`.

## 9. Уровень 2 и «следующий кандидат как токен» (дорожная карта)

| Этап | Что | Когда возможно |
|---|---|---|
| Learning-to-rank | LightGBM LambdaMART на `impressions` с метками (оффер 3, шорт-лист 2, открытие 1, отказ 0) и поправкой на позицию (IPS) | от ~5–10 тыс. показов с реакциями |
| Последовательные рекомендации | SASRec / BERT4Rec по сессиям работодателей: следующий объект как следующий токен | от тысяч сессий |
| Генеративный поиск с семантическими ID | Вектор кандидата (векторы доверия по навыкам + текстовый эмбеддинг) → RQ-VAE → 3 кода по 256 значений, например `(12, 7, 41)`: крупный кластер → подкластер → человек. Трансформер генерирует коды следующего кандидата, декодирование ограничено существующими ID (trie). Новые кандидаты сразу получают коды, поэтому холодного старта нет | от тысяч сессий |

**Почему не в MVP:**
- реальных сессий нет, а обучение на синтетике из нашего генератора выучит сам генератор;
- каталог маленький, человека нанимают один раз, коллаборативный сигнал слабый;
- чёрный ящик конфликтует с принципом «каждый ✓ — путь в графе»;
- нет времени у ML.

**Вау-опция**, если останется время: маленький SASRec на симулированных сессиях. У симулированных работодателей есть скрытое предпочтение («любит капитанов команд»), которого нет в фильтрах. На странице качества показываем, за сколько сессий модель его восстанавливает. С подписью «механизм на симуляции».

## 10. Метрики

| Что | Метрика | Где |
|---|---|---|
| Подбор | P@5, nDCG@10, доля приукрашенных резюме в топ-10 против BM25 и «только эмбеддинги» | синтетический рынок ([ml.md §11](ml.md#11-оценка-качества)) |
| Подстройка в сессии | nDCG@10 после k = 3, 5, 10 действий против варианта без подстройки | симулированные работодатели со скрытыми предпочтениями |
| Разнообразие | средняя попарная близость в топ-10 до и после MMR | синтетика |
| Uplift | предсказанное число вакансий = фактическому после подтверждения навыка (детерминированная проверка) | юнит-тест + демо |

## 11. API

| Метод и путь | Назначение |
|---|---|
| `GET /vacancies/{id}/matches` | Подборка; пишет `impressions`, возвращает `session_id` |
| `POST /search/candidates` | Поиск; пишет `impressions`, возвращает `session_id` |
| `GET /candidates/{pseudo_id}/similar?limit=` | Похожие: `{items: [CandidateCard + similarity, common_skills[]], session_id}`; `sim = 0.7·J + 0.3·cos⁺` (J — взвешенный Жаккар навыков по доверию без `claimed_only`; нет вектора — только J); пишет показы (`context_type=similar`); скрытый/несуществующий — 404 |
| `POST /recs/feedback` | `{session_id, candidate_pseudo_id, event, reason?}` |
| `GET /recs/sessions/{id}` / `DELETE /recs/sessions/{id}` | Учтённые подстройки (для чипсов «Учли: …») / сброс |
| `GET /candidates/me/uplift` | `{relevant_total, base, items: [{skill, current_level, extra, pct, median_salary_delta, how_to_confirm[]}], combo: {skills[], extra, pct}}` |
| `GET /candidates/me/navigator` | Uplift (топ-3) + путь к следующему грейду + ближайшие соревнования |
| `GET /candidates/me/graph`, `GET /candidates/{pseudo_id}/graph` | Подграф для визуализации ([graph.md §6](graph.md#6-api-подграфа)) |
