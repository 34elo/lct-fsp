# Тестирование, категории и ранжирование (v2)

> Технический документ для реализации эпиков E21–E26, E30. Продуктовая логика — в [solution.md](../solution.md), решения — ADR-018…024. Все числа живут в `data/scoring.yaml` (раздел `assessment`), здесь — их значения по умолчанию.
> **Принцип: просто и прозрачно.** Одна шкала θ, одна модель (Rasch), одно правило остановки (SPRT), одна формула ранжирования. Всё остальное — данные и конфиг.

## 1. Как модули связаны

```
taxonomy  ── навыки (тип), профессии (веса навыков), грейды (пороги θ)
   │
assessment ── опрос → попытка → задания → ответы → итог (грейд, θ по типам, честность)
   │  service: get_grades(candidate), get_theta(candidate, profession), integrity(candidate)
   │  outbox:  assessment.attempt.finished, candidate.category.changed
   ▼
graph ── доказательства источника `test` по навыкам → доверие (существующий пересчёт)
   ▼
matching ── категория = профессия × грейд; сила профиля; подбор под потребность; объяснения
```

- Модули общаются только через `service.py` друг друга (import-linter).
- `assessment` не знает про подбор, `matching` не знает про задания.
- `graph/category.py` и `graph/grade.py` больше **не задают** категорию и грейд: их сигналы идут в силу профиля (§7).

**Сквозной поток:**
1. Кандидат сохраняет опрос.
2. Создаёт попытку на профессию и грейд. Проверки: email подтверждён, согласия есть, кулдаун соблюдён.
3. Цикл `next` / `answer` до остановки SPRT.
4. Итог: запись грейда, доказательства `test` в `graph`, события в outbox.
5. `matching` пересчитывает силу профиля по событию.
6. Кандидат появляется в категории, если есть согласие `profile_publication`.

## 2. Модель навыков

- **Навык:** `type ∈ {fundamental, hard, thinking, business, soft, experience}`.
- **Профессия:** `slug`, название, веса навыков `{skill: w}` (бывший `roles.yaml`). Создаёт админ. В MVP: Backend, Frontend, Mobile, Data/ML, DevOps, QA, AI Engineer.
- **Грейд:** универсальная шкала θ. Порог `cut` — минимальный θ грейда:

| Грейд | `cut` |
|---|---|
| Junior | −1.0 |
| Middle | 0.0 |
| Senior | 1.0 |

- **Категория** = профессия, выбранная в опросе, × подтверждённый грейд. Хочешь вторую категорию — проходи тест по второй профессии.
- **Карточка навыка** (`data/skills/cards/<skill>.yaml`): утверждения по уровням, понятия, заблуждения. Нужна авторам заданий и для объяснений («Middle: выполнены утверждения 1, 2, 4»). Для работы движка не обязательна. Схема — `SkillCard` в `app/taxonomy/cards.py` (`schema_version`, `skill` = имя файла, `type` = тип из справочника, `summary`, `levels.{junior,middle,senior}` по 2–8 утверждений с нумерацией с 1, `concepts[] {term, note}` ≥ 3, `misconceptions[] {claim, truth}` ≥ 2); проверка — `make cards-check` (в CI).

## 4. Семейства заданий

Семейство — генератор вариантов с доказуемым ответом. Две реализации с общим интерфейсом:

```python
class Family(Protocol):
    slug: str
    kind: Kind
    skill: str
    level: int

    def generate(self, rng: Random, world: World) -> Item: ...  # условие, варианты, ключ, meta
    def score(self, item: Item, answer: Any) -> float: ...  # 0..1
```

- **Кодовые** (`services/core/app/assessment/families/*.py`): трассировка кода, мутации, расчёты, архитектура как граф, анализ данных с известной истиной.
  Семейства по миру (E26-2, `families/world_tasks.py`) берут артефакты из полного `World`: архитектура — `arch_blast_radius` (сколько прикладных сервисов заденет отказ узла, транзитивно) и `arch_start_order` (порядок подъёма цепочки зависимостей с одного пути от gateway — порядок единственный); данные — `data_table_aggregate` (сумма, количество, максимум по таблице с фильтром) и `kpi_anomaly_day` (выброс 25–40 % в ряду метрики за 14 дней; доля — только вниз); логи — `incident_log_root_cause` (каскад `timeout` вверх по графу, первопричина — единственная своя ошибка; шум до инцидента); SQL — `sql_join_filter` (JOIN по FK + фильтр, `COUNT(*)` или `SUM`) и `sql_left_join` (родители без детей, `COUNT(*)` по LEFT JOIN, лидер по числу детей); SJT по команде — `sjt_teamwork`, `sjt_mentoring` (имена, роли и сервисы из `team`). Для данных и SQL `meta["exec"]` исполняет расчёт (SQL — в SQLite в памяти) и сверяется с ключом. Ручки тянутся из `rng` семейства до обращения к миру, поэтому перекраска их не меняет.
  Цепочки-инциденты (E26-3, `families/incident_chains.py`, `kind = chain`, тип «мышление», уровень 4) — одно задание из пяти шагов-`Item` обычных типов, следующий опирается на вывод предыдущего: `incident_chain_outage` (навык `root_cause_analysis`) — метрика бизнеса с выбросом сегодня (`choice`) → логи релиза и каскада `timeout`, первопричина (`choice`) → два места релиза, дефект в одном: соединение не возвращается в пул или кеш с уникальным ключом без ограничения (`find_bug`) → сколько входов gateway отдают ошибки (`exact`) → первое действие (`choice`); `incident_chain_latency` (`performance_reasoning`) — p95 по сервисам «неделю назад → сегодня», источник — наибольший абсолютный рост (`choice`) → журнал запросов postgres: N+1 или перебор без индекса (`choice`) → обработчик и миграция релиза (`find_bug`) → запросов в секунду к postgres = RPS источника × запросов за вызов (`estimate`) → исправление (`choice`). Артефакт шага не называет прошлые ответы («сервис-первопричина», таблицы не совпадают с её именем). Ключ — список ключей шагов; балл — средний балл шагов (недостающие шаги — 0, лишние — 0 за всё), поэтому цепочка калибруется как обычное семейство: один `b`, `pilot` при добавлении, допуск админом. `families-check` проверяет каждый шаг теми же правилами и что ошибка в одном шаге даёт частичный балл. В конструкторе `chain` недоступен.
- **Спецификации** (`families.spec`, из конструктора): универсальные интерпретаторы типов. Формулы считает безопасный вычислитель выражений (без `eval`).

**Типы заданий и оценка:**

| `kind` | Ответ | `score` |
|---|---|---|
| `exact` | Строка или число (вывод кода, результат SQL) | 1 при совпадении после нормализации, иначе 0 |
| `estimate` | Число (оценка на порядок) | 1, если \|log₁₀(ответ/истина)\| ≤ 0.3; 0.5, если ≤ 0.6; иначе 0 |
| `choice` | Один вариант | 1 / 0 |
| `find_bug` | Строки дефекта | 1 — все; 0.5 — половина и больше; иначе 0 |
| `order` | Последовательность | 1 − D / D_max, D = Σ\|позиция кандидата − позиция ключа\| |
| `sjt` | Ранжирование вариантов действий | Как `order`, ключ — порядок по оценкам эффективности |
| `chain` | Список ответов по шагам цепочки (E26-3) | Средний балл шагов, каждый по своему `kind` |
| `open` | Текст | Доля выполненных пунктов рубрики. **Только регулярные задания**, в θ не идёт |

**Мир (`World`)** — контекст варианта, а не отдельный движок:
- `World.from_seed(seed, domain)` → компания, домен, словарь сущностей, список сервисов, таблицы, метрики (`app/assessment/world.py`). Полный мир (E26-1): `nodes` + `edges` — граф сервисов с gateway и инфраструктурой (ацикличен, у сервиса владелец, RPS, p95); `data` — таблицы с 6–10 строками, связанные внешними ключами; `kpis` — метрики с рядом за 14 дней; `team` — 4–6 человек с ролями и сервисами. Новые части берут свои генераторы `Random(f"{seed}:{domain}:<часть>")`, старые поля не меняются — выданные задания пересобираются с тем же ключом.
- Семейства берут из мира имена и числа, поэтому один и тот же тест выглядит по-разному у разных людей.
- Домен берётся из вакансии (e-commerce, финтех; RAG-сервис для AI Engineer) или случайно: `domain_for_vacancy(role, title, description)` — профессия `ai_engineer` → `rag_service`, иначе ключевые слова текста (ничья или пусто → сид). Используется в `POST /assessment/plan/preview` для примеров; попытка берёт домен из профессии.
- Перекраска не меняет ручки сложности.

**Автопроверка семейства** (`make families-check`, CI) на 1000 сидах:
- генерация без ошибок;
- ответ решателя = исполнению (для кода);
- ключ однозначен, неверные варианты ≠ ключу;
- детерминизм (два прогона с разным `PYTHONHASHSEED`);
- ручки в границах уровня.

Плюс проверка банка: каждый тип навыка покрыт ≥ 2 семействами, каждый `kind`, кроме `open`, — хотя бы одним; навык семейства есть в `data/taxonomy`, и его тип совпадает; есть якоря. Код — `app/assessment/families/check.py`. Соглашения для семейства: `meta["exec"]` — Python-фрагмент, stdout которого сверяется с ключом; `meta["exec_ok"]` / `meta["exec_bug"]` — оригинал и мутант (`find_bug`), их вывод на примере обязан различаться; `knob_bounds` класса ↔ `meta["knobs"]` варианта. Исполняется только код, сгенерированный семейством.

## 5. Тест: оценка, остановка, грейд

**Модель Rasch:**

```
P(θ, b) = 1 / (1 + e^-(θ − b))
```

Частичный балл `score ∈ [0, 1]` входит в правдоподобие как дробный исход.

**θ:** EAP на сетке [−4, 4] с шагом 0.1, априорное распределение N(0, 1), SE — стандартное отклонение апостериорного. Плюс θ по типам навыков — EAP по ответам этого типа (для профиля и объяснений).

**Априорная `b` семейства** по уровню:

| Уровень | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| `b` | −2 | −1 | 0 | 1 | 2 |

**Классификационный тест (SPRT) у порога `cut` заявленного грейда:**
- Гипотезы: θ₀ = cut − 0.7 и θ₁ = cut + 0.7 (δ = 0.7 подобрана по eval, [ADR-030](decisions.md#adr-030-параметры-sprt-бонуса-честности-и-тревоги-утечки-по-eval)).
- После каждого ответа (кроме пилотных):
  ```
  LLR += y·ln(P₁/P₀) + (1 − y)·ln((1 − P₁)/(1 − P₀))
  ```
- Остановка при α = β = 0.1:
  - LLR ≥ +2.197 → **прошёл**;
  - LLR ≤ −2.197 → **не прошёл**.
- Минимум 10 оцениваемых заданий, максимум 24. На максимуме решение по EAP θ относительно `cut` с пометкой «низкая уверенность». Широкая зона безразличия (±0.7) компенсируется минимумом 10: SPRT не останавливает тест на 4–6 удачных ответах.

**Бонусный этап.** Запускается, если кандидат прошёл за ≤ 10 заданий и θ ≥ cut_следующего (отступ `margin` = 0). Это до 10 заданий с тем же правилом SPRT у порога следующего грейда. Прежний мягкий допуск (θ ≥ cut_следующего − 0.5, до 6 заданий) давал около половины завышений грейда и основной выигрыш «знающих» утёкшие варианты (ADR-030). Прошёл — предложение повышения, кандидат принимает его сам.

**Правила грейда:**
- Подтверждение действует 12 месяцев.
- Смена грейда — не чаще раза в 90 дней.
- Повтор того же грейда после неудачи — через 30 дней.
- После неудачи одна попытка на грейд ниже доступна сразу.
- Грейд принудительно не понижается.
- Нарушение кулдауна → `409 cooldown` с датой следующей попытки.

## 6. Ранжирование заданий: какое задание дать следующим

Прозрачная процедура в три шага, без «чёрных ящиков».

**1. Секция.** План теста — это доли типов навыков (с поправкой на грейд) × навыки профессии внутри типа:

| Тип | Junior | Middle | Senior |
|---|---|---|---|
| Фундамент | 35 % | 25 % | 20 % |
| Хард | 40 % | 35 % | 25 % |
| Мышление | 10 % | 20 % | 30 % |
| Бизнес | 5 % | 10 % | 15 % |
| Софт | 5 % | 5 % | 5 % |
| Учиться | 5 % | 5 % | 5 % |

На шаге `k` берётся секция с наибольшим дефицитом: `доля · (k + 1) − выдано_в_секции`.

**2. Кандидаты в секции** — семейства, которые одновременно:
- имеют статус `active`;
- подходят по навыку секции;
- имеют уровень в пределах заявленного грейда ±1;
- не показывались этому кандидату 90 дней;
- имеют экспозицию за 7 дней < 30 % тестов.

**3. Счёт и выбор:**

```
score(f) = P·(1 − P) · (1 − 0.3·ai_solvable),   P = σ(θ_target − b_f)
θ_target = cut (основной этап) или cut_следующего (бонусный)
```

Из топ-3 по счёту выбор равновероятный, сид — от попытки. Первый множитель — информативность задания у порога: лучше всего различают задания со сложностью около порога. Второй мягко уводит от заданий, которые легко решает ИИ.

**План по вакансии** — та же функция `build_plan(skill_weights, grade)`, только веса навыков берутся из вакансии, а не из профессии.

**Пилотные слоты:**
- 2 скрытые позиции в случайных местах после 3-го задания;
- семейство для пилота: статус `pilot`, секции профессии, **наименьшее `n`**, при равенстве случайно;
- на θ и LLR не влияет.

## 7. Жизненный цикл семейства и калибровка

```
draft ─ автопроверка ─► pilot ─ пороги + админ ─► active ─ тревога ─► quarantine ─► retired
```

**Калибровка.** После завершения попытки по финальному θ (не по промежуточному):

```
b ← b + K·(P(θ, b) − y),   K = max(0.05, 0.5/√(1 + n))
```

У якорных семейств (`anchor`, около 10 % банка) `K = 0`: они держат шкалу.

- Калибруются все отвеченные семейства попытки, включая пилотные; `n += 1` у всех, у якорей тоже. θ попытки считается до калибровки, по `b` на момент ответа.
- θ по типам до записи грейда хранится в `attempts.plan.theta_by_type`. Код — `app/assessment/psychometrics.py` (формулы), `psychometrics_db.py` (попытка и банк); параметры — `scoring.yaml`: `assessment.eap`, `assessment.calibration`.

**Пороги допуска** `pilot → active`. Все условия плюс кнопка админа:
- n ≥ 30;
- точечно-бисериальная корреляция `r_pb` (score × финальный θ) ≥ 0.2;
- |b| ≤ 3;
- разброс доли верных по группам сидов ≤ 0.15;
- разница остатков «с ФСП / без ФСП» ≤ 0.1 (простая проверка перекоса, DIF).

**Тревоги → `quarantine`** (автоматически, потом решает админ):
- `r_pb < 0.05` при n ≥ 50;
- средний остаток `y − P(θ, b)` за последние 50 ответов вырос на 0.2 и больше относительно предыдущих (утечка). Остаток, а не доля верных: если задание стали решать более сильные кандидаты, доля верных растёт, а остаток — нет (ADR-030);
- 3 апелляции.

При выводе семейства θ затронутых попыток пересчитываются (ответы хранятся). Грейд меняется, только если изменилось решение SPRT, и кандидат получает уведомление.

**Офлайн-конвейер LLM (E26-4, `app/assessment/llm_bank.py`, `make assessment-llm-bank [ARGS=…]`).** Заказ (навык × `kind` × уровень) → генератор ml-api (`POST /v1/families/generate`) → форма `FamilySpec` → навык есть в справочнике → ключ генератора или черновик (`/v1/families/key-draft`) → автопроверка конструктора на 200 сидах → `families` (`source = llm`, `draft`, `key_status = draft`, slug `llm-<sha256 формы без title>` — повтор не дублирует). Отбраковка: `kind_mismatch`, `schema`, `unknown_skill`, `duplicate`, `no_key`, `autocheck`. Второе мнение не отбраковывает, а пишется в `spec.llm.flags` для админа: `key_draft_disagrees` (черновик ключа ≠ ключу генератора), `key_from_draft`, `key_doubtful` (и черновик против, и решатель набрал 0). Дальше — как у конструктора: ключ утверждает админ (`POST /admin/families/{id}/key`, `author` = генератор), в пилот — `POST /admin/families/{id}/pilot`. **`ai_solvable`** — прогон нашей LLM как кандидата (`POST /v1/families/solve`): средний `score` семейства на `k` = 5 вариантах со своими сидами (не боевыми), для всех не-`open` семейств в `draft`/`pilot`/`active`; повтор перезаписывает. LLM недоступна (`LLM_ENABLED=false`, нет `ML_API_URL`, ошибка ml-api) — ничего не предлагается, `ai_solvable` не меняется. Запросы идут по одному (одна GPU). ## 8. Честность прохождения

Индекс `I` начинается с 1 и снижается за сигналы:

| Сигнал | Штраф |
|---|---|
| Верный ответ на нелёгкое задание (θ − b < 0.5, т.е. P < 0.62) быстрее 0.3 × медианы времени семейства | −0.15 за каждый |
| Уход со вкладки > 10 с, затем верный ответ | −0.15 за каждый, максимум −0.45 |
| Person-fit lz < −2 | −0.2 |
| Совпадение «невозможных» неверных ответов с другими кандидатами | −0.3 |

«Нелёгкое» (θ − b < 0.5) считается по опорному θ — EAP без «быстрых» ответов: иначе списанные верные ответы завышают θ и прячут сами себя. Person-fit — по итоговому θ. Таймер задания — p95 времени ответа семейства (не меньше 15 с; при < 20 ответах — таймер семейства).

При `I < 0.6` результат помечается «требует подтверждения»: доверие ограничено ●●○○, сила профиля × 0.8. Пометку снимает пересдача или ФСП. Без банов, без камеры.

**Валидация на синтетике (E27-1).** `make eval-assessment [SEED=42]` → `reports/eval-assessment/report.{md,json}` (код — `tools/eval_assessment/`). Симулятор повторяет поток попытки (§5–6) на чистых функциях `selection`, `sprt`, `psychometrics`, `integrity`, `lifecycle` без БД; истинные θ и `b` — своя модель. Фазы: два пути на кандидата с разными вариантами (точность грейда, κ, длина, калибровка, `r_pb`, экспозиция, детектор честности на 10 % «списывающих»), фиксированная длина (r(θ̂, θ)), утечка 20 % семейств для 30 % кандидатов, LLM-«кандидат» (симуляция по `ai_solvable`; настоящая модель — E26-4). Пилоты не моделируются. Цели — [metrics.md §9.1](metrics.md#91-сразу-после-кода-без-пользователей). Параметры SPRT, бонуса, честности и тревоги утечки подобраны по этому отчёту (ADR-030). Сверх целей отчёт показывает точность при фиксированном отступе 0.5 от порогов, долю завышенных грейдов и прирост завышения у «знающих» над фоном.

## 9. Ранжирование кандидатов

**Сила профиля** `strength ∈ [0, 1]` — внутри категории:

```
strength = (0.5·T + 0.2·F + 0.15·S + 0.1·R + 0.05·C) · (I < 0.6 ? 0.8 : 1)
```

| Слагаемое | Что это | Как считается |
|---|---|---|
| T | Положение θ внутри полосы грейда | clamp((θ − cut_g) / (cut_{g+1} − cut_g), 0, 1); у Senior ширина полосы 1.0 |
| F | ФСП | Существующая сила ФСП-доказательств (`graph/fsp_strength.py`) ∈ [0, 1]; без ФСП — 0, без штрафа |
| S | Подтверждённые навыки | Среднее доверие по навыкам потребности (или топ-навыкам профессии) из графа |
| R | Свежесть | exp(−дней_с_последнего_теста_или_задания / 180) |
| C | Полнота профиля | Доля заполненных полей |

**Потребность → категории:**
- `affinity(prof) = Σ_s min(w_need(s), w_prof(s)) / Σ_s w_need(s)`;
- показываем профессии с affinity ≥ 0.4, грейд из потребности, число кандидатов, медиану ожиданий, долю с ФСП.

**Выдача внутри категории:**

```
rank = 0.6·match + 0.4·strength
```

`match` — существующий скоринг E7-1 (покрытие навыков с доверием, вилка, формат, смысловое сходство). Объяснение — топ-3 слагаемых с наибольшим вкладом плюс «заявлено vs подтверждено».

Сделано в E25-1 (регулярные задания, `tasks.py`, `tasks_router.py`). Работодатель (роль `employer`, нужна компания, чужое → 404): `POST /employer/tasks` `{family_id, profession, grade, title?, period_days 7–14}` — черновик из своего задания конструктора (E30-1; `open` — только своё, рубрика копируется в задание) или семейства банка (`pilot`/`active`); `GET /employer/tasks`, `GET /employer/tasks/{id}` (счётчики `submissions`, `scored`), `POST /employer/tasks/{id}/publish` (рассылка), `POST /employer/tasks/{id}/close`, `GET /employer/tasks/{id}/submissions` (только `pseudo_id` и `invite_url` = `/employer/offers/new?candidate=<pseudo_id>&source=regular_task`), `PUT /employer/tasks/{id}/submissions/{sid}/score` `{marks: [bool]}` — рубрика-чеклист `open`, балл — доля, `scored_by = employer` (`409 not_open_task` у остальных, `422 invalid_marks`). Публикация: получатели — `category_members(profession, grade)` ∩ `consents.has_consent(profile_publication)` (blocks.md §4.5); событие `regular_task.published` в outbox (уведомление — блок 2, E9-6); повтор до конца `period_days` ничего не делает (`delivered: false`), после — новый `round` (новый вариант и новый ответ у кандидата). Кандидат: `GET /assessment/tasks` — открытые задания его действующих категорий (без согласия — пусто), `GET /assessment/tasks/{id}` — вариант без ключа и рубрики, `POST /assessment/tasks/{id}/answer` `{answer}` — один ответ на раунд, повтор возвращает принятый; кодовые и спецификационные типы оцениваются сразу (`auto`), `open` ждёт работодателя. Ответ не идёт в θ; `last_activity_at` учитывает `task_submissions` (свежесть R). Черновик оценки `open` от LLM (`llm_draft`) пока не сделан: без LLM работает чеклист.

Сделано в E24-2 («Объясни ответ», `explain.py`): `POST /assessment/attempts/{id}/responses/{response_id}/explain` `{self_reason?}` (тело необязательно). Попытка идёт — `409 attempt_active` (ключ и разбор не раскрываются), ответа не было — `409 not_answered`, чужая попытка или ответ из другой попытки — `404`, лимит — 30 запросов в час на кандидата (`429`). Причина считается только правилами по заданию, ответу, баллу и времени: `correct`, `skipped`, `rushed` (балл 0 и ответ быстрее 10 % лимита), `misconception` (`choice`), `calc_error`, `off_by_one`, `order_of_magnitude`, `close_estimate`, `wrong_place`, `partial`, `order_mistake`, `suboptimal_action`, `chain_step` (в `detail` — номер шага), `knowledge_gap`. Для `misconception` берётся заблуждение из карточки навыка (`misconceptions[seed mod n]`, детерминированно). Текст: при `LLM_ENABLED` и `ML_API_URL` — ml-api `POST /v1/assessment/explain` (причина и заблуждение уже даны, LLM только формулирует; в запросе условие задания без ключа и без ответа кандидата), иначе или при сбое — шаблон (`source = template`). Правильный ответ и ключ не показываются никогда. `self_reason` (`misread | rushed | calc_error | knowledge_gap | guess | technical`) — самооценка кандидата, нигде не хранится; в ответе `self_reason_matches` — совпала ли она с причиной по правилам. В `GET /assessment/attempts/{id}` у завершённой попытки в `result.answers` — `{response_id, seq, skill, score}` оцениваемых ответов (без ключей): из них UI берёт `response_id` для объяснения. Свободный текст кандидата не принимается (оценка текста LLM или работодателем не сделана: ПДн-риск, нет хранилища).
