# Работа двумя блоками (v2)

> **Обязательно к прочтению** каждому агенту и человеку перед любой задачей из [plan.md §4.2](plan.md#42-очередь-v2-два-блока). Документ задаёт единый стандарт для двух параллельных потоков работ: кто чем владеет, что лежит на стыке и в каком виде, как менять общие файлы, как сливать ветки. Цель — чтобы блоки не ждали друг друга и сливались почти без конфликтов.
>
> Очередь задач с зависимостями и статусами — [plan.md §4.2](plan.md#42-очередь-v2-два-блока). Описания задач — [backlog.md](backlog.md). Технический дизайн теста и подбора — [assessment.md](../architecture/assessment.md). Если этот документ расходится с другими, **на стыке блоков прав этот документ**, внутри блока — профильный документ из `docs/architecture/`.

## 0. Коротко: 12 правил для агента

1. **Узнай свой блок.** Он указан в разделе очереди, откуда взята задача: `4.2.0` — этап 0, `4.2.1` — блок 1, `4.2.2` — блок 2, `4.2.3` — стыковка. Работай только на ветке своего блока (§7).
2. **Правь только свою зону** (§3). Чужой код можно читать и вызывать, но только через публичный `service.py` модуля, контракт из `packages/contracts` или маршрут фронта из `routes.ts`.
3. **Стык — только по §4.** Всё, чем блоки обмениваются, описано в §4 вплоть до полей и сигнатур. Не придумывай свою форму данных для стыка, не дублируй чужую логику у себя.
4. **Чужого кода ещё нет — работай на заглушке из этапа 0** (§4.11). Не жди другой блок и не пиши его задачу за него.
5. **Нужно что-то от другого блока, чего нет в §4** — это «заявка на стык» (§9). Сам в чужую зону не лезешь.
6. **Общие файлы** (`main.py`, `models.py`, реестры событий, `routes.ts`, `App.tsx`, миграции, `plan.md`, документы) правишь только по правилам §5: в своей секции между маркерами, добавлением строк, без переписывания чужого.
7. **Миграции:** ID с префиксом блока (`b1_…`, `b2_…`), меняешь только таблицы своей зоны (§5.2).
8. **Контракты в `packages/contracts`** правишь только в файлах своего блока (§5.3). Добавлять можно, ломать нельзя.
9. **API-клиент фронта (`apps/web/src/api`) и `openapi.json` руками не мержим:** при конфликте перегенерируем (§7.5).
10. **Тексты UI** лежат в `text.ts` своей фичи, компоненты берутся из `@fsp/ui` (после Т1), цвета — из токенов (§6.4).
11. **Коммиты** — Conventional Commits с ID задачи. Scope — путь модуля, как раньше: `feat(core/assessment): E22-1 …`.
12. **В отчёте задачи** добавь строку `Стык:` — что затронуто на стыке, или «нет» (§8).

## 1. Схема работы

```
            ┌───────── Этап 0 (блок 1, ветка stage0) ─────────┐
 dev ──●────┤ контракты стыка, таблица grades, заглушки,     ├──● Т0
       │    │ каркас тестов, маршруты фронта, seed           │  │
       │    └─────────────────────────────────────────────────┘  │
       │                                                         │
       ├── block2: E19-0…E19-4 (дизайн-система, без бэкенда) ──────┤ merge dev
       │                                                         ▼
       │   block1: ядро теста ─────────────── экраны ─────── фичи ───────┐
       │                  ▲ Т1: @fsp/ui в dev                             │
       │   block2: дизайн → подбор, офферы, отклики ─── экраны ── фичи ───┤
       │                                                                  │
 dev ──●──────── Т1 ──────────── Т2 ────────────── Т3 ─────────────── Т4 ●
                дизайн          ядро через API    экраны, промежуточная  финал
```

- **Этап 0** — короткий общий фундамент: всё, что лежит на стыке, появляется в коде **до** параллельной работы. Его делает владелец блока 1, потому что стык — это результат теста. Блок 2 в это время начинает дизайн-систему: ей этап 0 не нужен.
- **Блоки** идут параллельно. Каждый работает на своей ветке и использует только контракты и заглушки этапа 0.
- **Точки стыковки Т1–Т4** (§10) — моменты, когда блоки сливаются в `dev` и проверяют, что всё сходится. Между ними можно (и полезно) подтягивать `dev` к себе.

## 2. Блоки

### Блок 1 «Кандидат и тест»
Путь кандидата от регистрации до подтверждённой категории и всё, что определяет категорию.
- Email-подтверждение, профиль `lite`, режим без LLM.
- Модель навыков: типы, профессии, карточки, рост графа навыков.
- Модуль `assessment`: опрос, движок теста (Rasch, SPRT), грейды и кулдауны, семейства заданий, «Мир», жизненный цикл семейств, конструктор, банк заданий, честность, «Объясни ответ», валидация теста.
- Регулярные задания: бэкенд и экраны, включая страницу работодателя `/employer/tasks`.
- Профиль кандидата: ручная форма, резюме, PDF, граф доказательств, «заявлено vs подтверждено» (источник данных).
- Экраны кандидата: вход и регистрация, онбординг, профиль, опрос, тест, результат, история; админ-экраны профессий, карточек, графа навыков и очереди допуска.

### Блок 2 «Работодатель, подбор и платформа»
Всё, что происходит с уже категоризированным кандидатом, плюс общая витрина.
- Дизайн-система `@fsp/ui`, каркас приложения, редизайн экранов работодателя, офферов кандидата и лендинга.
- Обязательные сущности ТЗ: приглашение без вакансии, отклики, контакты компании, согласие `profile_publication`, OIDC-мок ФСП, OpenAPI.
- Подбор: категория в поиске, сила профиля и `rank`, потребность → категории → кандидаты, шорт-лист, подстройка выдачи, LLM-разбор запроса, навигатор и uplift.
- ФСП (вебхук, команды, связи, демо-кнопки), Telegram-бот целиком, бейджи и Open Badge.
- Метрики и аналитика: каталог, события подбора, онлайн-метрики, трекинг, живые прогоны, дашборд ФСП, модерация, нагрузка, валидация подбора.

### Стыковка (вместе, после Т3–Т4)
E29-3, E14-6, E31-3, E31-5, E14-4, E19-15, E27-4, E15-4. Эти задачи по смыслу требуют обоих блоков.

**Объём:** в блоке 1 — 5 задач этапа 0 и 46 своих, в блоке 2 — 53. Почти все тяжёлые задачи (Opus) в блоке 1, мелкие (Haiku) в основном в блоке 2.

**Разделённые задачи** (половины `a` и `b` — §12): E19-11, E19-16, E20-7, E20-9, E31-2, E13-1, E13-4.

## 4. Контракты на стыке

Это **единственные** точки соприкосновения блоков. Этап 0 реализует их кодом, дальше они заморожены (изменения — §9). Б1 владеет реализацией, Б2 — потребитель.

### 4.1. Словарь: профессии, грейды, типы навыков

Файл `packages/contracts/src/fsp_contracts/assessment.py` (владелец — этап 0, затем Б1):

```python
from enum import StrEnum
from typing import Annotated
from pydantic import Field


class SkillType(StrEnum):
    fundamental = "fundamental"  # фундамент
    hard = "hard"  # хард
    thinking = "thinking"  # инженерное мышление
    business = "business"  # бизнес
    soft = "soft"  # софт
    experience = "experience"  # опыт («учиться»)


class TestGrade(StrEnum):
    """Грейды v2. Значения совпадают с `enums.Grade`, другие грейды v2 не использует."""

    junior = "junior"
    middle = "middle"
    senior = "senior"


TEST_GRADE_ORDER: tuple[TestGrade, ...] = (TestGrade.junior, TestGrade.middle, TestGrade.senior)

# Профессия — данные (создаёт админ), не enum. Slug из data/taxonomy/roles.yaml.
ProfessionSlug = Annotated[str, Field(pattern=r"^[a-z][a-z0-9_]{1,31}$")]
```

- **Профессии MVP** (ADR-025, уточнено ADR-027 п. 1): `backend`, `frontend` с полным покрытием банка + `ai_engineer` как витрина (добавляет E21-1, Б1), каждая × `junior`/`middle`/`senior`. `ml`, `mobile`, `devops`, `qa` остаются в `roles.yaml` как данные, но скрыты в опросе и UI (флаг `active`, E36-2): код не должен на них рассчитывать, но и ломаться на них не должен (старые грейды и seed по `ml` читаются как раньше). Тип `ProfessionSlug` не меняется.
- `enums.RoleSlug` и `enums.Grade` остаются для старых полей (резюме, вакансии). Новые поля v2 используют `ProfessionSlug` и `TestGrade`.
- **Категория** — пара `(profession, grade)`. В URL и ключах записывается как `backend/middle`, в логах и аналитике — как `backend.middle`.

### 4.2. Таблица `grades` — главный стык

Создаёт этап 0 (миграция `s0_01_grades`). **Пишет только Б1** (E22-4, и seed через `seed_grade`), **Б2 только читает** через сервис из §4.3. Прямой SQL из Б2 к этой таблице запрещён.

| Поле | Тип | Смысл |
|---|---|---|
| `candidate_id` | uuid, FK `candidates.user_id` | |
| `profession` | text | `ProfessionSlug` |
| `grade` | text | `TestGrade` — текущий подтверждённый грейд |
| `theta` | float | θ на общей шкале (cut: junior −1.0, middle 0.0, senior 1.0) |
| `se` | float null | Стандартная ошибка |
| `band_position` | float | T ∈ [0, 1] — положение θ в полосе грейда (assessment.md §9). Считает Б1 |
| `theta_by_type` | json | `{SkillType: θ}` |
| `integrity` | float | Индекс честности I ∈ [0, 1], по умолчанию 1.0 |
| `needs_confirmation` | bool | I < 0.6 → «требует подтверждения» |
| `low_confidence` | bool | Решение принято на максимуме заданий |
| `source` | text | `test` (настоящий тест) или `seed` (демо и тесты) |
| `attempt_id` | uuid null | Попытка, давшая грейд. FK добавит Б1, когда появятся `attempts` |
| `confirmed_at`, `valid_until`, `next_change_at` | timestamptz | Подтверждение, срок (12 мес.), ближайшая смена (кулдаун) |
| `updated_at` | timestamptz | |

Ключ — `(candidate_id, profession)`: один текущий грейд на профессию. История хранится в `attempts` (Б1). Неудачная попытка строку не меняет: грейд принудительно не понижается.

### 4.3. Публичное API `app/assessment/service.py` для блока 2

DTO лежат в `fsp_contracts.assessment`:

```python
class CategoryRef(BaseModel):
    profession: ProfessionSlug
    grade: TestGrade


class CandidateGrade(BaseModel):
    candidate_id: UUID
    profession: ProfessionSlug
    grade: TestGrade
    theta: float
    se: float | None = None
    band_position: float  # T ∈ [0, 1]
    theta_by_type: dict[SkillType, float] = {}
    integrity: float = 1.0
    needs_confirmation: bool = False
    low_confidence: bool = False
    source: Literal["test", "seed"]
    attempt_id: UUID | None = None
    confirmed_at: datetime
    valid_until: datetime
    next_change_at: datetime
    mode: Literal["standard", "express"] = "standard"  # ADR-025, E32-4a: метка «экспресс»


class DeclaredGrade(BaseModel):  # ADR-025: заявленный в опросе, без действующего подтверждения
    candidate_id: UUID
    profession: ProfessionSlug
    grade: TestGrade
    declared_at: datetime  # дата опроса


class ClaimedVsConfirmed(BaseModel):
    profession: ProfessionSlug
    declared_grade: TestGrade | None  # последний опрос
    resume_grade: str | None  # из резюме (старая шкала enums.Grade), только «заявлено»
    confirmed_grade: TestGrade | None  # из grades
    status: Literal["confirmed", "overclaimed", "underclaimed", "unconfirmed"]


class ProfessionInfo(BaseModel):
    slug: ProfessionSlug
    title: str
    skill_weights: dict[
        str, float
    ]  # slug навыка → вес 0..1 («насколько типичен», как в roles.yaml); не нормирован
    skill_types: dict[str, SkillType] = {}  # заполняет E21-1
```

Сигнатуры заморожены. Все функции асинхронные, первый аргумент — `session: AsyncSession`:

| Функция | Возвращает | Семантика |
|---|---|---|
| `get_grades(session, candidate_id)` | `list[CandidateGrade]` | Только действующие грейды (`valid_until > now()`) |
| `get_grades_many(session, candidate_ids)` | `dict[UUID, list[CandidateGrade]]` | То же пачкой, для выдачи без N+1. Отсутствующих ключей нет — пустой список |
| `get_grade(session, candidate_id, profession)` | `CandidateGrade \| None` | Действующий грейд по профессии |
| `category_members(session, profession, grade)` | `list[UUID]` | Кандидаты с действующим грейдом ровно `grade`. **Без учёта согласий**: видимость фильтрует Б2 |
| `category_counts(session)` | `dict[tuple[str, str], int]` | `(profession, grade) → число` действующих грейдов, без учёта согласий |
| `claimed_vs_confirmed(session, candidate_id)` | `list[ClaimedVsConfirmed]` | По каждой профессии из опросов или грейдов |
| `last_activity_at(session, candidate_id)` | `datetime \| None` | Последний завершённый тест или регулярное задание — для свежести R |
| `seed_grade(session, candidate_id, profession, grade, theta, *, integrity=1.0, needs_confirmation=False, now=None)` | `CandidateGrade` | **Только seed и тесты.** Upsert с `source="seed"` + событие `candidate.category.changed` в outbox |
| `declared_grades_many(session, candidate_ids)` | `dict[UUID, list[DeclaredGrade]]` | ADR-025. Заявленный грейд из последнего опроса по профессии, где **нет** действующего грейда. Каждый запрошенный кандидат есть в словаре (пусто — `[]`). Без учёта согласий |
| `declared_members(session, profession, grade)` | `list[UUID]` | ADR-025. Кандидаты, заявившие ровно `grade` и не подтверждённые по профессии. Без учёта согласий |
| `declared_counts(session)` | `dict[tuple[str, str], int]` | ADR-025. `(profession, grade) → число` неподтверждённых заявленных. Не пересекается с `category_counts` |

`status` в `ClaimedVsConfirmed`:
- `confirmed` — `confirmed_grade` есть и равен заявленному или заявленного нет;
- `overclaimed` — заявлен выше подтверждённого;
- `underclaimed` — заявлен ниже;
- `unconfirmed` — подтверждённого нет.

Из `taxonomy/service.py` (владелец Б1):

| Функция | Возвращает | Семантика |
|---|---|---|
| `list_professions(session)` | `list[ProfessionInfo]` | Профессии и веса навыков. Этап 0 читает существующие роли и веса, E21-1 добавляет типы и `ai_engineer`, не меняя сигнатуру |

**Что считает Б2 из этих данных** (assessment.md §9): T = `band_position`; множитель честности = 0.8, если `needs_confirmation`; R = exp(−дней с `last_activity_at` / 180), при `None` — 0; F — из `graph/fsp_strength.py` (зона Б2, v2 по результативности — E32-2); S — из существующих функций `graph.service` (только чтение); C — из `candidates.service`. **Неподтверждённый (заявленный) грейд** (ADR-025): T = 0, множитель 0.5 ко всей силе, метка «не подтверждён»; выдаётся только при выключенном фильтре «только подтверждённые» (по умолчанию включён). `mode = express` — метка «экспресс» в карточке, формула та же.

Отдельного события при сохранении опроса нет: заявленные грейды Б2 читает при запросе выдачи.

### 4.4. События (outbox → RabbitMQ `events`)

Регистрирует этап 0 в `fsp_contracts/assessment.py`, словарь `ASSESSMENT_EVENTS` подключается в `EVENTS` (§5.3). **Производитель — Б1** (и `seed_grade`), потребители — Б2 (`matching`, бот, аналитика).

### 4.5. Видимость кандидата

- **Кандидат попадает в выдачу работодателю, только если выполнено всё:** есть действующий грейд (`get_grades` не пуст) **или** заявленный грейд (`declared_grades_many`, ADR-025; только при выключенном фильтре «только подтверждённые», с меткой «не подтверждён»), есть согласие `profile_publication` и не скрыт статусом поиска. Проверяет **Б2** в `matching`.
- `ConsentType.profile_publication` добавляет этап 0. Экран согласий (Б1) берёт список типов из API, отдельной правки ему не нужно.
- Б1 тоже учитывает это согласие: рассылка регулярных заданий (E25-1) идёт только кандидатам с `profile_publication`. Проверка — через `consents.service.has_consent`.
- **Поля карточки работодателю** (ADR-027 п. 3). Контакты — только после принятия приглашения или отклика кандидата (как сейчас, `contact_reveals`). ФИО — только если кандидат разрешил (по умолчанию нет). Опыт и места работы — по умолчанию видны, кандидат может скрыть. Достижения ФСП — по умолчанию видны. Регион — по настройке. Настройки, их API и событие изменения делает **Б1** (E36-4); имена полей и события Б1 записывает в этот раздел и в журнал §13.1. Карточку по настройкам собирает **Б2** (E36-5) только через публичную функцию Б1, без чтения таблиц Б1. До E36-4 действует прежнее правило: карточка без ФИО и контактов.

## 5. Общие файлы: как не конфликтовать

**Общий принцип:** общий файл заранее разбит на секции блоков маркерами. Блок пишет только внутри своей секции и только добавляет строки. Конфликт на маркерах решается правилом «оставить обе стороны».

### 5.1. Регистрационные файлы core

Этап 0 расставляет маркеры в `main.py`, `models.py`, `worker.py`, `scheduler.py`, `config.py` и в регистрации роутеров `services/ml`:

```python
# >>> block1 (assessment, taxonomy, identity, candidates, graph, resumes)
from app.assessment.router import router as assessment_router
# <<< block1
# >>> block2 (matching, offers, vacancies, companies, consents, fsp, telegram, analytics)
# <<< block2
```

- Новый роутер, модуль моделей, подписка, задача расписания, настройка — **одна строка внутри своей секции**.
- Строки вне секций (существующий код) не трогаем.
- Настройки в `config.py` получают префикс по смыслу (`ASSESSMENT_*`, `MATCHING_*`) и значение по умолчанию, чтобы сервис стартовал без `.env`.

### 5.2. Миграции Alembic

- **ID ревизии и имя файла** с префиксом:
  - этап 0 — `s0_NN_<имя>`;
  - блок 1 — `b1_NN_<имя>`;
  - блок 2 — `b2_NN_<имя>`.

  Пример: файл `b1_03_attempts.py`, `revision = "b1_03"`. Нумерация внутри блока сквозная, с 01.
- Миграция меняет только таблицы своей зоны (§3). Колонка в чужой таблице — заявка (§9).
- **Цепочка внутри блока линейная.** Первая миграция блока ссылается на голову `dev` на момент старта (`s0_NN`).
- **При слиянии в `dev`** (§7.3): если в `dev` появились миграции другого блока, первая ещё не слитая миграция твоего блока перецепляется: `down_revision` = текущая голова `dev`. Это единственная разрешённая правка уже написанной миграции. Проверка: `uv run alembic -c services/core/alembic.ini heads` → ровно одна голова, затем `uv run pytest -q services/core/tests/test_migrations.py`.
- Данные не удаляем; `downgrade` обязателен.

### 5.3. `packages/contracts`

| Файл | Владелец |
|---|---|
| `assessment.py`, `analytics_assessment.py` | Б1 (создаёт этап 0) |
| `hiring.py`, `analytics_hiring.py` | Б2 (создаёт этап 0, пустые словари `HIRING_EVENTS`, `HIRING_ANALYTICS_EVENTS`) |
| `events.py` | Существующие классы — по домену: `candidate.*`, `resume.*`, `evidence.*`, `skills.*`, `taxonomy.*`, `ml.*` — Б1; `vacancy.*`, `offer.*`, `matches.*`, `fsp.*`, `category.disputed` — Б2. **Новые события v2 сюда не добавляются:** только в `assessment.py` или `hiring.py`. Строки `**ASSESSMENT_EVENTS, **HIRING_EVENTS` в конце `EVENTS` ставит этап 0 |
| `enums.py` | Добавлять значения в существующий enum может владелец его домена (`EvidenceSource`, `SkillKind`, `SkillStatus` — Б1; `OfferStatus`, `DeclineReason`, `ConsentType`, `WorkFormat`, `SearchStatus` — Б2). Новые enum'ы — только в файл своего блока |
| `ui.py` (SSE), `notify.py` (бот) | Б2. Нужен новый тип SSE или уведомление для Б1 — заявка; до её выполнения Б1 обходится без него |
| `analytics.py` | Б2. Подключение словарей обоих файлов делает этап 0 |
| `commands.py`, `ml.py`, `fsp.py`, `envelope.py`, `registry.py` | `ml.py` — Б1, `fsp.py` — Б2, остальные — только по заявке |

**Правила изменения контракта:**
- **Совместимое изменение** — новое необязательное поле со значением по умолчанию, новое событие, новый DTO. Владелец файла делает его сам, в том же коммите обновляет документ (`messaging.md` или `assessment.md`) и пишет строку в журнал стыков (§13), если изменение видно другому блоку.
- **Ломающее изменение** — удаление или переименование поля, смена типа или смысла. Только новое имя или `schema_version`, и только по заявке с согласия людей.
- На каждую модель стыка — контрактный тест в `packages/contracts/tests/` (пример payload ↔ модель).

### 5.4. `apps/web/src/app/routes.ts` и `App.tsx`

- `routes.ts`: этап 0 добавляет записи v2 с `owner: "b1" | "b2"` и `nav?: boolean`. Блок меняет только записи со своим `owner` и добавляет новые в свою секцию маркеров `// >>> block1` … `// <<< block1`.

- Порядок маршрутов не важен: конкретные пути (`/me/assessment/history`) объявлены раньше параметрических, и это проверяет тест `routes.test.ts` из этапа 0.

## 6. Единые стандарты кода

Действуют для обоих блоков, дополняют `AGENTS.md`.

### 6.1. Бэкенд

- **Модуль core** = `models.py` (таблицы), `schemas.py` (pydantic-модели API), `service.py` (публичные функции модуля), `router.py` (HTTP), `handlers.py` (подписки). Другие модули импортируют **только** `service.py` и `fsp_contracts`.
- **Функции сервиса** асинхронные, первым аргументом `session: AsyncSession`. **Публичные функции, которые вызывает другой блок, не делают `commit`:** транзакцией управляет вызывающий (роутер или обработчик). Событие пишется в outbox в той же транзакции.
- **Типы:** деньги — `int` ₽/мес; время — `datetime` с `tz=UTC`; ID — `UUID`; slug — строки латиницей. Грейды v2 — `TestGrade`, профессии — `ProfessionSlug`.
- **Работодатель** видит кандидата только по `pseudo_id`; `candidate_id` в ответы для `E` не попадает.
- **Пагинация** курсорная (`api.md` §1). Список без пагинации — только справочники.
- **Идемпотентность:** повтор `POST` с тем же `response_id` или `Idempotency-Key` возвращает исходный результат; повторная доставка события ничего не меняет.
- **Конфиг формул** — `data/scoring.yaml`, в разделе своего блока. Числа в коде — только как значения по умолчанию.

### 6.2. События

- Имя `<домен>.<сущность>.<глагол в прошедшем>`: `assessment.attempt.finished`.
- Payload без ПДн, только ID и числа.
- Каждый обработчик — с inbox и проверкой версии.

### 6.3. Тесты (минимум для задачи)

- Формулы — юнит-тесты на числах из документа.
- Эндпоинт — успех, чужой ресурс → 404, нет прав → 403 или 401, ошибки валидации с машинным `code`.
- Обработчик — повторная доставка не меняет результат.
- Потребитель стыка (Б2) тестирует на `make_grade`, а не на моках функций Б1.
- Запуск: `uv run pytest -q <путь>`, вывод через `| tail -n 30`. Линтер: `make lint`.

### 6.4. Фронт

- **После Т1** — только компоненты `@fsp/ui` и токены. До Т1 Б2 строит `@fsp/ui`, а Б1 UI не делает.
- Тексты на русском — в `features/<фича>/text.ts`, перечисления — в `shared/i18n`. Недостающее значение в `shared/i18n` — заявка; пока её не выполнили, локальный словарь в своей фиче.
- Данные — только через сгенерированные orval-хуки. Если эндпоинта ещё нет в клиенте, сначала эндпоинт и перегенерация.
- Каждый экран проверяется на 375 px и в тёмной теме. В отчёте указать, что проверено.
- Тест-идентификаторы: `data-testid="<фича>-<элемент>"`, например `assessment-next`.

### 6.5. Коммиты и отчёты

- `feat(core/assessment): E22-1 каркас попытки`, `fix(web/needs): E23-6 …`, `chore(plan): E22-1 ✅ <хеш>`.
- В каждом отчёте задачи (формат `AGENTS.md` «В конце задачи» и `task-auto.md`) добавляется строка: `Стык: нет | изменён <что>, журнал §13 | заявка <№>`.

## 7. Git и ветки

### 7.1. Ветки

| Ветка | Назначение | Кто пишет |
|---|---|---|
| `dev` | Интеграция. Всегда проходит `make lint` и `make test` | Только люди, слиянием |
| `stage0` | Этап 0 | Б1 (агент `/vibe 0` или человек) |
| `block1` | Блок 1 | Б1 (агент `/vibe 1` или человек) |
| `block2` | Блок 2 | Б2 (агент `/vibe 2` или человек) |
| `main` | Сдача | Люди, из `dev` на Т3 и Т4 |
| `vibe` | Очередь v1, больше не используется | — |

- Человек может работать в короткой ветке `feat/<ID>-…` от своей ветки блока и сливать её обратно в ветку блока.
- Агент никогда не сливает в `dev` или `main`, не делает `--force` и не удаляет ветки.

### 7.2. Старт

1. Этап 0: `git switch -c stage0 origin/dev` → задачи `4.2.0` → PR в `dev` → **Т0**.
2. Б2 стартует сразу: `git switch -c block2 origin/dev`, задачи E19-0…E19-4 и E19-16b (им этап 0 не нужен). После Т0 — `git merge origin/dev` в `block2`.
3. Б1 после Т0: `git switch -c block1 origin/dev`.

### 7.3. Слияние блока в `dev` (выполняет человек)

1. `git switch block<N> && git fetch && git merge origin/dev`. Чужие изменения сначала приходят к тебе.
2. Конфликты решаем по §7.5.
3. Миграции: проверить, что голова одна (§5.2).
4. `make lint && make test`. Всё зелёное — PR `block<N> → dev`, ревью вторым блоком (только стыковые файлы: §4, §5).
5. После слияния другой блок делает `git merge origin/dev` в свою ветку в течение дня.

Сливать можно в любой момент, когда у блока есть законченные задачи. **Обязательные** слияния — на точках Т1–Т4 (§10). Правило: чем чаще, тем меньше конфликты. Рекомендуем не реже раза в два дня.

### 7.4. После слияния что-то сломалось

- Падает **твой** тест из-за чужого изменения на стыке. Сверься с §4. Если отступил другой блок — заявка (§9) и `⛔ стык <№>` у задачи. Если ты — чинишь.
- Падает **чужой** тест. Не правишь, сообщаешь владельцу.

### 7.5. Разрешение конфликтов по типам файлов

| Файл | Как решать |
|---|---|
| Секции с маркерами (`main.py`, `models.py`, `routes.ts`, `App.tsx`, `Makefile`, `.env.example`) | Оставить обе стороны |
| `EVENTS`, `ANALYTICS_EVENTS`, `decisions.md` (добавление в конец) | Оставить обе стороны, проверить уникальность ключей и номеров |
| `plan.md` | Оставить обе стороны (разные разделы) |
| Миграции | Перецепить `down_revision` (§5.2) |
| `openapi.json`, `src/api/**`, lock-файлы | Перегенерировать (§5.5) |
| Файл чужой зоны | Взять версию владельца (`dev`), свои правки оформить заявкой |
| Документ по разделам | Каждый блок — свой раздел; при пересечении оставить версию владельца раздела |

## 8. Как агенту выполнять задачу

1. **Определи блок и ветку.** Блок — по разделу очереди. Убедись, что текущая ветка — ветка блока (`git branch --show-current`).
2. **Прочитай задачу** в `backlog.md`. Для половин `a` и `b`, задач `S0-*` и задач с пометкой в §12 — описание из §11–12 этого документа.
3. **Проверь зависимости по колонке «Зависит от» очереди своего блока:**
   - ID задачи — нужен статус `✅` или `🔍` **в своём разделе или в архиве v1**;
   - `Т1`, `Т2`, `Т3` — точка стыковки отмечена ✅ в таблице §10.1 плана; иначе `⛔ ждёт Т<n>`;
   - `S0` — все задачи `4.2.0` ✅.
4. **Составь список файлов, которые поменяешь,** и сверь каждый с §3. Есть файл чужой зоны:
   - это общий файл из §5 — правь по его правилу;
   - иначе — заявка (§9). Задача делается без этой части, если критерий «готово» это позволяет; не позволяет — `БЛОКЕР: стык <что нужно>`.
5. **Касаешься стыка (§4)** — используй ровно описанные имена, поля и сигнатуры. Нужно совместимое расширение своего контракта — делай по §5.3 и пиши в журнал §13.
6. **Код → тесты → `make lint` → документы своей зоны.**
7. **Коммит** на ветке блока. `plan.md` не трогаешь, статус ставит диспетчер.
8. **Отчёт** по формату `task-auto.md` + строка `Стык:`.

## 9. Заявка на стык

Когда блоку нужно что-то от другого блока, чего нет в §4: новая функция в чужом `service.py`, поле в чужой таблице, новый тип SSE или уведомления, компонент в `@fsp/ui`, правка `packages/platform`.

1. Добавь строку в журнал стыков §13 в свою секцию:
   `| <дата> | З-<блок>-<NN> | <от кого> → <кому> | <что нужно, сигнатура или поле> | <какая задача ждёт> | открыта |`.
2. Человек (утром или на синхронизации) решает: делает владелец (задача в его очередь с ID `X-<NN>`) или отказ с альтернативой.
3. До выполнения заявки — обходной путь **только в своей зоне**: локальный компонент, локальный словарь, временно скрытая часть экрана. Обходной путь, который читает чужие таблицы или дублирует чужую формулу, запрещён.
4. В режиме `/vibe` агент людей не спрашивает: пишет заявку, ставит задаче `⛔ стык З-…` и берёт следующую.
