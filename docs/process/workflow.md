## 2. Git

- `main` всегда разворачиваемый. Работа в ветках `feat/<эпик>-<кратко>`, `fix/…`, `docs/…`, `chore/…`.
- **v2 (два блока):** интеграция — `dev`, ветки блоков — `stage0`, `block1`, `block2`. Порядок слияния и разрешение конфликтов — [blocks.md §7](blocks.md#7-git-и-ветки).
- Коммиты — Conventional Commits: `feat(core/offers): лимит офферов в сутки`.
- PR маленькие (до ~400 строк диффа без сгенерированного), 1 ревьюер. Изменения `packages/contracts` и `api.md` ревьюят обе стороны контракта.
- Сгенерированный клиент фронта (`apps/web/src/api`) коммитим, проверяем в CI.
- Секреты, модели, эталоны с ПДн, `infra/snapshots/` — в `.gitignore`.

## 3. Как вести контракты

1. **Сначала контракт, потом код.** Новый эндпоинт → строка в [api.md](../architecture/api.md) и pydantic-схема в роутере. Фронт генерирует клиент по стабу (роутер может вернуть фикстуру).
2. **Межпроцессные контракты** (события и команды RabbitMQ, `ui.user.*`, `notify.telegram`, ml DTO) — только в `packages/contracts`. Ломающее изменение — новое имя или `schema_version`. AsyncAPI генерируется FastStream.
3. **ML-заглушки:** `ML_FAKE=true` → ml-api и задачи отдают фикстуры из `services/ml/fixtures/`. Фронт и бэк не ждут модели.

## 4. Код

| | Python | TypeScript |
|---|---|---|
| Форматирование / линт | ruff format, ruff check | Prettier, ESLint |
| Типы | type hints везде, mypy в мягком режиме | strict |
| Тесты | pytest; интеграционные — testcontainers (PG, Redis) | vitest, Playwright |
| Именование | `snake_case`, модули по доменам | компоненты `PascalCase`, хуки `useX` |
| Ошибки | доменные исключения → Problem Details в одном обработчике | ошибки API через общий `ProblemError` |
| Логи | structlog, без ПДн, с `request_id` | — |
| Время / деньги | UTC `datetime`, деньги `int` ₽/мес | форматтеры в `shared/lib/format` |

**Границы модулей core** (import-linter): `modules.<a>` может импортировать только `modules.<b>.service` и `modules.<b>.schemas`, но не `repo` и `models` чужого модуля.

## 5. Definition of Done

Задача готова, когда:
- [ ] код в `main`, CI зелёный;
- [ ] есть тесты на основную ветку логики и на проверку прав (если эндпоинт);
- [ ] эндпоинт виден в OpenAPI с описаниями полей и примерами;
- [ ] если менялись контракты, схемы или формулы — обновлены `api.md`, `data-model.md`, `ml.md`;
- [ ] фича работает на демо-стенде с seed-данными;
- [ ] для UI: проверено на ширине 375 px и в тёмной теме.

## 6. Ритм

- Ежедневный стендап 15 минут: вчера / сегодня / блокеры.
- Каждый вечер — деплой `main` на стенд и прогон e2e демо-сценария.
- С Д5 сквозной сценарий обязан работать каждый вечер. Регрессии демо исправляем в первую очередь.

## 7. Работа с ИИ-агентами

### 7.1. Как устроено
- **`AGENTS.md`** — единые правила для любых агентов. Claude Code, Codex и Cursor читают его сами. Файл короткий и стабильный, поэтому хорошо кешируется. Детали — по ссылкам из таблицы «Что читать под задачу».
- **`CLAUDE.md`** подключает `AGENTS.md` и добавляет особенности Claude Code.
- **`.claude/settings.json`** — разрешения на безопасные команды (меньше подтверждений) и запрет читать `.env`, модели и снапшоты.
- **`.claude/commands/`** — команды `/task <ID>`, `/contract <что>`, `/docs-sync <область>`.
- **В каждом сервисе** после создания — свой `AGENTS.md` до 40 строк: агент, работающий в `services/core`, не тянет в контекст фронт.

### 7.2. Как запускать, чтобы меньше тратить токены и лимиты

| Правило | Почему |
|---|---|
| **Одна сессия — одна задача из бэклога.** Начинай с `/task E7-1`, между задачами — `/clear` | Контекст не копится, кеш промпта работает на стабильном начале (`AGENTS.md`) |
| **Plan mode для задач больше одного файла.** Сначала план, подтверждение, потом код | Меньше переделок, а это самый дорогой расход |
| **Модель по задаче:** Sonnet — основной код; Opus — архитектура, сложная отладка, ревью контрактов; Haiku — переименования, фикстуры, поиск | Самая дорогая модель нужна в 10–20% задач |
| **Не давай читать лишнее:** сгенерированный клиент, lock-файлы, логи целиком, дампы. Тесты с `-q`, логи через `--tail 50` | Один лог на 5 тысяч строк съедает больше, чем вся задача |
| **Указывай путь, а не вставляй содержимое:** «см. `docs/architecture/matching.md` §4.1» вместо копии текста | Агент прочитает ровно нужный раздел |
| **Контракты первыми и `ML_FAKE=true`** | Агенту фронта или бэка не нужен контекст ML и чужих сервисов |
| **Параллельно — через git worktree:** у каждого человека или агента своя ветка и папка (`git worktree add ../lct-fsp-e7-1 -b feat/e7-1` или запуск Claude Code с `--worktree`) | Нет конфликтов и токенов на их разбор |
| **Сабагенты — редко.** Только широкий поиск по коду | Каждый сабагент заново читает контекст |
| **Длинная сессия** → `/compact` или новая сессия с кратким итогом прошлой | Дешевле, чем тащить всю историю |
| **Ревью** — встроенная `/code-review` по диффу перед PR, а не «перечитай весь проект» | Смотрит только изменения |
| **Следи за расходом** — `/usage` (или `/cost`) в Claude Code | Видно, какие задачи дорогие |

### 7.3. Шаблон запроса агенту (если не через `/task`)

```text
Задача <ID> из docs/process/backlog.md: <одна строка, что сделать>.
Контекст: только <раздел документа>, <раздел документа>. Остальное не читай.
Сначала план (5–10 пунктов) и жди подтверждения. Потом код и тесты (-q).
В конце: что сделано, как проверить, какие документы обновлены, вопросы.
```

### 7.4. Распределение агентов по людям
- У каждого участника свой агент в своём worktree и на своей зоне из [services.md §3](../architecture/services.md#3-владельцы).
- Изменения в `packages/contracts` идут только отдельным PR через `/contract`, ревью обеих сторон.
- Вечером, после мержа в `main`: `make demo-reset` + e2e демо-сценария.

### 7.5. Вайбкодинг по плану (`/vibe`)

**Как запустить:**
1. Открой Claude Code в папке репозитория: в терминале `claude` или вкладка Code в приложении.
2. Включи режим без подтверждений: Shift+Tab → `auto` или `accept edits` (в приложении — переключатель режима).
3. Напиши `/vibe <блок>` и иди отдыхать: `/vibe 0` — этап 0, `/vibe 1` — блок 1, `/vibe 2` — блок 2. Правила двух блоков — [blocks.md](blocks.md).

**Что происходит:**
- Диспетчер сам коммитит текущее состояние и переходит на ветку блока (`stage0`, `block1`, `block2`).
- Берёт задачи из своего раздела [plan.md §4.2](plan.md#42-очередь-v2-два-блока) по порядку и каждую отдаёт отдельному сабагенту со свежим контекстом.
- Задачи, ждущие точку стыковки (`Т0`…`Т3`), пропускает.
- Чего ещё нет (GPU, дизайн, токены, API ФСП), заменяет заглушками.
- После каждой задачи проверяет тесты и то, что не задеты файлы чужого блока, ставит статус в плане и коммитит. В чате копятся только короткие отчёты.
- `/vibe 1 10` — ограничить число задач.
- Пушит только в ветку своего блока, в `dev` и `main` не сливает.

**Утром:**
1. Журнал своего блока в [plan.md §6.1 или §6.2](plan.md#6-журнал-ночей) и журнал стыков в [blocks.md §13](blocks.md#13-журнал-стыков).
2. Задачи `🔍` проверить и отметить `✅`.
3. По задачам `⛔` прочитать причину и вернуть `⏳` или забрать себе. По заявкам на стык — решить вместе с другим блоком.
4. Слить ветку блока в `dev` по [blocks.md §7.3](blocks.md#73-слияние-блока-в-dev-выполняет-человек). На точках стыковки отметить их в плане §4.2.T.

**Если упёрлись в лимиты** — запусти `/vibe <блок>` снова после сброса: продолжит с места остановки, статусы лежат в плане. Запасной вариант без чата, который сам ждёт сброса лимитов: `tools/agents/vibe.sh <блок> 20` в `tmux`.

**Экономия:** сабагенты на Sonnet, Opus только там, где указан в очереди, Haiku на механике.
