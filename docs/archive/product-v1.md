## Коротко (актуальная выжимка)
### Одной фразой
**«Не резюме, а доказательства».** ИТ-агрегатор с обратной механикой: кандидат автоматически получает категорию по подтверждённым навыкам (ФСП, код, тесты), а работодатель сам находит его и приходит с вакансией и вилкой.

### Ядро MVP (Must)
1. Кандидат: вход (сайт + бот) → резюме → ФСП → навыки с доверием ○○○○…●●●● → автокатегория и грейд с объяснением.
2. Работодатель: компания → вакансия на профессиональном языке → поиск и карта рынка → анонимная карточка с объяснением совпадения → оффер с обязательной вилкой.
3. Оффер → push в Telegram → принять / отклонить с причиной / вопрос → контакты раскрываются после принятия.
4. Админ ФСП: справочник навыков и правила «дисциплина → навыки».

### Сильно желательно (Should)
ДНК кода по GitHub · объяснение и оспаривание категории · навигатор с соревнованиями ФСП · адаптивный тест в боте · карта рынка · поиск обычным текстом · модерация · дашборд ФСП · страница качества.

### Вау (по ресурсам)
ИИ-интервью по коду · найм команды ФСП · «новый результат ФСП → профиль обновился → push» · «что будет, если…» · бейдж «Подтверждено ФСП».

### Что изменилось после анализа
- **Mini App убран из MVP:** мобильного разработчика нет. Канал кандидата — бот + адаптивный сайт (C12 → W).
- **Граф доказательств** — центральная идея: профиль = кандидат → проверяемые факты → навыки с силой. Граф навыков растёт сам из упоминаний (ядро + конвейер с модерацией и склейкой синонимов).
- **Uplift для кандидата:** «подтверди Docker — подойдёшь под 64% больше вакансий», со способами подтверждения (тест, GitHub, соревнование ФСП).
- **Софт-навыки** без точек доверия — командные сигналы из фактов (капитан, командные выступления, траектория) с небольшим коэффициентом.
- **Рекомендации работодателю:** похожие кандидаты и подстройка выдачи под его реакции в сессии; показы логируются для будущего обучения.
- Практика больших платформ и нормы — [notes/research.md](notes/research.md).

### Демо (≈3 мин)
Аня отправляет резюме в бот → «Войти через ФСП» → значки загораются → GitHub → радар → Ольга пишет запрос текстом → чипсы → Аня в выдаче с объяснением 92% → оффер с вилкой → push в Telegram → «Принять» → навигатор → новый результат ФСП обновляет профиль на глазах. Подробно: [§18](#18-демо-питч-демонстрационные-данные).

## 1. Разбор кейса

**Задача:** веб-сервис, отраслевой агрегатор вакансий для ИТ с **обратной механикой подбора**. Соискатели **автоматически категоризируются** по **объективно подтверждаемому профилю**, работодатель сам находит категорию и выходит на конкретного кандидата **с вакансией и заработной платой**.

**Ресурсы организаторов:** данные ФСП (дисциплины, соревнования, результаты, роли, разряды), брендбук и макеты ФСП, консультации экспертов.

**Ожидаемые компетенции:** PM, бэкенд, фронтенд, DS/ML (**матчинг, разбор резюме, механизм тестирования**), UX/UI (опционально).

### Что в формулировке ключевое

| Формулировка | Продуктовое следствие |
|---|---|
| «обратная механика подбора» | Первым пишет работодатель. Главный объект витрины — кандидат, а не вакансия |
| «автоматически категоризируются» | Категорию присваивает система, а не сам кандидат. При этом её можно объяснить и оспорить |
| «объективно подтверждаемый профиль» | У каждого навыка видны источник и уровень доверия |
| «профессиональный язык» | Формализованы стек, грейд, роль в команде, формат работы |
| «с вакансией и заработной платой» | Оффер без вилки отправить нельзя |
| «автоматическое обогащение … достижениями» | Достижения ФСП появляются в профиле без ручного ввода |
| «разбор резюме, механизм тестирования» | Жюри ждёт три интеллектуальных блока: подбор, разбор резюме, проверка навыков |

### Скрытый интерес заказчика

ФСП нужна не только биржа труда, но и **популяризация спортивного программирования**. Участие в соревнованиях должно превращаться в карьерный капитал, а платформа должна **возвращать людей на соревнования**. Решение, которое замыкает этот цикл, сильнее решения, которое просто показывает данные ФСП.

## 2. Проблема и контекст рынка

### 2.1. Проблема (по кейсу)

- Универсальные площадки не говорят на языке ИТ, поэтому релевантность выдачи низкая для обеих сторон.
- Работодатель вручную разбирает сотни нерелевантных откликов силами дорогих специалистов.
- Кандидат откликается вслепую и не получает обратной связи.
- Резюме фиксирует стек и места работы, но **не подтверждает практическую компетентность**, и отбор сводится к совпадению ключевых слов.

### 2.2. Контекст (🧪 гипотезы, подкрепить источниками для питча)

- Сегмент начинающих специалистов перегрет: на одну junior-вакансию приходится много откликов, а у выпускника нет опыта, который можно было бы показать.
- Генеративный ИИ упростил написание «идеальных» резюме и сопроводительных писем, поэтому текст резюме обесценивается как сигнал и **растёт ценность проверяемых доказательств**.
- Крупные ИТ-компании уже нанимают через собственные соревнования, то есть рынок признаёт соревновательные результаты как сигнал. Но каждая компания делает это в своей закрытой воронке.

### 2.3. Ключевые инсайты

1. **Резюме — это заявление, а не доказательство.** Продукт должен превращать заявления в доказательства.
2. **У студента-олимпиадника результаты соревнований часто единственное объективное доказательство навыков.** Платформа становится мостом «соревнования → первая работа», и это главная история для ФСП.
3. **Обратная механика убирает шум.** Вместо массовых откликов приходят адресные офферы.
4. **Вилка в оффере** даёт кандидату прозрачность и отсекает несерьёзных работодателей.
5. **Данные ФСП есть только у нас.** Ни одна другая площадка не может подтверждать навыки результатами официального вида спорта.

## 3. Пользователи и персоны

### 3.1. Стейкхолдеры

| Стейкхолдер | Боль | Ценность платформы |
|---|---|---|
| Студент / олимпиадник | Нет коммерческого опыта. HR не понимает, что значит призовое место | Достижения переводятся на язык работодателя |
| Junior / Middle | Откликается вслепую, не получает ответов, отсеивается по ключевым словам | Работодатель приходит сам и с зарплатой. Есть объяснение, почему нет офферов |
| Senior | Спам от рекрутеров без вилки и под чужой стек | Анонимность, обязательная вилка, фильтры интересов |
| HR / рекрутер | Не разбирается в ИТ, отбирает по словам | Готовые категории на профессиональном языке, у каждого навыка видна степень доверия |
| Тимлид / CTO | Дорогие часы на первичные собеседования, половина кандидатов их не проходит | Предварительная проверка: на собеседование приходят уже отобранные кандидаты |
| ФСП | Нужно доказать, что спортивное программирование полезно для карьеры, и растить аудиторию | Аналитика трудоустройства, поток людей на соревнования |

### 3.2. Персоны (для дизайна и демо)

**Аня, 20 лет, студентка 3 курса.** Призёр всероссийского этапа по продуктовому программированию, капитан команды. Есть пара пет-проектов на GitHub, коммерческого опыта нет.
*Задача:* получить первую работу или стажировку, не рассылая сотни откликов. *Страх:* «моё резюме пустое, меня даже не прочитают». *Что ей даёт продукт:* достижения ФСП превращаются в подтверждённые навыки, она видит свою категорию и получает офферы.

**Дима, 26 лет, Middle Backend (Python).** 3 года опыта, открыт к предложениям, но не ищет активно.
*Задача:* узнать, сколько он стоит, и получать только релевантные предложения. *Раздражает:* рекрутеры с Java-вакансиями без вилки. *Что ему даёт продукт:* анонимность, минимальная зарплата как фильтр, офферы с вилкой в Telegram.

**Ольга, 34 года, HR в продуктовой компании (200 человек).** Закрывает 5–7 ИТ-вакансий одновременно, в технологиях разбирается поверхностно.
*Задача:* быстро собрать шорт-лист, который не завернёт тимлид. *Страх:* потратить время тимлида на неподходящих кандидатов. *Что ей даёт продукт:* поиск обычным текстом, объяснение «почему подходит», уровни доверия к навыкам.

**Игорь, 38 лет, CTO стартапа.** Нанимает сам, ценит людей, которые умеют быстро делать продукт в команде.
*Задача:* найти сильных людей, а лучше сразу сыгранную команду. *Что ему даёт продукт:* фильтр по достижениям ФСП, «ДНК кода», найм команды.

**Администратор ФСП.**
*Задача:* показать федерации и партнёрам, что участие в соревнованиях ведёт к трудоустройству, и привлекать людей на новые соревнования. *Что ему даёт продукт:* аналитика трудоустройства участников, востребованные навыки, переходы на соревнования.

### 4.4. Вывод

Ни одна площадка не объединяет **обратный найм**, **подтверждение навыков из нескольких источников, включая спортивные достижения**, и **замкнутый цикл с соревновательным движением**. Это наше УТП.

## 5. Позиционирование и ценностное предложение

### 5.1. Позиционирование

> **«Не резюме, а доказательства».**
> Платформа ФСП, где ИТ-специалиста оценивают по подтверждённым навыкам, а работодатель сам приходит с вакансией и зарплатой.

### 5.2. Ценностное предложение по сторонам

| Сторона | Ценность одной фразой | За счёт чего |
|---|---|---|
| Кандидат | «Перестань откликаться: работодатели придут к тебе с зарплатой» | Обратная механика, автокатегория, обязательная вилка, Telegram |
| Начинающий кандидат | «Твои победы — это твой опыт» | Перевод достижений ФСП в навыки и грейд |
| Работодатель | «Только проверенные кандидаты и понятно, почему они подходят» | Уровни доверия, объяснимый подбор, карта рынка |
| ФСП | «Соревнования, которые ведут к карьере» | Аналитика трудоустройства, навигатор, который ведёт на соревнования |

### 5.3. Принципы продукта

1. **Доказательства важнее заявлений.** Каждый навык показывает, откуда он взялся и насколько ему можно доверять.
2. **Прозрачность алгоритма.** Любой вывод системы (категория, грейд, совпадение) можно объяснить человеческим языком.
3. **Кандидат управляет своими данными.** Он решает, что показывать и кому, а контакты раскрываются только с его согласия.
4. **Уважение ко времени.** Никаких офферов без вилки, никакого спама, ответ в один клик.
5. **Цикл с ФСП.** Продукт всегда подсказывает, как подтвердить навык на соревновании.
6. **Профессиональный язык.** Стек, грейд, роль, формат — а не «ответственный, коммуникабельный».

## 9. Механики продукта: альтернативы и выбор

Для каждой механики: варианты, сравнение и **решение**. ✅ — в MVP, 🔁 — запасной вариант, 🚀 — вау-расширение.

### 9.1. Обратная механика: как работодатель выходит на кандидата

| Вариант | Описание | Плюсы | Минусы |
|---|---|---|---|
| A. Прямой оффер | Работодатель выбирает кандидата и отправляет вакансию с вилкой | Просто и ровно по кейсу | Риск спама |
| B. Запрос на интервью | То же, но предлагается собеседование, а не работа | Привычно рынку, мягче | По сути то же, что A |
| C. Взаимный мэтч | Обе стороны «лайкают» анонимные карточки, при взаимности открывается чат | Без спама, хорошо ложится на Telegram | Не совсем «работодатель выходит на конкретного кандидата» |
| D. «Витрина недели» | Кандидат на неделю выставляется как активно ищущий, компании присылают офферы, он выбирает лучший | Честная конкуренция за кандидата, вау | Может восприниматься как «торговля людьми» |
| E. Массовая рассылка по шорт-листу | Оффер всем кандидатам категории | Экономит время работодателя | Возвращает спам |

**Решение:** ✅ **A + B**: оффер = вакансия + вилка + сообщение. Статусы: отправлен → просмотрен → принят / отклонён с причиной / вопрос → интервью → нанят. Контакты раскрываются после принятия.
🚀 Из D берём режим «Активно ищу 7 дней»: кандидат поднимается в выдаче и получает метку «🔥 активен».

### 9.2. Разбор резюме

| Вариант | Описание | Плюсы | Минусы |
|---|---|---|---|
| A. Словари и шаблоны | Поиск известных навыков и дат в тексте | Предсказуемо | Плохо понимает опыт и проекты |
| B. Языковая модель | Модель читает резюме и заполняет структуру профиля | Понимает контекст, проекты, русский язык | Может «придумывать», нужна проверка |
| C. Гибрид | Модель заполняет структуру, а навыки сверяются со справочником | Лучшее качество и контроль | Чуть сложнее |

**Решение:** ✅ **C**. Продуктовые правила:
- навык, которого нет в справочнике, не попадает в профиль автоматически, а уходит администратору на проверку;
- навыки из резюме получают низкий уровень доверия (это заявление, а не доказательство);
- кандидат видит результат разбора и может его исправить. Исправления отмечаются как «заявлено самим».

### 9.3. Связь с ФСП

**Как подтвердить, что пользователь — именно этот участник ФСП:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Ввести ФСП-ID без проверки | Просто | Можно присвоить чужие достижения |
| B. Код подтверждения на контакт из данных ФСП | Надёжно | Зависит от того, есть ли контакты в данных ФСП |
| C. «Войти через ФСП» (единый вход) | Идеально для пользователя | Скорее всего недоступно на хакатоне |

**Как часто обновлять данные:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| При привязке | Просто | Данные устаревают |
| Регулярно (например, раз в сутки) | Актуальность | — |
| Мгновенно при новом результате | Вау: «выиграл соревнование, и профиль обновился» | Нужна поддержка со стороны ФСП |

**Решение:** ✅ **B, если данные позволяют, иначе A** с пометкой «не верифицировано» (такие достижения получают меньший вес). Данные загружаются при привязке и обновляются регулярно. 🚀 На демо — кнопка «Войти через ФСП» и сценарий «новый результат → профиль обновился → push в Telegram».

### 9.4. Перевод достижений ФСП в навыки

Дисциплины ФСП (⚠️ **ПРОВЕРИТЬ**): алгоритмическое программирование, продуктовое программирование, программирование систем информационной безопасности, программирование беспилотных авиационных систем, программирование робототехники.

| Вариант | Описание | Плюсы | Минусы |
|---|---|---|---|
| A. Таблица «дисциплина → навыки» | Каждая дисциплина подтверждает свой набор навыков | Просто, понятно, легко согласовать с экспертами | Грубо |
| B. Учёт «веса» достижения | Учитываются уровень соревнования, место относительно числа участников, роль в команде, давность | Различает победителя всероссийского этапа и участника регионального | Коэффициенты подбираются экспертно |
| C. Спортивный рейтинг | Рейтинг участника по всем соревнованиям с учётом силы соперников (как в шахматах) | Объективно, вау | Нужны полные таблицы результатов |
| D. Навыки по описанию треков | Трек «ML» на хакатоне подтверждает ML | Точнее A | Нужны описания треков |

**Решение:** ✅ **A + B**, правила редактирует администратор ФСП. 🚀 **C**, если в данных есть полные таблицы результатов. **D** для продуктовых соревнований с треками, если данные позволят.

**Черновик соответствия (согласовать с экспертами ФСП):**

| Дисциплина | Подтверждаемые навыки |
|---|---|
| Алгоритмическое | Алгоритмы, структуры данных, математика, C++ / Python |
| Продуктовое | Командная разработка, fullstack, бэкенд / фронтенд, продуктовое мышление |
| Информационная безопасность | Безопасность, пентест, сети, Linux, реверс-инжиниринг |
| Беспилотные авиационные системы | Встраиваемые системы, системы управления, компьютерное зрение, C++ / Python |
| Робототехника | Встраиваемые системы, системы управления, ROS, электроника |

Что ещё влияет:
- **роль капитана** добавляет навык «лидерство» и сигнал к грейду;
- **разряд** (⚠️ ПРОВЕРИТЬ шкалу) служит самостоятельным маркером уровня;
- **давность:** вес старых достижений постепенно снижается.

### 9.5. «ДНК кода»: анализ репозиториев

**Что анализируем:**

| Слой | Что даёт пользователю |
|---|---|
| Языки | Доля языков в коде, который написал сам кандидат |
| Технологии | Конкретные фреймворки и инструменты по файлам зависимостей и конфигурации (Docker, CI, Kubernetes…) |
| Авторство | Какая доля кода действительно написана кандидатом |
| Инженерная зрелость | Есть ли тесты, автоматическая сборка, документация, аккуратная история изменений |
| Вклад в open source | Принятые изменения в чужие проекты: сильный сигнал, потому что код приняли чужие люди |
| Краткая характеристика | Текстовое описание стиля и сильных сторон («пишет асинхронный код, слабое покрытие ошибок») |

**Признаки подозрительности (снижают доверие):**
- форк без собственных изменений;
- огромный объём кода одним изменением;
- весь объём написан за одну ночь;
- изменения сделаны не от имени кандидата;
- код совпадает с популярными шаблонами.

**Варианты глубины:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только общая информация о репозиториях | Быстро | Поверхностно, легко обмануть |
| B. Глубокий анализ всех репозиториев | Полно | Долго |
| C. Общая информация обо всех + глубокий анализ лучших 5–10 | Баланс | — |

**Решение:** ✅ **C** + все слои, кроме текстовой характеристики. 🚀 Текстовая характеристика, вклад в open source и ИИ-интервью по коду (9.9). Результат показывается как **радар**: бэкенд, фронтенд, DevOps, данные, качество кода, open source.
Продуктовое правило: до принятия оффера работодатель видит **итоги анализа, но не ссылки на репозитории**, потому что ссылки раскрывают личность. Кандидат может включить их показ сам.

### 9.6. Категория и грейд

**Категория** = роль × грейд × основной стек × формат (+ метки: дисциплина ФСП, предметная область).

| Вариант определения роли и стека | Плюсы | Минусы |
|---|---|---|
| A. Правила по составу навыков | Объяснимо, предсказуемо | Пограничные случаи |
| B. Обучаемая модель | Гибче | Нет реальных данных для обучения |
| C. Свободная оценка языковой моделью | Гибко | Нестабильно, хуже объясняется |
| D. Автоматическое выделение групп | Находит «скрытые ниши» рынка | Группы надо называть, они нестабильны |
| E. Несколько категорий с весами | Реалистично (fullstack = бэкенд + фронтенд) | Чуть сложнее интерфейс |

| Вариант определения грейда | Плюсы | Минусы |
|---|---|---|
| A. Сумма сигналов с порогами (стаж, сложность проектов, ФСП, разряд, тесты, зрелость кода) | Объяснимо, настраивается | Пороги ставятся экспертно |
| B. Обучаемая модель | Красиво | Нет данных |
| C. Оценка языковой моделью с обоснованием | Хорошее текстовое пояснение | Субъективно |
| D. Калибровка по рынку (где кандидат оказывается по офферам) | Самоуточняется со временем | Нет данных на старте |

**Решение:** ✅ категория по правилам с несколькими метками (A + E). Грейд — сумма сигналов (A) с **уверенностью** и **разбивкой**: «почему Middle: стаж +, ФСП ++, код +, тесты нет данных». 🚀 «Скрытые ниши рынка» (D) для экрана аналитики. Калибровка по рынку (D) в дорожной карте.
Продуктовые правила:
- если сигналов мало, грейд показывается с пометкой «предварительно» и подсказкой, как его уточнить;
- кандидат может оспорить категорию: его версия показывается рядом как «заявлено самим».

### 9.7. Уровень доверия к навыку

Профиль — это не список навыков, а **навыки с доказательствами**. Каждое доказательство имеет источник, силу и дату.

| Вариант объединения доказательств | Плюсы | Минусы |
|---|---|---|
| A. Берётся самое сильное доказательство | Просто | Не учитывает несколько независимых подтверждений |
| B. Независимые подтверждения усиливают друг друга | Интуитивно: «подтверждено и ФСП, и кодом» сильнее одного источника | Много слабых сигналов можно «накрутить» |
| C. Среднее | Стабильно | Не растёт от новых подтверждений |

**Решение:** ✅ **B** с ограничениями: один тип источника засчитывается один раз (десять резюме не дают высокого доверия), старые доказательства постепенно теряют вес.

| Источник | Сила | Значок |
|---|---|---|
| Заявлено самим | очень слабая | ○○○○ |
| Резюме | слабая | ●○○○ |
| Код на GitHub | средняя, зависит от авторства и зрелости | ●●○○ |
| Тест на платформе | выше средней | ●●●○ |
| ИИ-интервью по коду / задача с кодом | выше средней | ●●●○ |
| Достижение ФСП | сильная, зависит от уровня и места | ●●●● |

Работодатель может отфильтровать кандидатов по минимальному уровню доверия: «только навыки с ●●● и выше».

### 9.8. Подбор (матчинг) вакансия ↔ кандидат

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Обязательные условия + покрытие навыков с учётом доверия | Объяснимо | Не понимает смежные навыки |
| B. Смысловое сходство текстов вакансии и профиля | Понимает смысл и синонимы | «Чёрный ящик» |
| C. Учёт смежности навыков (знает FastAPI → частично подходит под Django) | Мягкий подбор, объяснимо | Нужна карта смежности |
| D. Текстовое обоснование языковой моделью для лучших кандидатов | Отличные объяснения | Медленно |
| E. Обучение на реакциях (приняли / отклонили) | Самоулучшение | Нет данных на старте |

**Решение:** ✅ **A + B + C**:
1. Сначала обязательные условия: формат, пересечение вилки с ожиданиями, обязательные навыки с достаточным доверием.
2. Затем ранжирование: покрытие навыков (с учётом доверия и смежности), смысловое сходство, соответствие грейда, бонус за ФСП.
3. Объяснение: топ-3 плюса и минуса со ссылкой на доказательства.

🚀 **D** для топ-5 кандидатов на странице вакансии. **E** в дорожной карте: реакции на офферы собираем уже сейчас.

Пример объяснения:
```
92% · Middle Backend Python
✓ FastAPI, PostgreSQL — подтверждено кодом (●●●○) и тестом
✓ Призёр всероссийского этапа по продуктовому программированию, капитан команды
✓ Ожидания 180–220 тыс. попадают в вашу вилку
⚠ Нет подтверждения Kafka (есть смежное: RabbitMQ ●●○○)
```

### 9.9. Проверка навыков (механизм тестирования)

| Вариант | Описание | Плюсы | Минусы |
|---|---|---|---|
| A. Банк тестовых вопросов | Фиксированные вопросы по навыкам | Просто и надёжно | Вопросы утекают, банк нужно собирать |
| B. Вопросы генерируются на лету | Языковая модель создаёт вопросы под навык и уровень | Нет утечек | Возможны ошибки в вопросах |
| C. Адаптивный тест | Следующий вопрос сложнее или проще в зависимости от ответа, уровень определяется за 5–8 вопросов | Быстро, научно обосновано | Нужна экспертная оценка сложности вопросов |
| D. Задача с кодом | Кандидат пишет решение, оно автоматически проверяется | Самая объективная проверка, близко к ФСП | Трудоёмко |
| E. **ИИ-интервью по коду кандидата** | Вопросы задаются по его собственным репозиториям: «почему здесь токены хранятся в Redis?» | Уникально, проверяет авторство | Зависит от качества модели |
| F. Импорт рейтинга Codeforces и подобных | Ещё один объективный источник | Дёшево, логично для олимпиадников | Не у всех есть аккаунт |

**Решение:** ✅ **A + C**: банк вопросов по ~10 ключевым навыкам, адаптивный выбор, прохождение **прямо в Telegram** кнопками. 🚀 **E** — главная вау-фича проверки. **F** — дёшево и полезно для аудитории ФСП (S). **D** только если останется время. **B** используем для пополнения банка, но каждый вопрос проверяет человек.

### 9.10. Поиск обычным текстом (для работодателя)

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Текст превращается в фильтры («бэкенд, Go, удалёнка, до 300 тыс.») | Прозрачно: фильтры видны и редактируются | Сложные запросы понимаются частично |
| B. Поиск по смыслу | Понимает формулировки | Не объясняет, не учитывает зарплату |
| C. Гибрид: фильтры из текста + сортировка по смыслу | Лучшее из обоих | — |
| D. Диалоговый ассистент рекрутера | Вау | Трудоёмко |

**Решение:** ✅ **C**: запрос превращается в чипсы-фильтры, которые можно поправить. 🚀 Кнопка «Создать вакансию из запроса».

### 9.11. Карта рынка талантов

| Вариант | Плюсы | Минусы |

| A. Тепловая карта «роль × грейд» | Наглядно, легко читается | — |
| B. Блоки разного размера по категориям | Хорошо показывает доли | Хуже читается |
| C. Граф навыков рынка | Вау | Сложно читать |
| D. Обычный список карточек | Привычно | Без вау |

**Решение:** ✅ **A** на главной у работодателя: цвет переключается между «количество кандидатов / медиана ожиданий / доля подтверждённых ФСП», клик по ячейке открывает список (D). 🚀 **C** как отдельная вкладка «Навыки рынка».

### 9.12. Анонимность

| Вариант | Описание |
|---|---|
| A. Полная анонимность до принятия оффера | Только навыки, доказательства, грейд, ожидания. Псевдоним вида «Backend #4821» |
| B. Частичная | Компании в опыте видны, ФИО скрыто |
| C. Управляет кандидат | Переключатели: показывать компании, вуз, репозитории |
| D. Открытый профиль | Как на универсальных площадках |

**Решение:** ✅ **A по умолчанию + C**. Названия соревнований ФСП и места показываются (это главная ценность, а установить по ним личность сложно), фамилия в результатах — нет.

## 11. Правила и политики платформы

### 11.1. Офферы
- Вилка «от–до» обязательна. Если вилка ниже минимума кандидата, работодатель получает предупреждение, а кандидат видит пометку «ниже ваших ожиданий».
- Оффер привязан к конкретной вакансии, писать кандидату «просто так» нельзя.
- Срок жизни оффера — ⚠️ например, 7 дней. Потом он истекает, а работодатель получает статус «нет ответа».
- Лимит офферов в день на компанию (⚠️ уточнить число), чтобы не было массовой рассылки.
- На одну вакансию одному кандидату — один оффер.

### 11.2. Отказ и обратная связь
- Отказ одним кликом с причиной: «мало денег», «не тот стек», «не подходит формат», «не ищу сейчас», «другое».
- Работодатель видит причину. Это и есть обратная связь, которой нет на других площадках.
- Агрегированные причины отказов влияют на подбор: если кандидатам постоянно «не тот стек», подбор для этой компании нужно уточнять.

### 11.3. Рейтинг ответственности компании
- Учитывает долю офферов без ответа, долю отказов «не тот стек» и «мало денег», скорость ответа на вопросы кандидата.
- Виден кандидату в оффере. Компании с низким рейтингом получают ограничения.

### 11.4. Видимость и контроль кандидата
- Статусы: «активно ищу» / «открыт к предложениям» / «не беспокоить».
- Стоп-лист компаний (например, текущий работодатель).
- Переключатели видимости: компании, вуз, репозитории.
- Полный профиль и контакты раскрываются только после принятия оффера.
- Каждый просмотр профиля фиксируется, кандидат видит «вас смотрели N раз».

### 11.5. Категория и спорные ситуации
- Категорию и грейд всегда можно объяснить.
- Кандидат может оспорить: его версия показывается рядом как «заявлено самим».
- Достижения ФСП не редактируются вручную, только через синхронизацию.

### 11.6. Модерация
- Компании проходят проверку до первого оффера.
- Кандидат может пожаловаться на оффер (спам, некорректное содержание).
- Подозрительные репозитории не блокируют кандидата, но снижают доверие к соответствующим навыкам.

## 12. Ключевые экраны и сценарии

### 12.1. Кандидат (сайт, адаптивный под телефон)
1. **Онбординг:** согласия → загрузка резюме → привязка ФСП → привязка GitHub. Каждый шаг можно пропустить.
2. **Мой профиль:** категория и грейд с объяснением; навыки со значками доверия, по клику видно, откуда взялся навык; достижения ФСП; радар «ДНК кода».
3. **Офферы:** список с вилкой, процентом совпадения, рейтингом компании.
4. **Навигатор:** чего не хватает до следующего грейда, «что будет, если…», ближайшие соревнования ФСП.
5. **Проверка навыков:** тесты и ИИ-интервью.
6. **Настройки:** статус, минимальная зарплата, формат, видимость, стоп-лист.

### 12.2. Работодатель (сайт)
1. **Карта рынка:** тепловая карта категорий.
2. **Поиск:** строка запроса → чипсы-фильтры → анонимные карточки.
3. **Карточка кандидата:** навыки с доверием, ФСП, ДНК кода, объяснение совпадения, кнопка «Сделать оффер».
4. **Вакансии:** создание и редактирование, подобранные кандидаты по каждой вакансии.
5. **Оффер:** выбор вакансии, вилка, сообщение, подсказка по рынку.
6. **Мои офферы:** статусы, причины отказов, раскрытые контакты.
7. **Команды** (🚀): карточки команд ФСП.

### 12.3. Telegram-бот

| Команда / событие | Поведение |

## 15. Метрики качества в формате хакатона

> Реальных пользователей не будет, поэтому бизнес-метрики (конверсию, время до найма) честно не посчитать. Вместо этого **измеряем, насколько хорошо работает каждая механика**, на трёх типах данных: ручной эталонный набор, синтетический рынок с известным ответом, живые тестовые прогоны.
> **Главный принцип:** каждая цифра сопровождается объяснением «как мерили» и **сравнением с базовым решением** — поиском по ключевым словам, как на обычных площадках. Жюри убеждает именно разница, а не абсолютные цифры на синтетике.

### 15.1. Данные для оценки

| Набор | Что это | Объём | Когда |
|---|---|---|---|
| Эталонные резюме | Реальные резюме (свои, друзей с согласия, обезличенные открытые), размеченные вручную двумя людьми независимо | 30–50 | До старта / Д1–2 |
| Эталонные репозитории | Репозитории команды и знакомых + 5–10 специально подставных (форк, чужой код одним изменением, шаблон) | 20–30 | Д1–3 |
| Эталонная релевантность | 15–20 вакансий, для кандидатов ручная оценка: не подходит / частично / подходит. Размечаем только тех, кого разные методы поставили в топ-20 | ~300–500 пар | Д6 |
| Синтетический рынок | Кандидаты с заранее заданным «настоящим» уровнем навыков (подробнее в 15.2) | 500–2000 | Д2–4 |
| Эталонные текстовые запросы | Запросы работодателя обычным текстом с правильными фильтрами | 30–50 | Д5 |
| Живые прогоны | Люди не из команды проходят сценарии | 5–8 человек | Д8–9 |

### 15.2. Синтетический рынок с известным ответом (главная методология)

Реальных исходов найма нет, поэтому **правильный ответ задаём сами**, а потом проверяем, кто его лучше находит.

1. У каждого синтетического кандидата есть **скрытый настоящий профиль**: реальный уровень каждого навыка и реальный грейд.
2. Из него получаем то, что видит платформа, с типичными искажениями:
   - **резюме:** 20–30% кандидатов вписывают навыки, которых у них нет;
   - **ФСП:** достижения хорошо соответствуют настоящим навыкам (надёжный источник);
   - **GitHub:** есть только у части, среди них встречаются подставные;
   - **тесты:** ответы зависят от настоящего уровня с естественным разбросом.
3. Для каждой пары «вакансия — кандидат» правильная релевантность считается по **настоящему** профилю.
4. Сравниваем:
   - **базовое решение** — поиск по ключевым словам в резюме;
   - **базовое + поиск по смыслу**;
   - **наш продукт целиком**;
   - **наш продукт без ФСП / без GitHub / без тестов**. Отключая источники по одному, видим вклад каждого.

**Формат фразы для питча:** «На синтетическом рынке из 1000 кандидатов, где каждый четвёртый приукрашивает резюме, поиск по ключевым словам находит подходящего кандидата в топ-10 в X% случаев, наш подбор — в Y%. Данные ФСП добавляют Z процентных пунктов».

⚠️ Два правила честности:
- **генератор синтетики и наш подбор устроены по-разному.** Иначе мы просто угадываем сами себя;
- **настраиваем на одной части данных, итоговые цифры считаем на другой.**

О том, что данные синтетические, в питче говорим прямо и показываем параметры генератора.

### 15.3. Метрики по механикам

| Механика | Метрика (простыми словами) | Цель |
|---|---|---|
| **Разбор резюме** | Насколько полно и точно найдены навыки (F1) | ≥ 0.85 |
| | Как часто модель «придумывает» навык, которого нет в тексте | ≤ 2% |
| | Ошибка в стаже | ≤ 6 мес. |

| | Сколько честных репозиториев ошибочно помечено подозрительными | ≤ 10% |
| **Доверие к навыкам** | Насколько уровень доверия соответствует настоящему уровню (синтетика) | Заметно лучше, чем у базового решения |
| | Отличает ли система приукрашенные навыки от настоящих | ≥ 0.8 по AUC (у базового решения ≈ 0.5) |

| | Качество ранжирования (nDCG@10) | Лучше базового решения |
| **Объяснения** | Каждый пункт объяснения ссылается на реальное доказательство | 100% |
| | Понятность объяснения для HR (живые прогоны, 1–5) | ≥ 4 |

| | Оценки ИИ совпадают с оценками людей | Заметная согласованность |
| **Поиск текстом** | Все фильтры распознаны верно | ≥ 70% запросов |
| | Каждый фильтр по отдельности (роль, стек, грейд, формат, зарплата) | ≥ 90% |
| **Связь с ФСП** | Все достижения загружены и превращены в навыки | 100% |
| | Время «привязал ФСП → профиль обновлён» | ≤ 5 с |

### 15.5. Как показать метрики жюри

1. **Страница качества в админке**: таблица «метод × метрика» (базовое решение / наш продукт / без отдельных источников), вклад каждого источника. Продукт измеряет себя сам, и это само по себе вау-деталь.
2. **Воспроизводимый пересчёт метрик** одной командой, отчёт лежит в документации.
3. **Один слайд в питче** с 3–4 цифрами:
   - точность извлечения навыков из резюме;
   - доля приукрашенных кандидатов в топ-10: у поиска по словам против нашего подбора;
   - **на сколько данные ФСП повышают точность подбора** (главная цифра для заказчика);
   - время от резюме до первого оффера и оценка удобства по живым прогонам.
4. **Честный блок «Ограничения»:** синтетика не равна реальному рынку, эталонный набор небольшой, в реальной эксплуатации метрики заменяются на продуктовые (15.6).

### 15.6. Метрики для реальной эксплуатации (для дорожной карты)

Реакции на офферы собираем уже сейчас, чтобы потом их можно было посчитать:
- доля офферов, на которые ответили и которые приняли;
- распределение причин отказа. Доля отказов «не тот стек» прямо показывает ошибки подбора;
- время от регистрации до первого оффера;
- доля наймов и удержание через 3–6 месяцев;
- для ФСП: сколько пользователей перешли из навигатора на соревнование и приняли в нём участие.

## 16. Бизнес-модель и развитие

> Для хакатона это не обязательная часть, но 1 слайд о том, как продукт живёт дальше, обычно добавляет баллов за «бизнес-ценность».

### 16.1. Варианты монетизации

| Вариант | Кто платит | Плюсы | Минусы |
|---|---|---|---|
| A. Подписка для компаний | Работодатель | Предсказуемо | Барьер для малых компаний |
| B. Плата за оффер или раскрытие контакта | Работодатель | Плата только за результат, хорошо работает с обратной механикой | Может стимулировать экономию на офферах |
| C. Процент от найма | Работодатель | Максимально «за результат» | Сложно отследить найм |
| D. Партнёрство с ФСП и спонсорами соревнований | ФСП, компании-партнёры | Компании-спонсоры получают ранний доступ к призёрам | Зависит от партнёрств |
| E. Платные функции для кандидатов | Кандидат | — | Противоречит принципу «для кандидата бесплатно» |

**Рекомендация для питча:** для кандидатов бесплатно всегда. Для работодателей — бесплатный лимит офферов + подписка (A + B). Плюс партнёрская модель с ФСП (D): компании-спонсоры соревнований получают приоритетный доступ к участникам.

### 16.2. Выход на рынок
1. **Стартовая база:** участники соревнований ФСП (регистрация через ФСП, приглашения после соревнований).
2. **Первые работодатели:** компании-партнёры и спонсоры соревнований ФСП.
3. **Рост:** вузы и ИТ-кружки, бейдж «Подтверждено ФСП» на GitHub, профессиональные сообщества.
4. **Цикл:** навигатор отправляет кандидатов на соревнования → новые результаты → более сильные профили → больше работодателей.

## 17. Этика, приватность, право

- **Согласия** даются отдельно: на обработку персональных данных, на запрос данных из ФСП, на анализ репозиториев, на уведомления в Telegram. Отзыв согласия удаляет связанные данные.
- **Анонимность по умолчанию:** до принятия оффера работодатель видит псевдоним и подтверждённые навыки. Каждый просмотр профиля фиксируется.
- **Минимизация:** контакты не используются в подборе, данные обрабатываются локально и не передаются внешним сервисам.
- **Право на удаление:** профиль удаляется полностью по запросу.
- **Защита от предвзятости:** пол, возраст, фото и место жительства (кроме формата и готовности к переезду) не участвуют в подборе и не видны до принятия оффера.
- **Прозрачность:** любой вывод системы можно объяснить, кандидат может оспорить категорию.
- **Соответствие 152-ФЗ** — ⚠️ уточнить у организаторов, какие требования к оформлению согласий нужны для MVP.
- **Анализ кода** не выполняет чужой код, а только читает его. Доступ к закрытым репозиториям — только с явного разрешения.

### 18.1. Сценарий демо (≈3 минуты)
1. **Аня** (студентка, почти пустое резюме) отправляет PDF боту → профиль «Junior Backend Python», навыки ●○○○.
2. «Войти через ФСП» → призёр всероссийского этапа, капитан → значки «загораются» ●●●●, грейд растёт.
3. Вводит GitHub-ник → через 30 секунд радар «ДНК кода», технологии подтверждены (●●●○).
4. 🚀 ИИ-интервью: один вопрос по её собственному коду, ответ засчитан.
5. **Ольга** (HR) пишет: «нужен бэкендер на Python для высоконагруженного API, удалёнка, до 220 тыс.» → чипсы-фильтры → карта рынка → Аня в выдаче с объяснением «92%: ✓ ✓ ⚠».
6. Ольга отправляет оффер с вилкой.
7. На телефоне push в Telegram → «✅ Принять» → контакты раскрыты.
8. Аня открывает навигатор: «Подтверди Docker на соревновании ФСП 15.11, +14 вакансий в твоей категории».
9. 🚀 Приходит новый результат ФСП, и профиль обновляется на глазах.

### 18.2. Структура питча (5–7 минут)
1. Проблема: обе стороны теряют время, резюме ≠ компетенции (цифры из открытых источников, без выдумок).
2. Инсайт: соревнования ФСП — объективное доказательство, особенно для начинающих.
3. Решение: «не резюме, а доказательства», обратный найм.
4. Демо.
5. Как это работает (без технических деталей): доказательства и уровни доверия, ДНК кода, проверка навыков, объяснимый подбор, всё на локальных моделях.
6. Метрики: слайд из 15.5 + ограничения.
7. Ценность для ФСП: цикл «соревнования ↔ карьера», аналитика.
8. Конкуренты: таблица из 4.3, наша колонка заполнена полностью.
9. Бизнес-модель и дорожная карта.
10. Команда.

### 18.3. Демонстрационные данные
- **300–500 кандидатов**: распределение по ролям и грейдам близко к рынку (больше Junior/Middle в бэкенде и фронтенде, меньше в ML, безопасности, встраиваемых системах), ожидания по зарплате соответствуют грейдам.
- Примерно у 40% есть достижения ФСП, у половины анализ GitHub, у 30% пройденные тесты.
- **20–30 компаний**, **60–100 вакансий** с вилками, история офферов (для медиан, статистики и навигатора).
- **2–3 героя демо**, тщательно подготовленных, + один реальный GitHub-аккаунт кого-то из команды для живого анализа.
- Отдельно: синтетический рынок для метрик (15.2). Это не то же самое, что демонстрационная витрина.

## 19. Передача в техническую проработку

Продуктовые решения, которые техническая часть должна обеспечить. Решения по реализации принимаются отдельно. Техническая проработка: [docs/architecture](architecture/overview.md) (черновик `fsp-tech-draft.md` из ранних обсуждений заменён этим разделом).

1. Работа с данными ФСП через сменный модуль: тестовые данные сейчас, реальные потом, без переделки продукта.
2. Разбор резюме PDF/DOCX до ~30 секунд, результат сверяется со справочником навыков.
3. Хранение навыков вместе с доказательствами: источник, сила, дата, ссылка. Пересчёт доверия, категории и грейда при каждом новом доказательстве.
4. Анализ репозиториев в фоне с прогрессом и признаками подозрительности.
5. Подбор: условия → ранжирование → объяснение со ссылками на доказательства.
6. Поиск обычным текстом → фильтры.
7. Адаптивный тест и ИИ-интервью, в том числе через Telegram.
8. Telegram-бот, push об оффере с кнопками, вход на сайт по ссылке из бота.
9. Анонимизация и журнал просмотров, согласия, удаление профиля.
10. Только локальные модели.
11. Генератор демонстрационных данных и синтетического рынка для метрик, воспроизводимый пересчёт метрик.
12. Развёртывание, документированное API, инструкция по развёртыванию, техдокументация (требование кейса).

## 21. Открытые вопросы

**К организаторам и экспертам ФСП:**
1. Какие данные есть в API: составы команд, полные таблицы результатов, уровни соревнований, шкала разрядов, треки, контакты участников?
2. Как подтвердить, что пользователь — этот участник ФСП?
3. Можно ли получать новые результаты сразу после соревнования?
4. Критерии оценки и их веса.
5. Нужна ли интеграция с внешними вакансиями или только внутренние?
6. Какие дисциплины приоритетны для ИТ-найма? Как эксперты видят соответствие «дисциплина → навыки»?
7. Есть ли требования к оформлению согласий на обработку данных?
8. Где разворачивать продукт, есть ли ограничения на внешние сервисы (например, GitHub)?

**Внутри команды:**
1. Кто совмещает роль PM.
2. Кто отвечает за разметку эталонных данных.
3. Кто готовит питч и демо.

## 22. Глоссарий

| Термин | Значение |
|---|---|
| Обратная механика | Работодатель ищет кандидата и пишет первым |
| Доказательство | Подтверждение навыка из конкретного источника: резюме, код, тест, ФСП |
| Уровень доверия | Насколько можно верить навыку, значки ○○○○…●●●● |
| Категория | Роль × грейд × основной стек × формат |
| ДНК кода | Итог анализа репозиториев: технологии, авторство, зрелость, радар |
| Адаптивный тест | Сложность следующего вопроса зависит от предыдущих ответов |
| ИИ-интервью по коду | Вопросы по собственным репозиториям кандидата |
| Навигатор | Подсказки, чего не хватает до следующего грейда и где это подтвердить |
| Mini App | Приложение внутри Telegram без установки |
| MoSCoW | Must / Should / Could / Won't: приоритизация требований |
| Базовое решение | Поиск по ключевым словам, с которым сравниваем наш подбор |
| SUS | Стандартная анкета удобства интерфейса, балл 0–100 |
| JTBD | Jobs to be Done: какую задачу пользователь «нанимает» продукт решить |
